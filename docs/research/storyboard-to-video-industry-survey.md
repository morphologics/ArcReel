# Survey of how the industry implements "storyboard-to-video"

> Purpose: to provide a basis for one of ArcReel's data modeling decisions — whether the grid (grid_4/6/9) should be modeled as "an assembly optimization option inside the storyboard route" or as "an independent generation route". This document states only first-hand facts and does not make the decision for the owner. Survey date: 2026-08-03; all "access dates" are that day. Products and models update quickly; conclusions marked "no first-hand source found" should be treated as possibly outdated.

## I. Core conclusions (answer first)

**No public API of any mainstream video generation model was found that natively accepts "one whole multi-panel storyboard image" as a conditioning input, has the model break it down internally into multiple shots in one go, and outputs one continuous multi-shot video.** After checking Sora, Vidu, Kling, Jimeng/Seedance, Hailuo, Pika, Runway and Google Veo/Flow one by one, all existing "storyboard-to-video" capabilities in the industry fall into one of the following three categories, often with two or three layers stacked in the same product:

1. **Reference-to-video (r2v)**: feed roughly 1–9 images as anchors for character/style/subject consistency, and the model outputs **one continuous video**; the images don't correspond to specific shots or time segments. This is the common underlying capability at the API layer of Vidu, Kling, Seedance and Hailuo, with clear terminology boundaries that are consistent across vendors.
2. **First/last frame**: exactly 2 images define the start and end states, and the model interpolates the motion in between, still producing **one continuous video**. Kling, Veo 3.1, Hailuo and Jimeng all have this capability; it is a narrower special case of r2v (the image count is fixed at 2 and has explicit temporal semantics).
3. **UI-layer timeline/storyboard orchestration (storyboard editor)**: Sora's storyboard editor, Google Flow's Scenebuilder, Jimeng's "故事创作" (Story creation) mode and Runway's Multi-Shot Video Recipe are all **product or orchestration layer** features — the user organizes content by shot/card, and the system still calls the underlying generation capabilities (text-to-image/image-to-video/image-to-image) shot by shot, then stitches and adds transitions, rather than feeding one multi-panel image to the model to get a video in one go.

**The only practice close to ArcReel's grid approach (a strong image model produces a large multi-panel image → cut → image-to-video panel by panel)** is the gpt-image-2 + Seedance 2.0 workflow documented in third-party blogs: first have gpt-image-2 generate a 3×3 nine-panel storyboard image (nine panels in one image), then feed it panel by panel to Seedance for image-to-video — but this is **a manually combined workflow at the community/tutorial level, not a single API or button productized officially by any vendor** (see V.6). In other words, ArcReel's existing grid implementation already sits at the frontier of known industry practice, rather than lagging behind some existing "native storyboard-to-video" capability in the industry.

## II. Findings by product / by model

### 1. OpenAI Sora (Sora 2 / storyboard)

**Product UI layer**: Storyboard is an editor in the Sora 2 web app for ChatGPT Pro users, entered by clicking "storyboard" in the composer. Users can "build a video frame by frame from scratch — just like storyboards in Sora 1, or simply describe a scene, choose a duration, and let Sora generate a detailed editable storyboard". The storyboard editor organizes multiple prompt cards (caption cards describing scene/character/action) in chronological order into "a single multi-shot clip"; it also supports using keyframe images directly instead of text descriptions, and "Sora generates a video connecting these still images". There is also a separate **Stitching** feature for joining multiple **separately generated** clips into one video up to 60 seconds long — a feature alongside the storyboard editor, showing that OpenAI itself distinguishes between two different mechanisms: "a multi-shot storyboard generated in a single pass" and "stitching multiple independently generated results".
Source: OpenAI Help Center, "Creating videos with Sora" https://help.openai.com/en/articles/12460853-creating-videos-with-sora (direct fetching was blocked with 403; the above is the search-engine-indexed summary of the official page and could not be checked sentence by sentence against the full text; access date 2026-08-03).

**Model API layer**: Sora currently has no public third-party developer API documentation describing the underlying input contract of storyboard (Sora 2's API access is mainly about video generation itself; storyboard is an editing experience inside the ChatGPT/Sora product); no official documentation was found explaining whether the storyboard editor, when submitting to the underlying model, does "one call with joint multi-shot generation" or "per-card calls stitched internally by the model". This point has **no first-hand source confirming it**; it can only be confirmed that at the product level it presents as "one generation yields one multi-shot video".

### 2. Vidu (Shengshu Technology)

**Product UI layer**: Vidu's official product names this capability **Reference to Video (参考生视频)**, an independent generation mode alongside text-to-video and image-to-video.

**Model API layer**: The official API documentation states clearly: the `reference2video` endpoint of models such as viduq3-mix / viduq3-turbo / viduq3 / viduq2 / viduq1 / vidu2.0 accepts **1–7 images** (viduq2-pro drops to 1–4 if a video is also uploaded); the documentation says verbatim: "The model will use the provided images as references to generate a video with consistent subjects" — the images are **subject/style consistency references** and don't correspond to specific shots or time segments; **the words "storyboard" or "分镜" do not appear** in the documentation. The output is one continuous video (the maximum duration varies by model; the viduq3 series supports up to 16 seconds at 1080p).
Source: Vidu official API documentation https://platform.vidu.com/docs/reference-to-video, access date 2026-08-03.

### 3. Kling (Kuaishou)

**Product UI layer**: The Kling open platform subdivides image-to-video into parallel modes such as "based on first frame", "based on first and last frames", "reference-to-video" and "video editing"; the Chinese product page's marketing wording for "参考生视频" (reference-to-video) is close to "multi-image reference", but **no official usage calling it "分镜板生视频" (storyboard-to-video) was found**.

**Model API layer** (verified against Kling's official API parameters via the Alibaba Cloud Model Studio (Bailian) documentation mirror; Alibaba Cloud is a reseller providing access to Kling, and the documentation describes Kling's native API contract):
- Text-to-video: no image needed, outputs a single continuous video of 3–15 seconds.
- Image-to-video (first frame): 1 image, used as the "first frame image", outputs a single continuous video.
- Image-to-video (first and last frames): 2 images, the start frame and the end frame respectively; the model interpolates between the two frames and outputs a single continuous video.
- Reference-to-video (multi-image reference): at most 7 reference images (the total including the length of the multi-image subject element_list array may not exceed 7; drops to 4 if a feature video is also provided); the documentation stresses that these are "reference images" for subject/style consistency, **not mapped one to one to shots/time segments**, and the output is still a single continuous video (3–15 seconds, or 3–10 seconds when combined with a feature video).
Source: Alibaba Cloud Model Studio, "可灵视频生成 API 参考" (Kling video generation API reference) https://help.aliyun.com/zh/model-studio/kling-video-generation-api-reference/, access date 2026-08-03. Kling's official developer sites https://klingai.com/document-api/apiReference/ and https://kling.ai/document-api/apiReference/model/multiImageToVideo were blocked with 403/446 on several direct fetch attempts, so the official text could not be checked sentence by sentence; the parameters above follow the Alibaba Cloud mirror documentation and are marked as a **semi-first-hand source** (Alibaba Cloud describes pass-through parameters of Kling's official API, not its own development, but it is ultimately not the original text on Kling's website).

### 4. Jimeng Dreamina / Seedance (ByteDance)

**Product UI layer**: The Jimeng website (jimeng.jianying.com) offers a "故事创作" (Story creation) mode: the user enters story text, Jimeng first automatically generates a **storyboard script** (broken down into multiple storyboard shots), and after confirmation **generates the corresponding image for each storyboard shot separately**, and finally "automatically composes the storyboard images into a video, including transition effects and basic animation" — that is: text → storyboard script → image per panel → video per panel (or per segment) → stitching + transitions, a multi-step pipeline at the **product orchestration layer**, not a model taking one multi-panel image and producing a video in one go. Jimeng also has a separate "首尾帧" (first and last frame) input method (a first-frame image + last-frame image control the start and end states of a single video), a capability alongside the Story creation mode.
Source: third-party tutorials and encyclopedia entries aggregated by search engines paraphrasing Jimeng's website feature pages (CSDN, Zhihu tutorials, baike, etc.); **no sentence-by-sentence original text from Jimeng's official help center on the "Story creation" workflow was found**; the workflow description above is a second-hand paraphrase; please note: this is cited from second-hand reports and has not been directly verified against Jimeng's official documentation. Access date 2026-08-03.

**Model API layer (Seedance, Volcengine Ark official API)**: The Seedance 2.0 series API officially launched on 2026-04-14, supporting four input modalities — text/image/audio/video; image-to-video supports first-frame or first-and-last-frame control, and multimodal reference supports joint generation with 0–9 reference images + 0–3 reference videos + 0–3 reference audio clips. This is the same paradigm as Vidu's/Kling's "reference-to-video": multiple images as consistency references, a single video as output, not a mapping from storyboard panels to shots. **Seedance 2.5** (per public information from the Volcengine FORCE conference on 2026-06-23, still in the rollout stage) claims native output of 30-second continuous video and supports joint generation with up to 50 all-modality reference materials — essentially still "more reference materials and longer single-video duration"; **no official documentation was found stating that this is a new contract of "multi-panel storyboard image" or "per-shot timeline conditioning input"**; this conclusion is based on third-party tech media reports (SegmentFault, PingWest, Sina Finance), which are second-hand sources; the specific parameter pages of Volcengine's official Ark documentation failed on several fetch attempts (404/redirected to the navigation page), so the first-hand parameter table could not be verified; **marked as no first-hand source found**.
Sources: "火山引擎：Seedance 2.0API 服务全面开放" (Volcengine: Seedance 2.0 API service fully opened) https://www.stdaily.com/web/gdxw/2026-04/14/content_502009.html (second-hand media report quoting Volcengine's official release); Volcengine Ark documentation entry https://docs.volcengine.com/docs/82379/1951250 (only the navigation page was fetched; the parameter body could not be read). Access date 2026-08-03.

### 5. Hailuo (MiniMax)

**Product UI layer**: No first-hand statement of "分镜/storyboard" as an independent official product feature was found; search results show Hailuo's product positioning as "generating video directly from text/images, skipping the traditional script–storyboard–shoot process", i.e. the product positions itself as **bypassing** the storyboard step, rather than providing a storyboard orchestration tool.

**Model API layer**: The official API documentation (video-generation-v2-create) explicitly distinguishes input content by role: `first_frame` / `last_frame` (at most 1 each) and `reference_image` (at most 9) / `reference_video` / `reference_audio`, and **first/last frame mode and multimodal reference mode are mutually exclusive**; the documentation says verbatim: "图生视频与多模态参考生视频互斥" ("Image-to-video and multimodal reference-to-video are mutually exclusive"). The output is "one continuous video clip", with no input concept of storyboard/multi-panel image/multi-shot timeline.
Source: MiniMax open platform documentation center, "创建视频生成任务" (Create video generation task) https://platform.minimaxi.com/docs/api-reference/video-generation-v2-create, access date 2026-08-03.

### 6. Pika

**Product UI layer**: Pika's **Scene Ingredients / Pikascenes** feature allows uploading multiple images (characters/props/costumes/backgrounds) and blending them into one shot; marketing copy contains wording such as "translate storyboards into detailed prompts", but this is only "using the word storyboard as a marketing analogy"; the feature is essentially **single-shot** multi-reference-image composition, does not produce multi-shot video, and has no multi-panel image input.
Source: aggregated information from Pika-related pages (there are many third-party mirror pages such as pikartai.com; **the original first-hand documentation on pika.art was not located**; the above is based on search engine summaries and is marked as possibly not fully first-hand). Access date 2026-08-03.

**Model API layer**: The parameters of the Pika API's pikascenes endpoint (relayed via platforms such as fal.ai) are a list of image URLs + prompt + aspect ratio/duration, etc.; it is likewise multi-image-reference single-shot generation with no concept of storyboard panels.

### 7. Runway

**Product UI layer / API layer (combined)**: Runway Dev's official documentation provides a "Recipe" explicitly named **Multi-Shot Video** (an orchestration-layer wrapper interface, not the underlying foundation model itself). It has two modes:
- **auto mode**: submit a story prompt, and Runway internally breaks the story down into several shots.
- **custom mode**: the user provides a shot list of 3–5 shots, each with `prompt` (3–512 characters) and `duration` (seconds); Runway "refines and assembles" these shots, keeping the user-specified order.
The endpoint returns a task id, and polling `GET /v1/tasks/{id}` yields the final output video URL — **only one API call is exposed externally**, but the official documentation does not say whether internally it calls the Gen-4/4.5 foundation model separately for each shot and then stitches, or whether there is a genuine single-pass joint multi-shot generation model; the name "Recipe" itself suggests an orchestration-layer wrapper built on top of the foundation models, but **no explicit official statement on this was found; marked as unconfirmed**.
Source: Runway Dev official documentation, "Multi-Shot Video" https://docs.dev.runwayml.com/recipes/multi-shot-video/, access date 2026-08-03.

### 8. Google Veo / Flow

**Model API layer (official Gemini API documentation)**: Veo 3.1 supports: `image` (first frame, single image), `lastFrame` (last frame, single image; interpolation supported only by Veo 3.1), and `referenceImages` (at most 3, for style/content guidance, type `VideoGenerationReferenceImage`). The documentation states "Videos per request: 1" — **each request outputs one continuous video**; there is no wording or parameter for "storyboard" or "single-pass multi-shot generation" in the documentation.
Source: Google AI for Developers, "Generate videos with Veo 3.1 in Gemini API" https://ai.google.dev/gemini-api/docs/veo, access date 2026-08-03. For first/last frame interpolation see also the Google Cloud documentation "Generate videos using first and last video frames" https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/video/generate-videos-from-first-and-last-frames, access date 2026-08-03.

**Product UI layer (Flow)**: Flow is Google's product-layer tool for film and video creators, with a built-in **Scenebuilder**, which the official blog calls "your in-Flow storyboard" — in it, users assemble **individually generated shots** into a complete narrative and can edit/extend existing shots (keeping character consistency and continuity of motion), but underneath each shot is still generated by a separate call to Veo; Scenebuilder is a **product orchestration/timeline UI**, not a capability where the model takes a multi-panel storyboard image and produces a video in one go. Flow's "Ingredients to Video" supports at most 3 reference images per prompt, corresponding to the Veo API's `referenceImages`.
Source: Google official blog, "Introducing Flow: Google's AI filmmaking tool designed for Veo" https://blog.google/innovation-and-ai/products/google-flow-veo-ai-filmmaking-tool/, access date 2026-08-03.

### 9. Higher-level products built on gpt-image-1/2 (third-party workflows, not official product features)

OpenAI officially does not promote "storyboard" as a productized feature of the gpt-image-1/2 image API; gpt-image-2 is essentially still a general-purpose image generation/editing model. But several third-party tutorials (Venice.ai, Alici, CrePal, Rewarx, etc.) document a manual workflow: **use gpt-image-2 to generate one 3×3 nine-panel image in one go (a single image containing 9 panels, each representing a shot), then cut this image and feed it panel by panel to Seedance 2.0 for image-to-video**, used for making trailer/ad storyboards. This is structurally highly consistent with ArcReel's existing grid_4/6/9 implementation: a strong image model produces a jointly generated large multi-panel image (preserving art style/character consistency) → cut → i2v panel by panel. **But this is only a combined workflow summarized by the community, not a single API or button feature officially released by any vendor**; no vendor claims "this is our native storyboard-to-video capability".
Sources: Venice.ai blog, "How to Create AI Trailers with GPT Image 2 + Seedance 2.0" https://venice.ai/blog/how-to-create-ai-trailers-gpt-image-2-seedance; Rewarx, "Generate Storyboard Frames with GPT Image 2" https://www.rewarx.com/blogs/generate-storyboard-frames-gpt-image-2. Both are third-party tutorials/second-hand content, not vendor first-hand documentation; access date 2026-08-03.

## III. Terminology

| Term | Prevailing meaning in the industry | First-hand basis |
|---|---|---|
| **reference-to-video / 参考生视频 (r2v)** | Input several (usually 1–9) static reference images of characters/scenes/props as **anchors for subject and style consistency**, and the model generates **one continuous video** from the text prompt; the images don't correspond to specific shots or time segments; it is a third generation mode alongside text-to-video and image-to-video. Terminology and implementation are highly consistent across vendors. | Vidu official API (`reference2video`, 1–7 images); Kling "参考生视频" (≤7 images); Seedance multimodal reference (0–9 images); MiniMax `reference_image` (≤9 images, mutually exclusive with first/last frame) — all confirmed by first-hand documentation |
| **first/last frame / 首尾帧** | A special case of r2v: exactly 2 images, semantically the "start state" and "end state", the model interpolates the motion between the two frames, and the output is still one continuous video. | Kling image-to-video (first and last frames); Google Veo 3.1 `image`+`lastFrame`; MiniMax `first_frame`/`last_frame`; Jimeng first/last frame input (for first-hand/semi-first-hand sources see the sections above) |
| **storyboard-to-video / 分镜板生视频** | **There is no unified technical meaning consistent across vendors**; it is a fuzzy zone spanning "product marketing term" and "UI orchestration-layer feature", and what it actually refers to splits by product into: ① Sora: multiple text/keyframe "cards" arranged in chronological order, with the model outputting one continuous multi-shot clip (the product calls it a "single multi-shot clip", but whether it is a single joint generation underneath is not confirmed first-hand); ② Jimeng "Story creation": text broken down into a storyboard script → image per panel → video per panel → stitching with transitions (explicitly multiple calls + stitching at the orchestration layer); ③ Runway Multi-Shot Video: shot list → Runway's orchestration layer assembles one video (whether it internally calls the underlying model multiple times is not officially confirmed); ④ Google Flow Scenebuilder: assembling already-generated independent shots on a timeline (orchestration UI, not a single model input); ⑤ Pika/gpt-image type: only borrowing the word "storyboard" as an analogy in marketing copy; the feature is actually single-shot multi-image reference composition, or a community workflow that must be done manually step by step. **No first-hand documentation describes a contract where "the model API natively accepts one whole multi-panel storyboard image as a single input, automatically splits it into shots internally and outputs a continuous multi-shot video".** |
| **Chinese 「分镜板生视频」** | In Chinese contexts (Jimeng "Story creation", various tutorials), this phrase almost always refers to a **multi-step pipeline experience** of "AI-assisted generation of a storyboard script/storyboard images, then converting panel by panel to video, and finally stitching", i.e. the orchestration-layer meaning ④ in the table above, not "feeding one storyboard image to the model to get a video in one go". | Description on Jimeng's official product page (via second-hand paraphrase, see section 4 above; Jimeng's first-hand original text was not directly verified; marked as for reference) |

## IV. Implications for ArcReel's modeling decision (for reference, not deciding for the owner)

The following is the direction of the evidence obtained in this survey, for reference in the decision:

1. **No first-hand evidence was found supporting the existence, in any mainstream product or public API, of a native capability of "feeding a whole storyboard sheet directly to a video model and outputting a continuous multi-shot clip in one go".** All features named "storyboard" are underneath either per-shot calls to generation capabilities followed by stitching (the keyframe mode of the Sora storyboard editor, Jimeng Story creation, Runway Multi-Shot Recipe, Flow Scenebuilder), or borrowed marketing vocabulary (Pika). This means that if ArcReel wants to distinguish, in its data model, an "industry-existing native storyboard route", there is currently no first-hand factual basis to support it — because this "native form" itself does not yet exist in the verified public products/APIs.

2. **ArcReel's existing grid implementation (a strong image model produces a large multi-panel image → cut → i2v per scene) structurally corresponds exactly to the only documented practice in the industry, and the one closest to the literal meaning of "storyboard-to-video"** — namely the third-party combined workflow of gpt-image-2 + Seedance 2.0 (see II.9). But this is ultimately "using the multi-panel image generation capability of a general-purpose strong image model to optimize the batch-consistent generation of storyboard images", after which it still has to go through image-to-video scene by scene in the ordinary way — essentially still ArcReel's existing "storyboard route" (image-to-video, driven by storyboard images), only with a batch-processing optimization of how the storyboard images are produced. There is no evidence that this constitutes a generation route independent of the "storyboard route" with a different model input contract.

3. **The industry does have a third paradigm parallel to ArcReel's existing "storyboard route" (i2v) and "reference-to-video route" (r2v, `lib/script/reference_video/`), with a clear, independent model input contract** — namely "first/last frame" (exactly 2 images, with explicit start/end temporal semantics). This paradigm does not seem to be explicitly distinguished in ArcReel's modeling yet (if ArcReel's current image-to-video is driven by the first frame, then "first/last frame" may be an optional keyframe input sub-mode inside the i2v route rather than an independent route) — this is outside the scope of this survey and is raised only as a side observation.

4. **Direction of evidence**: modeling the grid as "an assembly optimization option inside the storyboard route" fits the industry facts found in this survey better than modeling it as an independent "generation route" — because the core criterion for distinguishing "generation routes" should be "whether the input contract accepted on the model side differs" (the input of i2v is a single storyboard image; the input of r2v is a set of asset reference images), and the grid does not change the input contract finally fed to the video model (it is still a single cut first/last frame image going through i2v); what it changes is only the upstream assembly step of "where and how the storyboard images are produced". But this is ultimately a data modeling trade-off, and the owner may have other product/engineering considerations; this document does not decide on their behalf.

## V. Method and limitations

- Several vendors' official developer sites (klingai.com, kling.ai, some deep parameter pages of docs.volcengine.com, help center articles on help.openai.com) were blocked with 403/446 or redirected to navigation pages on direct fetching, so the original text could not be checked sentence by sentence; these cases are marked one by one in the corresponding sections, with lower-credibility alternative sources used instead (search engine summaries, Alibaba Cloud reseller documentation mirrors, third-party media reports), explicitly noted as "semi-first-hand" or "second-hand, no first-hand source found".
- Whether Seedance 2.5 and Sora storyboard do single joint generation underneath vs. multiple orchestration-layer calls + stitching are the two biggest uncertainties in this survey; both are marked as not confirmed first-hand.
- The survey focused on the wording of official documentation and did not test each product in practice (such as actually calling the APIs and observing the results), so "not written in the docs" does not fully equal "the capability does not exist"; reviewers please note this limitation.
