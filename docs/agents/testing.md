# Running tests

After changing code or tests, the development loop first runs the smallest set of tests relevant to the change; before pushing, run the full gate for the affected domains as described in `AGENTS.md`.

## Selecting relevant tests

If the selection yields 0 tests, widen it to the corresponding directory or the full test suite; 0 tests does not count as passing verification.

- **Backend test files changed**: run those files directly.
- **Backend source changed**: `uv run python -m pytest --testmon`. pytest-testmon runs only the test cases affected by the change, according to the coverage relationships recorded in `.testmondata`; without a data file it runs the full suite and builds the database, and only after that is it incremental. When building the database for the first time or when the change surface is large, add `-n 4 --dist loadfile`; for small selections, parallelism is actually slower. Code executed in a separate process is not in the coverage relationships (e.g. test cases like `tests/integration/test_imports.py` that import in a subprocess); when changing modules they touch, run them additionally by path. Passing it a directory narrows the scope further; test selectors with `::`, `-k` and `-m` make it fall back to no filtering, and are only for manual pinpointing.
- **Changes that need the full backend suite**: `pyproject.toml`, `uv.lock`, the root `tests/conftest.py`, package initialisers containing behaviour, or anything involving Alembic, profile, DB, i18n or shared test infrastructure; also run the full suite when you cannot judge the scope of impact.
- **Frontend test files changed**: pass the files directly to Vitest.
- **Frontend source changed**: in `frontend/`, run `pnpm exec vitest related --run <source file>`; for branch-level checks use `pnpm exec vitest run --changed <base>`. TypeScript source changes also run the full typecheck.
- **Changes to the frontend page-level suites (`frontend/e2e/`), changes to layout- or scroll-related components, or changes to the set of APIs called or to when stream connections (including SSE) are established**: run `pnpm e2e` in `frontend/`. Page-level suites only replay recorded doubles and scenario `api` overrides, and unrecorded requests fail outright; when local rendering differs from CI, the result inside the container is authoritative; see "Frontend page-level tests" in `CONTRIBUTING.md` for how to run it. When changing the response shape of a backend API, also run `pnpm e2e:record` to re-record the API doubles.
- **Changes that need the full frontend suite (`pnpm check`)**: `package.json`, `pnpm-lock.yaml`, `vitest.config.*`, test setup, i18n or branding.
- **Subpackage `packages/arcreel-market-core/` source changed**: run all of the subpackage's tests (`cd packages/arcreel-market-core && uv run python -m pytest`; the subpackage has its own pytest configuration and is collected separately from the main repository), and select relevant tests by the main repository's importers; when the subpackage's message keys are added or removed, also run `tests/unit/lib/i18n/`.
- **Subpackage `packages/arcreel-catalog-core/` source changed**: run all of the subpackage's tests (`cd packages/arcreel-catalog-core && uv run python -m pytest`), and select relevant tests by the main repository's importers.

## Running in a worktree

A worktree has no `.venv` or `node_modules`: for the backend run `uv sync` first; for the frontend and docs site run `pnpm install --frozen-lockfile` in their respective directories. Copying the main checkout's `.testmondata` into the worktree skips testmon's first database build; the file records coverage relationships indexed by code fingerprint, and parts that do not match the current code are treated as changed and rerun. Test cases marked `local_port` are skipped, with the reason noted, in sandboxes that forbid binding local ports; the full suite needs to be run once in an environment that allows binding ports. The root conftest sets `PYTHON_DOTENV_DISABLED=1` for the test process and reads no `.env` at all, so the worktree root does not need an empty file to block the main checkout's `.env`; test cases that verify `.env` loading rules call `delenv` themselves.

## Event loop blocking guard

The root conftest loads `tests/blocking_guard`: for both sync and async test cases, it records throughout any blocking calls made by lib/server code on the event loop thread (including the application thread behind a sync `TestClient`), and at the end of a test case, violations not on the exemption list fail that test case, with the failure message giving the entry and call stack. The call stack lists lib/server/tests frames from innermost to outermost, preceded, in actual call order, by the innermost few non-repository frames between the blocking point and the first repository frame (standard library and third-party packages, with paths in package-relative form, and the number of omitted frames noted if there are more), used to tell which non-repository code invoked at a business-code `await` is doing the blocking. The entry is the lib/server async function closest to the blocking point (`<file>::<qualified name>`), even when the blocking happens in a double under `tests/`: once swapped for the production dependency, the same place would block the event loop just the same. When a double produces a false positive, fix the double according to the production implementation's threading contract: if it can be implemented in memory, change it to an in-memory implementation; if the double's responsibility inherently involves writing to disk (backends writing artifacts, simulating concurrent writers, calling production callbacks that write formal files), put that I/O in `asyncio.to_thread`. Blocking with no lib/server async function in the outer frames (a test function directly calling synchronous lib code) does not count.

- `tests/blocking_guard/exemptions.toml` holds permanent exemptions, accepting only one-off blocking on application startup and shutdown paths, each with a stated reason. There is no other way to get an exemption; newly added blocking calls are always fixed. In a full run, exemption entries not triggered in this run fail the session: if the startup or shutdown path changes, delete the corresponding entries at the same time. Every exemption must be triggered by a test case under `tests/unit`: CI's unit job runs only `tests/unit` by path, and with `--blocking-guard-expect-all-exemptions` it performs the same check, reporting untriggered entries as stale; the integration job does not pass that flag.

## CI hang diagnostics

The backend test job sets `ARCREEL_TEST_HANG_DUMP_DIR`, and `tests/hang_watchdog.py`, loaded by the root conftest, makes the xdist controller and each worker record the test case they start executing, and dumps the call stacks of all threads when a process makes no progress for 180 seconds; the session teardown and process exit phases are covered too. The test step timeout is shorter than the job timeout, and after the step fails or is cancelled, the "Hang and crash diagnostics" step outputs each process's last progress, thread stacks and kernel OOM records. A process whose progress ends at `sessionfinish` or `unconfigure` finished the session; a process whose progress stops at some `run` test case got stuck on or died in that test case. When investigating a hang or `node down: Not properly terminated`, look at this step first: the last test case of the downed worker is the one that was running at the time of the crash, and the controller's progress records its exit code or termination signal; then find the call stack according to how it died:

| How it died | Where the call stack is |
| --- | --- |
| Called `os._exit` | That worker's `.stacks`, with the header `调用 os._exit(<退出码>)` (Called os._exit(<exit code>)) |
| Terminated or interrupted by SIGTERM, SIGHUP or SIGINT | The process's file of the same name with `.SIGTERM` etc. |
| Segmentation fault or other fatal signal | `Fatal Python error` in the test step's stderr; if that line is absent, faulthandler's handler could not run, e.g. a stack overflow on a non-main thread |
| Killed by SIGKILL | No stack; check the kernel log for OOM |

The xdist commands in CI and the local gate carry `--max-worker-restart=0`: after a worker crashes, no replacement worker is started, and the run fails directly. When pytest-xdist 3.8.0 replaces a worker, it re-queues files that have already finished, and the session hangs at 99% (upstream pytest-dev/pytest-xdist#1378, fix commit 25282ab). Once the dependency is upgraded to a version containing that commit, this flag can be removed. When reproducing locally, set the same environment variable to get the same files.
