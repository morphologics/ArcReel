# Project Schema Migrations

Follow this document when adding or modifying a migration step in `lib/project/project_migrations/`, or changing the artifact backfill planner (`lib/artifacts/artifact_planner.py`). The structure of the migration chain, backup naming and the failure verdict mechanism are described in `docs/adr/0022`, `docs/adr/0062` and `docs/adr/0075`; this document only holds conventions that cannot be found in the code.

## Steps

1. **List every legacy shape this step must handle.** Each shape is "data written by code before some version that differs from what the current code expects"; the table below is the known list, and newly discovered shapes are added to it first. Done when: every relevant shape has a constructed sample in `tests/legacy_project_shapes.py`.
2. **Write the migrator, with an exit for both registering and skipping.** A release adds at most one migration step: if `CURRENT_PROJECT_SCHEMA_VERSION` is greater than the value at the most recent `v*` release tag, the latest step has not been released yet and the change goes into that step; only when the two are equal is a new step opened. Migrations that rewrite the artifact manifest return `ArtifactBackfillOutcome` (`lib/project/project_migration_report.py`), and the runner folds it into `.migration_report.json` inside the project. Every "do not register" branch in the planner calls `_skip(...)` with a reason, and those the user should see also carry a `category`: `unreadable` (artifact file cannot be read) or `legacy_audio_basis` (legacy voice-over missing TTS settings). A skip without a `category` means the basis cannot be computed; it reads as missing and does not go into the report. Done when: every skip with a `category` appears in the migration report.
3. **Run legacy shape samples through to the user's view.** Besides the migrator's own assertions, at least one test case uses `WorkflowStateService.get_project_summary` / `get_status` or the presentation read model to assert what the user sees (counts, status, preview available). Done when: the test cases under `tests/integration/lib/project/project_migrations/` cover the whole chain from "≤ the previous actually installed version" to the current version (`migrate_project_dir`), not just a single step.
4. **Update the user-facing migration notes.** The "Project structure migration" section of `website/docs/ops/deployment.md` describes backup, report and retry behaviour; if behaviour changes, update it.

## Conventions

- Upgrade paths often span multiple versions: a migration must handle all the variants left by earlier versions, not just the standard shape written by the previous version.
- Backups go through `lib/project/project_migrations/backups.py`; migrators that back up their own inputs are registered in the runner's `_MIGRATORS_WITH_OWNED_BACKUP`.
- Migrations that rewrite the manifest use `activate_artifact_target_state(bump_schema=True, target_schema_version=...)`, doing a read-only pre-check before writing to disk.
- Whole activation registers every present artifact as current. When only some basis input changes and existing artifacts should not become stale because of it, plan the target state once before and once after the change, and rewrite only entries that "were current before, and whose target registration changed" (precedent: style value normalisation in v13→v14), so that entries already stale are not faked as current. Archive imports with an envelope turn the claims in the envelope into a staged manifest before migration (`stage_preserved_artifact_claims`), and the migration chain rewrites them just as in an in-place upgrade, so migration steps that rewrite the manifest need no separate path for archives; import activation then restores the post-migration claims by content evidence.
- Legacy shapes written by the normal flow in the past are normalised uniformly at the chain head: `legacy_shapes.normalize_legacy_shapes` runs once at the first version ≥ v6 on the chain, before the script rewrite of v6→v7 and before any target state planning, so later migration steps and the planner only see normalised shapes. Newly discovered shapes of this kind are added here, not rejected separately in each step. Rejecting a whole project because of data is limited to `project.json` or scripts unreadable, `versions.json` or `.arcreel_artifacts.json` unreadable, corrupted script entry structure (corrupted v6 legacy ad shot index or unit structure, v8 units that are not objects), and unsafe import packages; the planner's fault tolerance takes effect only in activation mode (`_activation_mode`), and runtime behaviour is unchanged.
- Every change made by normalisation is recorded as a `MigrationAdjustment` (report section "Adjusted"), and files left as-is because they cannot be read are recorded as skips with a `category` (report section "Could not be brought in"); the report has only these two sections. Skips where the basis cannot be computed (generation gaps, no version record, non-canonical paths, source text not UTF-8, etc.) carry no `category` and are filtered out by `write_migration_report` / `extend_migration_report`; units needing re-planning do not go into the report either: for entries carrying `needs_replan`, their storyboard images, videos and voice-over are removed from "Could not be brought in" centrally by `write_migration_report`, rather than relying on each skip path to remember. Archive import, regardless of schema version, merges artifacts that import activation could not register and placeholders added during repair into the report (`extend_migration_report`). When the chain fails midway, the adjustments made are written into a report with `complete: false`, which is merged into the next report on retry; incomplete reports are not shown to users. When the chain fails only after committing the current version (an error after the last step committed, or failure of the final report write), the retry does not enter the chain again: the runner sees the project is already at the current version with the report still incomplete, and rewrites it as a complete report.
- When there is a trade-off, the copy that gets replaced is kept with `backups.set_aside_as_kept_copy` as a kept copy (`<name>.kept.v<N>-<ts>`), not cleaned up by `cleanup_stale_backups`, with its path written into the adjustment entry's `backup`; files that are merely rewritten get a versioned backup as usual.
- A generation gap is not the same as "cannot be projected": a gap only blocks generation, the expected basis is constructed as usual from existing input values, and missing items are recorded in the basis's `absent` (`lib/artifacts/input_gap.py`); when there is no gap the basis does not write this key, so the digests of registered entries with complete inputs are unchanged. Projects with schema < 18 are planned under the rule "any gap means it cannot be projected", so activation and provenance backfill in steps before v17→v18 are unaffected.
- Targets whose basis genuinely cannot be computed are not registered and read as missing; this does not mean "does not exist", nor "whole project fails". Of these, only unreadable files (blocked by the planner's `artifact_unreadable`) go into the report; the rest do not. Archive import asks for confirmation only when the report is non-empty; a healthy project exported by current code and re-imported shows no confirmation and leaves no report.
- When the planning rules are relaxed and artifacts previously skipped can now be registered, plan once before and once after the change, and backfill only entries that "had no target before, have one after, and are not in the manifest", leaving all registered entries untouched (precedent: gap backfill in v17→v18, `lib/project/project_migrations/input_gap_backfill.py`). Archive imports with an envelope backfill, by the same set difference, artifacts that have no claim in the envelope.
- Migration does not advance the project's last-activity time: `metadata.updated_at` of `project.json` and scripts keeps its original value, and newly written scripts do not use the migration run time as `updated_at`; do not call `lib.project.project_activity.record_project_activity`, nor go through the business write exits that call it (drafts, the formal script plan write transaction, edit timeline storage, project memory).
