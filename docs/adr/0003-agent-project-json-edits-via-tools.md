# Agent edits to project JSON data are routed through in-process MCP tools; bare Write/Edit/Bash are always denied

Before this decision the agent could directly modify `scripts/*.json` and `project.json` with bare `Write`/`Edit` (even Bash `echo>`/`sed`/`python -c`), passing only through a PreToolUse **JSON syntax** hook — structural errors (`duration_seconds` out of range, missing `image_prompt`, `ReferenceVideoUnit` shots↔duration inconsistency) still landed on disk, bypassing the unified entry point `_write_script_unlocked` (ADR-0002). This bypass made the "single guard point" a fiction. We decided to route all agent writes to project JSON data through a set of in-process MCP tools, and **forbid** raw byte writes to these two kinds of file outside the tools, so that ADR-0002's structural validation really has only one enforcement point.

Toolset (all in-process MCP `arcreel`, running in the server process, not inside the agent sandbox):

- `get_episode_script` + `patch_episode_script` — first read the body and the canonical JSON `sha256-v1` revision, then submit `{script, base_revision, operations[]}`. operations is an ordered discriminated union of `update` / `insert` / `remove` / `split`, located by `segment_id` / `scene_id` / `unit_id` / `shot_id`, common across content/generation modes. Within the project lock the service re-checks the revision, applies the whole batch in order to an in-memory candidate, then pre-checks structure, project references, the applicable Artifact Manifest basis and SpeechComposition all together; any failure returns a stable `code`, `operation_index`, unit/field location and `next_action`, and the whole batch writes nothing.
- `insert` / `split` complete the structural projection within the same batch transaction in `patch_episode_script`. **IDs are stable and not renumbered**; insert/split issue new IDs by mode, taking the number after the largest sequence number used in this episode, never reusing (`docs/adr/0090`): narration/drama segments/scenes use `E{episode}S{seq}`, reference units use `E{episode}U{seq}`; existing data also has `_{sub-seq}` suffixes left by splits. The first part of a split keeps the original id and its `generated_assets` / `end_frame_image`; the other new identities have their assets cleared.
- `patch_project` — add + modify for `project.json` (by table+name), **replacing** `add_assets.py` (that script is deleted, and the `analyze-assets` subagent calls this tool instead, incidentally eliminating its fragile single-line CLI-JSON invocation).
- `generate_episode_script` — whole-episode generation, changed to **write to disk via `_write_script_unlocked`** (replacing `ScriptGenerator`'s former bare `json.dump`).

Enforcement (two layers):

- **Bash subprocesses** (Linux/macOS, kernel level): `sandbox.filesystem.denyWrite` covers the `scripts/` directory and `project.json`. [Claude Code sandbox's OS-level enforcement](https://code.claude.com/docs/en/sandboxing#os-level-enforcement) explicitly states the constraints are enforced at OS level by Seatbelt / bwrap and **apply to all subprocesses in the sandbox (including Bash and its children)** — blocking the `echo>`/`sed`/`python -c` bypass. `denyWrite` was chosen over "pushing Edit-deny rules down": the former is a documented write-deny field, using the same `filesystem` passthrough as the existing `denyRead`, and doesn't depend on the not-explicitly-guaranteed behaviour of the SDK deriving Edit allow/deny rules into the Bash FS profile.
- **Built-in Write/Edit** (all platforms): built-in file tools don't go through the sandbox (they go through the permission system), and the `_check_write_access` hook rejects `scripts/*.json` + `project.json`. Same source as the denyWrite above (the same two kinds of path), forming two layers.
- All script writes funnel into `_write_script_unlocked`. Batch manual edits add a `ScriptBatchEditor` deep module outside it: within the same project/script critical section it does OCC and candidate pre-checking, and commits the script, the project episode index and the applicable episode-script Manifest entry as a compensatable commit; if a later step fails, the script/project are restored verbatim before the lock is released, and the Manifest hook restores the old entry itself. The underlying write entry point still keeps ADR-0002's "no worse" compatibility policy, while batch commands require this candidate to pass full structural and reference pre-checks; the only compatibility exception is legacy speech blockers not changed by this batch, which don't block unrelated edits.

## Consequences

- In-process MCP tools run in the server process and are **not inside the agent sandbox**, so the FS write-deny profile doesn't constrain them and the tools write to disk as usual; after deleting `add_assets.py`, there is **no longer any legitimate Bash write to `scripts/*.json`/`project.json`** inside the sandbox (`split_episode` writes `source/`, compose writes video output, neither touches them), so the kernel-level write-deny causes no collateral damage.
- **No-sandbox fallback** (Windows, or Linux bwrap detection failure): the kernel-level block is unavailable, so it falls back to the `_check_write_access` deny (Write/Edit, effective on all platforms) + the existing `_WINDOWS_BASH_PREFIX_WHITELIST` (only allowing `python .claude/skills/`, ffmpeg, ffprobe; arbitrary `echo>`/`sed`/`python -c` were never on the allowlist). Re-checked: after deleting `add_assets.py`, none of the `python .claude/skills/` scripts allowed by the allowlist write `scripts/*.json`/`project.json` (split writes `source/`, compose writes video output, peek is read-only), so the no-sandbox fallback needs no extra special defence.
- **Verification of denyWrite taking effect at kernel level**: `denyWrite` uses the same `filesystem` passthrough as `denyRead` (the latter is already used in production to protect `.env` etc., so the mechanism is trustworthy). Its kernel-level write rejection for Bash subprocesses is same-field behaviour promised by the SDK documentation; the configuration compilation and predicate behaviour of the two-layer rejection are covered by unit tests in `server/agent_runtime/agent_access_policy.py`; actual kernel-level write rejection relies on the SDK's promise and no live smoke test has been done — when verifying in a sandbox-enabled environment, the expectation is that `echo > scripts/x.json` inside the Bash tool is rejected by the kernel while MCP tool disk writes work normally.
- **Editing doesn't delete existing media or rewrite `generated_assets`**. After changing a prompt, old media is replaced by explicit regeneration; a structural remove only removes the script reference, and existing files in the project are kept. The same-id anchor of a split carries over the old assets; newly derived ids have their assets cleared. Manifest currency is derived at read time by basis comparison, and stale status is not written into the script.
- **Structured basis only registers formal direct inputs**: for narration / drama (including the reference_video route), when a canonical script_plan exists, that script_plan is used to construct the episode-script basis; without a script_plan nothing is registered. ad currently has no canonical script_plan, and the editing service does not manufacture a basis from the modified script itself, avoiding output self-reference.
- Tool **return text** is agent-facing (exempt from i18n); tool **display names** are user-facing and must be registered in `ARCREEL_MCP_TOOL_IDS` with trilingual `tool_name_<id>` (zh/en/vi) added.
- Same source as ADR-0002: this ADR fulfils its promise of "routing the agent's bare write surface". The reference_video structural tools act on the top-level `video_units`; a unit's `duration_seconds` is an independent arrangement field, not summed from member shots. Structural validation / the editing core / metadata recomputation share the `script_editor.resolve_items` discrimination.

## Boundary of the "no worse" semantics (post-#604 root-cause iteration)

PR #608 landed this ADR's tool routing on top of ADR-0002's "no worse", but several rounds of code review repeatedly found the same class of problem: `「不更坏」从一个具体策略悄悄泛化成了「宽容氛围」` ("no worse" quietly generalised from a specific policy into a "culture of leniency"); helpers outside the write-to-disk choke point, read paths, cross-episode sync and the agent allowlist all reused the attitude of "degrade when you meet dirty data", which stacked up into silent-noop / silent-overwrite gaps. This root-cause iteration draws the boundary firmly:

- **"No worse" exists at only two choke points**: `_guard_no_worse` in the script write-to-disk `_write_script_unlocked` (for script structure, based on `_select_model` + Pydantic ValidationError); and the error-set diff inside `_mutate` of `upsert_assets` (for project.json, based on the difference of the errors sets from `DataValidator.validate_project_payload`). All helpers / callers outside these two **are not allowed** to carry their own local policy for "what to do with dirty data".
- **Outside the choke points, always fail loud**: `resolve_items` raises `ScriptEditError` when the storyboard array key exists but is not a list (already the case); `batch_update_scene_assets` fails loud with `KeyError` when an id doesn't match (this PR); in `_write_script_unlocked` metadata recomputation, `duration_seconds=None` is treated as missing rather than crashing; `get_storyboard_items` goes through `resolve_items` so the exception types for dirty data are aligned (no longer `list(None)` raising a generic TypeError).
- **Degradation is the caller's explicit decision**: `versions.py::_sync_storyboard_metadata` is tightened from `except Exception` to `except ScriptEditError` + a warning including the episode name + continue (degrading cross-episode sync for dirty scripts, with an observable signal); unexpected exceptions are allowed to bubble up to a router 5xx. The read path `_resolve_items_or_warn` warns on dirty data (already the case), and returns `[]` without a warning on a missing key (an empty draft is a valid initial state). **Zero-signal success is forbidden** — every degradation path must have a warning.
- **The agent allowlist's silent drop becomes explicit feedback**: `upsert_assets` returns a diagnostic dict (added / merged / dropped_fields / dropped_legacy), from which the `patch_project` tool constructs text telling the agent "the following fields are outside the agent-editable scope (reference_image / sheet_field) and were ignored" and "the following historical fields are deprecated (type / importance)", so the LLM stops retrying fields that would be dropped the same way; the `analyze-assets` subagent prompt is changed to strictly skip existing ones (filtered before calling patch_project), eliminating the self-contradictory wording of "don't overwrite" vs "may revise".
- **Edit routing prioritises data shape**: editing tools, via forensic resolution (`lib/script/script_skeleton.resolve_script_kind`), route by the presence of the top-level keys `video_units` / `segments` / `scenes` / `shots` + `content_mode` as an aid, not by the project's declared generation route. Rationale: the question editing faces is "what does this script look like now"; if existing scripts whose skeleton doesn't match the project route were routed by route, the whole episode would be unreachable by all MCP editing tools, and the agent seeing "id not found" would have no clue to locate the problem. The generation side is the opposite, dispatching by project route, and the agent's generation enqueue tools and data validation additionally reject mismatched scripts via a route gate (see `docs/adr/0045`, `docs/adr/0055`) — mismatched episodes are therefore readable, editable and archivable/exportable (Jianying (CapCut) draft export takes clips per the canonical skeleton of the script's content_mode, so mismatched episodes get no completed clips), they just can't be generated from via the agent.
- **Tool responsibility boundaries**: `patch_episode_script`'s `_set_nested` **allows writing** when the leaf (last segment) doesn't exist (the agent should be able to fill in optional fields the LLM omitted, such as `video_prompt.note`, rather than being forced to remove+insert and regenerate the whole episode), while a missing parent node (intermediate path segment) still fails loud (blocking typos); `split` leaves the `generated_assets` of `parts[0]` (the anchor) untouched, aligned with `insert`'s anchor asset retention semantics, so misusing split as insert no longer loses generated assets.

Cross-cutting principle: **when retrofitting fail-loud, first enumerate the two-dimensional matrix** (read/write × key missing/key dirty × validate/no-validate) and decide cell by cell; do not push the "no worse" policy of "introduce no new errors at the structural validation layer" down into helpers that have no before/after concept (metadata recomputation, key lookup, exception handling) — degrading on dirty data in those scenarios is the caller's explicit responsibility, not the helper's default behaviour.
