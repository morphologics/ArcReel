# ComfyUI endpoint: one workflow as the second `kind` of custom invocation endpoint

A user's self-hosted native ComfyUI (local machine, intranet or their own cloud host) needs to be connected to ArcReel as a provider channel for image and video generation. It fits neither of the two existing integration forms: built-in providers' model lists are static dictionaries shipped with each release and cannot hold workflows imported at runtime; the genre boundary of declarative endpoints is "JSON in/out + submit/poll", whereas a ComfyUI request body is an entire node graph, assets are uploaded via multipart, and outputs are binary files, which is exactly the construct for which `docs/adr/0067` explicitly declined to extend the format.

We decided that **one ComfyUI workflow together with its node bindings is one custom invocation endpoint (ComfyUI endpoint, `kind: comfyui`), one ComfyUI server is one ordinary custom provider (`discovery_format: comfyui`), and the provider's model rows attach ComfyUI endpoints**. The workflow is embedded verbatim in API format in the endpoint definition; the definition uses the slot `docs/adr/0067` reserved for `kind`, is stored whole in `custom_endpoint.definition`, and the mirror columns are derived from the definition as before; endpoint CRUD, import/export, refuse-delete-when-referenced, the endpoint test framework and the market payload are all reused. At runtime the code forks on `kind`: `comfyui` produces image / video backends implemented in Python and does not go through the declarative runtime. The media type is decided by the endpoint definition; one ComfyUI provider can attach both image and video endpoints at the same time.

**Explicitly rejected**: (1) **Adding a built-in provider**: workflows are imported by users at runtime, which a built-in model list cannot hold. (2) **Extending the declarative format** to express node graphs, multipart and binary outputs: this would break through 0067's genre boundary, and even if expressed it would have no generality. (3) **Creating a separate family of entities** (a workflow table + workflow model rows): this would duplicate the CRUD, import/export, refuse-delete and market payload that endpoints already have, and the `kind` slot was reserved precisely for a second implementation form. (4) **One workflow = one model row**: model rows do not hold the definition itself, so they cannot be imported/exported or go into the market, and would lose the ability to "attach one workflow to multiple machines".

## The credential header template lives in the endpoint definition; no column is added to the provider row

ComfyUI itself has zero authentication, and the reverse-proxy authentication users add varies (header or query). The credential header template goes in the `auth` section of the endpoint definition, with the same schema as declarative endpoints; `{{api_key}}` may appear only in this section, and when `api_key` is empty the whole section is not rendered. No column is added to the provider row for this, and the single-field credential model of `docs/adr/0008` is kept intact. There are two known costs: authentication varies by deployment, so attaching the same workflow to two machines with different authentication requires copying the definition; and the provider-level connectivity check cannot access the endpoint-level credential template, so, like the openai protocol probe, it can only hit `/system_stats` bare with `api_key` as a Bearer token (no credential if `api_key` is empty); on deployments that use custom headers for reverse-proxy authentication the probe may report unreachable, in which case the test connection is authoritative. Both are accepted as edge cases.

## First two-way binding between endpoint and provider protocol

Previously, any custom invocation endpoint could be attached to any custom provider. ComfyUI endpoints cannot: the server validates both directions, so an endpoint with `kind: comfyui` can only be attached to a provider with `discovery_format: comfyui`, that protocol's provider model rows can only attach ComfyUI endpoints, and the selectors filter by protocol. The constraint applies only to the comfyui protocol; free attachment for other protocols is unchanged. The reason is that the ComfyUI endpoint runtime (`/upload/image`, `/prompt`, `/history`, `/view`) is meaningful only for a ComfyUI server, and declarative endpoints are equally meaningless for a ComfyUI server; a wrong attachment would only blow up at generation time.

## No provider bill; reference cost reuses the unit-price field; execution time is only recorded

ComfyUI runs on the user's own GPU, so there is no provider bill. We do not invent GPU pricing: the reference cost reuses the model row's existing unit-price field and existing formulas (video by clip length, images per image), with an empty unit price meaning 0; execution time is recorded as usual for reference in enterprise cost-allocation scenarios, but does not enter pricing. The accounting layer is unchanged.

## Cancellation and timeout stop the remote job, done inside the backend without extending the protocol

When ArcReel abandons a generation (user cancellation or polling timeout, the same for generation tasks and test connections), it notifies ComfyUI on a best-effort basis to cancel that job, freeing the GPU; this is the only cancellation in the whole repository that notifies the provider. After a commercial API job is abandoned we simply stop polling; the provider side keeps running and billing, so notifying is pointless, whereas on the ComfyUI side not stopping it would needlessly occupy the user's GPU. The implementation does not extend the invocation channel protocol: stopping the remote job happens inside the ComfyUI backend's own generation flow, and after local abandonment the existing failure path proceeds as before; a failure to stop the remote job is only logged, and the local state machine (`docs/adr/0006`) is unaffected. The cost is that users with slow GPUs may lose an almost-finished result at the timeout limit, mitigated by a configurable polling timeout.

## Consequences

- The endpoint definition schema splits into two by `kind`, with different structures: declarative definitions have request templates and a `capabilities` section, ComfyUI definitions have `workflow` and `bindings` sections (see `docs/adr/0082`). The shared validator dispatches on `kind`.
- `discovery_format` gains `comfyui`: the connectivity check hits `/system_stats` and returns `comfyui_version`, and model discovery returns a structured "not applicable" rather than an empty list; the default concurrency for this protocol's providers is 1.
- The assumption that "custom invocation endpoints are always video" is retired; the media type is always read from the endpoint definition.
- Endpoint testing for ComfyUI endpoints offers only preview request and test connection; response validation is not provided, since output extraction is fixed code with no user-configurable extraction path to validate.
- The first phase polls only `/history` and does not connect WebSocket; it does not show the queue position on the ComfyUI side and does not report fake progress.
- ComfyUI endpoint definitions are naturally market entry payloads, and the market entry type is unchanged; whether the market's first phase shows and installs ComfyUI endpoints is outside the scope of this ADR. Hosted ComfyUI cloud services (Comfy Cloud, RunningHub and the like) are also out of scope; they use declarative endpoints.
