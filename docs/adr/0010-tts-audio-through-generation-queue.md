> For the scope of TTS and its generation cardinality see `docs/adr/0089`: it is only generated in projects whose narration delivery method is TTS, one clip per unit containing voice-over, generated during the editing stage; this ADR's decision that audio goes through the generation queue and the backend stays synchronous remains in effect.

# TTS (audio media type) goes through GenerationQueue/Worker, like image/video; the backend is still synchronous, unlike inline text

ArcReel's media generation fans out along the `media_type` axis: image/video go through **GenerationQueue + GenerationWorker** (slots per provider×media_type, with progress/cancel/resume/orphan handling), while text is a **synchronous inline call** (`TextGenerator` = TextBackend + UsageTracker, not enqueued; the worker only does `for media_type in ("image","video")` and creates no task). When integrating narration voice-over (TTS), the first fork was: does audio go with text (synchronous inline) or with image/video (queue)?

Initially the leaning was synchronous inline, on the grounds of "same as text calls, no concurrency control", because the TTS backend call itself **is a synchronous one-shot POST** (modelled on `text_backends`, no submit-poll, returns in seconds), which looks closer to text. But it was then confirmed that **batch generation is a hard requirement on both the web and agent sides**, and the key fact is: **the generation cardinality of narration audio (one clip per segment, N clips per episode, batchable, regenerable) matches image/video, not text's "once per episode"**. Under synchronous inline, batching could only be orchestrated serially by the frontend, with progress tied to a browser tab, no task panel, and no cancel/resume/cross-device — disjointed from the image/video batch experience; whereas the queue was built precisely for "long batch tasks + progress + cancel + resume", and images/videos already use it.

We decided **audio goes through GenerationQueue/Worker, consistent with image/video**: a single clip = one enqueued item, a batch = N enqueued items, reusing the existing `/api/v1/tasks` task panel. At the same time we keep one **deliberate asymmetry** — audio's **backend is still a synchronous one-shot** (modelled on `text_backends`, not video's submit→poll→resume); after the worker claims, it calls the synchronous backend directly and marks the terminal state as soon as it returns in seconds. In other words: **"whether to enqueue" is decided by generation cardinality (whether it is batched per segment), not by whether the backend is asynchronous** — this is a point that will confuse future readers ("the audio backend is synchronous like text, so why is audio enqueued and text not?"), hence this ADR.

## Considered Options

- **Synchronous inline (like text) + serial batching in the frontend** — least code, worker untouched. Rejected: batch progress tied to the browser tab, no task panel, no cancel/resume/cross-device, disjointed from image/video; and audio's generation cardinality resembles image/video, not text, so the analogy doesn't hold.
- **Go through the queue (like image/video)** — adopted.

## Consequences

- **The worker gains a third lane**: `ProviderPool` adds `audio_max` / `has_audio_room`, the claim loop `for media_type in ("image","video")` is extended to include `"audio"`, and lane-related points such as `_resolve_dispatch_provider` / `_any_pool_has_room` / `_pool_full_providers` / `_load_pools_from_db` / `_build_default_pools` are touched (mechanical changes). TTS is cheap and fast, `AUDIO_MAX_WORKERS` is loose by default, and the lane should not become a bottleneck.
- **The agent tool is `generate_narration_audio(segment_ids?)`** (registered name; implemented as enqueueing, see `server/media_tools/narration_audio.py`, modelled on the storyboard enqueue tool), with queued rather than synchronous-wait semantics; omitted = all missing segments, a list = a specified batch range, a single segment is a one-element list (the schema only accepts an array; a bare string is rejected by parameter validation).
- **Web enqueues + reuses the existing task panel**: both single and batch enqueue; the frontend polls `/api/v1/tasks` for progress and reuses the existing cancel/resume UI.
- **The audio backend stays synchronous, with no resume/`provider_job_id`**: worker claims → calls the synchronous backend (returns in seconds) → marks terminal state. `docs/adr/0007`'s orphan handling degenerates for audio to "mark failed, don't resume", because it is synchronous and regeneration is cheap, so video's submit-poll-resume machinery isn't needed.
- **"Synchronous" is a choice for "short segments + synchronous API"; async is a reserved extension point**: v1 chose synchronous because (a) the chosen providers' TTS APIs return bytes synchronously anyway (DashScope Qwen-TTS sync HTTP, OpenAI-compatible `/v1/audio/speech` returns immediately), and (b) per-segment narration is short (`duration_seconds ≤ 60`, bounded text) and completes in seconds. **But long-text TTS interfaces in the industry are asynchronous** (MiniMax T2A async, Doubao async long text ≤100k characters, Google long-audio LRO, Azure batch). If in the future a provider offering only an async API is integrated, or it changes to "synthesise the whole episode's long text in one go", a video-style submit-poll lifecycle will be needed — so the `AudioBackend` Protocol is designed to **reserve** the async possibility (allowing per-backend shapes as text/video do), but v1 only builds synchronous.
- **Task needs no migration**: `task.task_type` / `media_type` are free String columns, and audio rows go straight into the database.
- **Versioning unchanged**: audio, like image/video, lands versions through VersionManager (see the `GLOSSARY.md` entries "旁白配音" (narration voice-over) and "媒体类型（media_type / call_type）" (media type)).
- **The asymmetry with text is a contract**: text is generated once per episode, synchronous inline, not enqueued; audio is N clips per episode, enqueued. Any later PR that wants to switch audio back to synchronous inline (or make text enqueued) must first deprecate this ADR and explain the change in generation cardinality.
