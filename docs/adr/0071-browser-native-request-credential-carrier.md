# Credential carriers for browser-native requests: SSE uses fetch with headers, media is anonymously readable, export uses a download token

Browser-native requests can't carry an `Authorization` header, and ArcReel used to give a different answer for each of three scenarios: SSE appended the long-lived session JWT as `?token=`, project export used a short-lived download token, and static media had no authentication. The strength and exposure of the three were inverted: SSE carried a full-privilege long-lived credential, yet it ended up in access logs via a query param. This decision handles the three separately by cause, rather than unifying them on one carrier.

**SSE is no longer treated as a browser-native request**. The event stream is consumed by the frontend with `fetch` carrying an `Authorization` header; the server attaches the three streaming endpoints back to the ordinary protected router, `get_current_user_flexible` and the `?token=` form are deleted together, and the authentication enforcement test asserts 401 for requests with `?token=`. `EventSource`'s native reconnect reuses the URL as-is, so any credential travelling in the URL must be re-minted before every reconnect, which amounts to bolting a ticket lifecycle onto an inherent defect of `EventSource`; switching to `fetch` removes the root of the defect, and the backend only shrinks. The cost is that the frontend takes charge of event parsing (`eventsource-parser`), `Last-Event-ID` resumption, and backoff reconnects, and the project event stream and the assistant stream are unified to rebuild automatically after a disconnect.

**Static media stays anonymously readable, as a deliberate decision**. ArcReel is a single-administrator self-hosted application, and its threat model does not include an attacker reading media without authorization; adding authentication to media would mean about fifty `<img>` / `<video>` src attributes all carrying credentials, the embedded agent and MCP clients would need an extra Bearer to fetch images, and copying links and opening in a new tab would break — all in exchange only for "can't see it if you can't guess the path". If sharing or external embedding is needed in future, share credentials should be explicitly issued, which is out of scope for this decision.

The scope of "static media" is precise; anonymously readable does not mean the project directory is anonymously readable. The public project file endpoint (`/files/{project}/{path}`) requires both directory and extension to be on allow-lists: directories are limited to those where the generation and upload flows write media, `storyboards/ end_frames/ videos/ reference_videos/ thumbnails/ characters/ scenes/ props/ products/ grids/ audio/` (including subdirectories), the snapshot buckets of each of these directories under `versions/`, and `style_reference.*` at the project root; extensions are limited to images (`.png .jpg .jpeg .webp`), video (`.mp4`), and audio (`.wav .mp3`); extensions are case-insensitive, while directory and file names are case-sensitive. The global asset endpoint (`/global-assets/{type}/{filename}`) is bound by the same extension allow-list. `project.json`, scripts, source files, drafts, subtitle and presentation JSON, `versions.json`, final cuts in `output/`, and non-media files within media directories are all out of scope and return 404 in the same form as a nonexistent file; they are read only via the protected API. Responses from both endpoints always carry `X-Content-Type-Options: nosniff`. The allow-lists are defined centrally in `server/routers/files.py`.

**Export download keeps the download token**, which is now the only credential form of self-authenticating endpoints. The "unify the three" left for separate discussion at the end of ADR `docs/adr/0059` is closed here.

## Explicitly not adopted

- **Cookie authentication**. It would let `<img>`, native downloads, and SSE carry credentials for free in one go, but its value holds only when media requires login or credentials must be moved entirely out of URLs; since media stays anonymous and SSE can switch to `fetch`, what's left are only the costs: reworking the login/logout flow, a CSRF surface, defining `AUTH_ENABLED=false` behavior, and re-reviewing the threat model.
- **Short-lived purpose-bound tickets (`purpose=stream`)**. Reusing the download token's minting pattern would be a small change, but the ticket would still be in the URL, and `EventSource` would have to exchange a ticket before every reconnect, introducing a runtime ticket lifecycle just to get around `EventSource` not carrying headers.
- **Deploying the frontend separately**. The `CORS_ORIGINS` allow-list serves only non-browser cross-origin API calls (which use Bearer), and browser access requires being same-origin with the backend; this is one of the premises for not needing the cookie approach, and also a constraint of this decision.

## Consequences

- In the glossary, "browser-native request" is left with only two kinds, `<img>` / `<video>` src and native download navigation, and "self-authenticating endpoint" is left with only the export download endpoint.
- The entry on SSE query param leakage in `docs/security/threat-model.md` is updated together with the implementation; cookies and refresh tokens remain changes that "need re-review".
- The frontend no longer has `EventSource` and `fakeEventSource` test doubles; the streaming client's test double becomes a controllable `fetch` response stream.
