# Authentication requirements are declared at a single point, where routers are registered

Whether an endpoint requires login has a single source of truth: the router registration block in `server/app.py`. Routers requiring authentication are attached with `dependencies=[Depends(get_current_user)]` at `include_router`, and public endpoints and self-authenticating endpoints are not. `CurrentUser` appearing in an endpoint signature only means the handler wants to read the user object, not that the endpoint requires authentication — only handlers that actually use `user` declare it. Previously authentication relied on each endpoint declaring `_user: CurrentUser` in its own signature; the whole group of provider configuration and credential routes was missing the declaration without anyone noticing, so credentials could be read and written without logging in, and the generation backend could be hijacked via a custom Base URL.

The exempted surface is divided by router object rather than by endpoint: a route module can define a second router object to carry endpoints without the dependency (`public_router` carries the anonymously reachable login entry and static media, `self_auth_router` carries self-authenticating endpoints), and files are still organized by domain. The registration block is therefore both where authentication requirements are declared and the list of the public surface; reading one screen answers "which URLs don't require login".

This form is idiomatic FastAPI, and forgetting to attach the dependency would still leave a whole router exposed — i.e. fail-open. The guarantee is provided by `tests/integration/server/test_auth_enforcement.py`: it enumerates all API operations from `app.openapi()`, sends an unauthenticated request to each one outside the exemption list and asserts 401; new routers are included automatically, and a missing attachment is exposed in CI rather than becoming a vulnerability after release. Endpoints on the exemption list skip that sweep, so each one has a separate positive assertion proving it isn't undefended: public endpoints assert anonymous reachability, and self-authenticating endpoints assert that anonymous requests are still rejected.

Since authentication no longer travels with the endpoint signature, route tests that assemble their own `FastAPI()` must replicate the registration attachment, otherwise they test an unauthenticated app: protected routers attach `tests/auth_deps.AUTH_DEPENDENCIES`, and cases that need to pass call `override_auth` from the same module. Most such tests bypass authentication with `dependency_overrides`, so missing a layer won't fail; only cases that specifically assert 401 will expose it; `test_auth_enforcement.py` only covers the production app, so this path has no backstop.

## Explicitly not adopted

- **App-level global dependency + endpoint exemption table**. Fail-closed at runtime, so a missing attachment is still safe, but FastAPI provides no exemption mechanism; implementing it would require walking the lazy wrapper objects left by `include_router` — tying authentication correctness to the framework's private representation, where a framework upgrade could scramble the exemption decisions. When the same walk appears only in tests, the worst outcome is a CI failure rather than abnormal production behavior. This approach would also need a special case for the SPA fallback the framework mounts itself, and by bypassing FastAPI's dependency cache it would decode the JWT one extra time for every protected request.
- **Endpoint-side decorators marking the public surface**. Exemptions would be scattered across business route files, auditing "the whole public surface" would require a repo-wide search, and changes adding exemptions would be inconspicuous, mixed into feature diffs.
- **Merging public and self-authenticating into one concept**. Both are written the same way at registration (neither attaches the dependency), but self-authenticating endpoints do stop anonymous requests while public endpoints don't; a merged name would make the former misread as open.
- **Unifying the authentication mechanism of the three kinds of direct browser requests**. SSE, export downloads, and static media have the same cause but different answers; the direction of convergence is a separate discussion and is not merged with this registration-form adjustment.
