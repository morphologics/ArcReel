# Typed provenance for legacy media version records is backfilled by the migration as a projection of the project state at that moment, and is thereafter treated the same as records frozen at generation time

> The part of this ADR stating "scripts without a formal script_plan are registered with a no-plan basis, and after re-running planning the script is judged stale because its basis changed" has been superseded by `docs/adr/0080`: the script basis does not take the script plan as input, and scripts are registered with the same kind of basis whether or not there is a plan; the provenance projection for legacy media version records remains in effect.
>
> The part of this ADR stating "projection failures (missing storyboard image, entry not eligible for speech synthesis, duration that cannot be bucketed, etc.) go into the migration report, and the user decides from the report whether to regenerate" has been superseded by `docs/adr/0098`: these gaps no longer block projection, and the videos are backfilled as usual. The rule that legacy narration audio is not backfilled and goes into the migration report remains in effect.

The artifact manifest (`docs/adr/0062`) and the presentation read model only recognise the typed provenance on version records: script binding, episode number, requested duration, request digest and video description (`lib/artifacts/artifact_version_provenance.py`). These fields were introduced in 0.27; the generation task writes them into the version record at submission time and they never change afterwards. Video records generated earlier have only five fields, `version / file / prompt / created_at / duration_seconds`, so both manifest backfill and presentation reads fail to parse them. Backfill silently skipped "cannot parse" as "artifact does not exist", so after upgrading, users saw a video count of 0/N, production status reverting to preparation, and the preview reporting "selected video presentation unavailable". This violates ADR 0062's rule that "backfilled means current; users should not be misled into regenerating artifacts they have already paid for".

Decision: add a schema migration step (v12→v13, `lib/project/project_migrations/v12_to_v13_legacy_media_provenance.py`). For every video that a script entry still points to and whose selected version record has no typed provenance, **project all typed provenance fields from the project state at the moment of migration and write them back to the record** (`lib/project/legacy_media_provenance.py`), then re-project the whole manifest. The projection uses the same basis builder as the currency comparison (`project_video_basis_components` in `lib/artifacts/media_artifact_currency.py`), so the registered value and the expected value come from the same source, and these videos are therefore current as soon as they are backfilled. The frozen shape is "no reference audio, no voice speaker, no reference-image cap, a single duration bucket equal to the requested duration"; the provider audio-track switch is projected from the project's current setting. Every backfilled record gets `provenance_backfilled_at`; read paths do not distinguish it from records frozen at generation time, and it is only used during troubleshooting to tell "projected" from "frozen".

In the same step, **scripts without a formal script_plan are registered with a no-plan basis** (`structured-content/episode-script-without-plan`, containing only the episode number): such a script stays current until the user re-runs planning and produces a formal plan, at which point the script entries are judged stale because their basis changed and switch back to the normal route. Production status skips the plan gate and the plan-confirmation gate for such episodes and determines status directly from the script and downstream artifacts.

Narration audio is not backfilled: its basis includes the TTS settings at synthesis time (provider, model, voice, speaking rate; see ADR 0062), which legacy records do not have, so any projection would be fabrication. Such records go into the migration report and the artifact reports missing, consistent with the current behaviour.

## Explicitly rejected

- **Relax the planner and the presentation read model to accept legacy records without typed provenance and compare them against a degraded basis**: every consumer would need an extra branch, which is exactly the "legacy / unknown origin" third state that ADR 0062 rejected, and the read paths would carry that branch forever. Rewriting the data once keeps the read paths unchanged.
- **Do not add `provenance_backfilled_at`**: projected records would be formally indistinguishable from frozen ones, leaving no clue when later investigating "why was this judged current". The cost is one field.
- **Fail the whole project migration if projection is not possible**: one bad record would put the whole project into a blocked state. ADR 0062 already specifies that targets whose basis cannot be projected are not registered and report missing on read; that is kept here, but skipped items are counted in the migration report instead of being silent.
- **Treat the legacy record's `duration_seconds` as the sole source of the requested duration**: it may be a string, and it may not match the entry's current duration. The requested duration is the first positive integer in the order: entry duration → project default duration → record duration.

## Consequences

- The migration rewrites `versions/versions.json` irreversibly; before rewriting it is backed up as `versions.json.bak.v12-<ts>`, under the same cleanup rule as other migration backups.
- Backfill only covers videos that a script still points to at the moment of migration and whose current file matches the selected snapshot's content; projection failures (missing storyboard image, entry not eligible for speech synthesis, duration that cannot be bucketed, etc.) go into the migration report, and the user decides from the report whether to regenerate.
- The currency of no-plan scripts does not track project metadata changes: the user changing asset definitions will not make such a script stale. This is an intentional simplification; the cost is that scripts for such episodes "always match" until a plan appears.
- Scripts written before the plan gate are also registered with the no-plan basis when saved (the planner is the single entry point for both registration and comparison). In the normal flow the script is always generated after the plan, so this branch only appears for legacy data and for calls that save a script directly.
- This is the second time the migration chain activates the manifest: v12→v13 runs a complete read-only pre-check on all existing projects, and projects rejected by the pre-check enter the blocked state per ADR 0062 with the offending file named; projects whose manifest can already be read at runtime pass the pre-check, and the ones rejected are data that the runtime cannot read either.
