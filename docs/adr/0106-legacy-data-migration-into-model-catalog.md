# Migrating existing data into the model catalog: custom model prices are discarded, and only capability values differing from both the entry and the preset are kept

Existing custom models carry user-entered prices, selectable durations and maximum output tokens, and built-in models' metadata and prices are written in `registry.py`. When migrating into the model catalog, we do not aim to carry the old data over as-is: the old price structure cannot express the new price table's meters and selection dimensions, and old durations were mostly inferred automatically from names, so keeping them as-is would only permanently stamp outdated values onto entries. Migration keeps only what the user explicitly expressed and the new structure can carry accurately, and the price changes are explained in the release notes.

## Rules

- All custom model prices are discarded during migration, with no multiplier derived and no user entry created. Models that match an entry are billed at the entry price, with both the provider multiplier and the provider model multiplier set to 1; those that do not match are recorded as unpriced (see `docs/adr/0105`). Already frozen historical costs are not recomputed.
- During migration, existing custom models are mapped to entries in the factory snapshot per the rules of `docs/adr/0105`; the result is used only for the capability comparison in the next rule and is not stored. Stored invocation endpoints are kept and not re-inferred.
- Existing capability overrides are kept as-is after mapping by dimension, except those on ComfyUI endpoints (see `docs/adr/0082`). Existing selectable durations and maximum output tokens are converted into capability overrides only when they equal neither the corresponding entry's value nor the preset inferred from the name; the rest are discarded; the same applies to models that do not match an entry, and when there is no value to compare against they are converted into capability overrides. The default resolution is a user preference and is kept as-is.
- Provider models that do not match an entry can also have capability overrides set: the media type comes from the invocation endpoint, and dimensions not overridden show the runtime fallback result.
- The first version of the catalog data repository's data is generated by a one-time conversion of `registry.py`; known pricing defects and delisted models are fixed in this version as well, and from then on code no longer holds models and prices. After migration, officially listed provider models are enabled by default, and those previously hidden are disabled by default.
- When settings and projects reference models outside the built-in provider lists, models with a known rename are rewritten to their successor via the retired-model mapping; other references are kept as-is, fail to resolve at runtime with an error prompting the user to choose again, and do not silently fall back to another model.

## Considered Options

- **Derive the provider model multiplier from the user price and the official price**: would preserve relay services' price differences. But it can be derived only when currencies match, the official price has no tiers, and text input/output ratios are consistent; cases where it cannot be derived are mostly pricing the old structure could not express in the first place, so keeping them would not compute correctly either. Reference costs do not align with bills anyway, and after discarding, users can fill in the multiplier themselves.
- **Create user entries for models that do not match but had prices filled in**: preserves the prices users entered, but the model vendor is unknown, so the entry identity would have to be guessed, and it conflicts with `docs/adr/0105`'s rule of not creating entries for unmatched models.
- **Convert all selectable durations into capability overrides**: a one-time backfill migration wrote durations by name for almost all existing video models, so converting them all into overrides would leave every video model permanently carrying an override the user never set, and durations updated by official sync would no longer take effect.
- **Scan settings and projects and create user-added provider models for references outside the lists**: such references only come from deleted models or writes that bypassed the UI, so the gain from automatically creating models for them is small; silently falling back to another model would change the user's model and price without their knowledge.

## Consequences

- After upgrading, users who had filled in prices on custom models will see costs change to the entry price, or shown as unpriced; the release notes need to state this change and explain how to express relay services' price differences with multipliers.
