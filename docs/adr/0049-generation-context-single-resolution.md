# Provider resolution products for generation tasks are consolidated into GenerationContext: resolve once, take values by the actual backend identity

The configuration products a generation task needs at execution time — each media lane's ProviderModel, resolution (quality tier), and capability limits such as supported_durations — are derived from the same provider resolution, but the execution layer long lacked an interface to carry them: `get_media_generator` resolved internally and then returned only the MediaGenerator, discarding the products. Downstream consumers therefore each fetched them again: image/video tasks, after getting the generator, reopened a ConfigResolver session and resolved again (a configuration change between the two resolutions would "build the backend from A and look up the resolution from B"); video tasks, when the second resolution failed, silently dropped to a hard-coded provider/model tuple and kept running; reference video tasks dug into the private attribute `generator._video_backend`, manually split the `project["video_backend"]` string to rebuild the registry provider_id, and also had to defend against "the model found by caps differs from the backend's actual model" (when a custom provider's target model is disabled, `load_custom_backend` silently falls back, so looking up capabilities by the resolution intent mismatches). On the interface side, three boolean flags `require_image_backend` / `needs_i2i` / `needs_audio` enumerated "which lanes this task needs", and regardless of declaration the other lane was resolved too — a project with only an image provider configured, running an image task, would fail entirely because video resolution failed.

We decided to consolidate this into one deep module: `server/services/tasks/generation_context.py` exposes a single entry point `resolve_generation_context(project_name, payload, *, project, user_id, image=, video=, audio=)`, returning an immutable `GenerationContext`. ① **Resolve once**: resolution and backend construction for all declared lanes complete within a single ConfigResolver session, and the products (`generator` + each lane's result value object) are delivered in the return value; consumers no longer re-resolve. ② **Named lane declaration**: passing `ImageLaneRequest(capability=...)` / `VideoLaneRequest()` / `AudioLaneRequest()` declares the lane, so a task pays configuration requirements and construction cost only for the lanes it uses; accessing an undeclared lane via its property raises directly (fail-loud, not an Optional type). ③ **Take values by actual identity**: each lane has a fixed solving order — resolve the ProviderModel → construct the backend via `assemble_backend` (`docs/adr/0039`) → look up resolution and capabilities using **the canonical `provider_id` as the provider axis and the backend's actual `.model` as the model axis**. The lookup key is `(provider_model.provider_id, backend.model)` rather than `backend.name`: the provider does not drift in the construction seam, and for family-alias providers (such as families reusing the Ark backend, whose `backend.name` is always the family name `ark`) `backend.name` is the family name, not a registry key, so it can't serve as the provider axis; the model is the only real drift axis — when a custom provider's target model is disabled the loader silently falls back, hence the backend's actual `.model` is used. The path where resolution intent and the actually constructed object mismatch no longer exists structurally, and consumers need no further consistency defenses. A lane result exposes two sets of string fields, `provider_model` (canonical registry identity) and `backend_name` / `backend_model` (actual identity reported by the backend), and does not expose the backend instance. ④ **Error semantics**: a lane resolution or construction failure is re-raised as-is and the whole call fails, producing no partial result and no silent cross-provider fallback; only a capability lookup failure degrades to an empty value and passes (per `docs/adr/0002`). resolution keeps the semantics of None = don't pass the SDK parameter (`docs/adr/0019`), and the video lane additionally offers `resolution_or_fallback` for callers that need a non-empty value. ⑤ **The audio lane carries narration voice/speed**: the resolution logic stays in ConfigResolver and only delegates value retrieval within the same session, so voice tasks no longer open a second session for this. ⑥ `resolution_resolver.py` disappears as a public module: the DB-dependent precedence chain (project override > legacy > custom provider default) is absorbed as `ConfigResolver.resolve_resolution()`, and the pure-lookup `get_provider_fallback` moves into a module-level public function in `lib/config/resolver.py`.

**Explicitly not adopted**: ① **Deepening MediaGenerator itself to carry the resolution products** — MediaGenerator only cares about "how to generate"; mixing in "how the provider was chosen" makes a grab bag of two concerns; a thin outer value object composes the two instead. ② **Opening three injection Ports for ConfigResolver / ProjectManager / backend construction** — the first two are local-substitutable dependencies (tests use an in-memory DB and real instances with tmp_path, no mocks), and only backend construction is a real external seam, for which `assemble_backend` is already a ready-made adapter pair; opening a Port for a dependency with only one production implementation is a hypothetical single-adapter seam. ③ **Partial success** — returning an incomplete context when a declared lane fails to resolve would disguise a configuration error as a partially normal state. ④ **Atomic failure on capability lookup failure too** — capabilities are metadata of an already-chosen provider/model; their absence does not mean the model can't be called, and atomic failure would regress the "no worse" semantics of `docs/adr/0002`. ⑤ **Keeping the hard-coded provider/model fallback on resolution failure** — it existed only because "the second resolution might fail while the backend is already built"; with a single resolution the premise disappears, and keeping it would, when the user explicitly configured a provider, silently switch to an unrelated provider and run up billing and content.

## Consequences

- **Consumers get everything in one call**: the "build generator + re-resolve separately / dig into private attributes / manual split" in 5 sites within generation_tasks (storyboard/character/design/grid/video), reference_video_tasks, and resume_executor all disappear; reference_video's caps-consistency defense branch becomes dead code and is deleted.
- **Behavior changes**: image tasks no longer require video provider configuration (and vice versa); video resolution failure changes from "silently switch to a hard-coded model and run" to "task fails, with a traceable record"; the model metadata grid writes to disk now records the backend's actual `.model` (the provider axis still records the canonical `provider_id`), which may differ from the resolution intent's model when identity diverges (custom provider model fallback).
- **Boundaries unchanged**: resolution still happens only in the execution layer (`docs/adr/0001`); resolver precedence payload > project > global default is unchanged; `_backend_cache` is still a server execution-layer concern (`docs/adr/0039` "caching stays with the caller"), moves with this module, and keeps an invalidation entry point for the provider-configuration change route to call.
- **Test surface consolidated**: consumer tests now replace the single point `resolve_generation_context` and assemble fake contexts directly from frozen dataclasses; the module's own tests use a real test DB + tmp_path + fake backend and assert through the interface, not on private attributes. The previous pattern of assembling resolve/backend combination monkeypatches across many test files is abolished.
- **cost_estimation is not a consumer**: cost estimation only resolves and does not construct backends; it now calls `ConfigResolver.resolve_image_backend / resolve_video_backend` directly, removing its copy that manually re-enacted precedence, and keeps the display semantics of degrading to unknown on resolution failure.
- **Terminology recorded**: the semantics of `GenerationContext` and the image / video / audio lane result types are carried by the module and class docstrings of `server/services/tasks/generation_context.py` (the glossary records only product concepts, not internal types).
- The empty-value pass-through for the fallback resolution and duration dimension of the video lane is superseded by `docs/adr/0086`.
