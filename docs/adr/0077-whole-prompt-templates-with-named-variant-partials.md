# One whole template per generation step; axis differences resolved with named variant partials; templates shipped built into the core library

Across the repository, roughly 60 prompt definition points are scattered over seven kinds of carrier (Python constants, large f-string templates, line-by-line concatenation, dict registries, Markdown files, project file fields, and system prompts assembled at runtime). The same project style field is injected with four different phrasings on four paths, and the negative prompt has its own wording on each of five paths. Creators cannot see the complete prompt a step actually sends, and a maintainer changing one sentence has to first find which constant it lives in and then confirm how many copies exist.

Decision: **one generation step corresponds to exactly one template file, whose body is the complete prompt for that call, leaving only data slots**; shared wording is extracted into template partials; **wording differences along an axis (source file type, asset type, ad duration tier, single-line differences by creation type) are resolved with named variants of partials, and templates do not compare axis values**; conditionals are only allowed as truthiness checks on slots, used for optional data blocks (episode-end hook, target duration, additional instructions, next-episode outline); **the built-in template directory lives inside the core library package and ships with it, not in the agent runtime profile**; **the template module takes the template directory as a constructor dependency** and does not locate the directory itself.

Three reasons drive every item above:

- **Simplify the existing mechanism.** With one file per step, "what does this step send" has a single answer; copy relationships between wordings become reference relationships between partials, and changing one wording means changing one file.
- **Turn black-box prompts into something users can see.** The system settings page lists all built-in templates by template category, and opening one shows its source. The less template syntax in the body, the more readable that page is; if axis differences were written as conditional branches, the settings page would either have to execute the template or make the reader run the branches in their head, **whereas when they live in files, the settings page can enumerate the wording for each axis value without executing the template**.
- **Pave the way for later user modification and sharing.** Users will not change ArcReel code; what they will change in future are the prose files of templates and partials. Changing the wording for one axis value means changing one prose file; the change surface is isolated per file and does not affect other axis values; adding a new source file type or asset type means adding files, not editing templates.

**Templates are shipped built into the core library package** because they are part of the code, not the agent's visible instructions: Docker images and read-only installs need no extra copy step or environment variable, and templates are not materialised into the project directory. Markdown inside the agent runtime profile (CLAUDE.md, skills, subagents, references) is loaded verbatim by the SDK without rendering and is not covered by this mechanism; disguising it as rendered templates would only mix two sets of semantics in one directory. **The template directory is injected as a module dependency**, so tests can point the module at a fixture directory to assert error behaviour, or at the built-in directory to assert completeness, while the production instance points at the one shipped with the package.

## Four boundaries

The following four boundaries are preconditions for this decision to hold. The parts that can be checked automatically are guarded by tests; the first one can only rely on the ADR and code review.

- **Slots used in truthiness conditions must not be derived from axis value comparisons.** A slot's truth value may only come from whether project data exists. Code must not compute boolean slots by comparing axis values such as `source_kind` / `content_mode` / `asset_type` / `generation_mode` (the existing builder's `is_screenplay` is a counter-example, and so is `inject_style`). Otherwise the axis difference has merely moved from template syntax into slot names, and the settings page loses enumerability again. **A directory scan cannot detect this; it is a code review item.**
- **Variant partials carry wording differences; code carries value differences.** `aspect_ratio_label` (9:16 → portrait composition / 16:9 → landscape composition / others phrased from the ratio) is a short label computed from a value, not an axis; it is produced by code as a slot value and does not get a variant family. The test is: does changing this branch change a value rule or wording? Wording goes into partials, value rules stay in code.
- **Slot values are projections with all keys present.** Nested slots (`project_overview.synopsis`, `episode_outline.hook`) have their shape completed by the slot value producer, with missing values passed as null; templates do not write `.get()`. Under StrictUndefined a missing key fails loud, which is exactly what we want: a wording change must not silently drop project data.
- **Partial names must be literals, and loops only appear in list partials.** A partial name is a path relative to `partials/`; the engine performs no implicit lookup, and templates must not concatenate partial names, since dynamic name building defeats static scanning at load time and leaves only a render-time fallback. Loops are used only to expand list slots item by item (candidate names, outline nodes, asset appearances), and are written only in list partials, never in the body.

Completeness of variant families is validated at load time: based on the frontmatter `applies_to`, each family is checked for a file for every axis value, and a missing file fails loud; **when an axis value deliberately has nothing to say, an empty file is provided**, rather than relying on "missing file renders as empty", which would express "intentionally empty" and "forgot to write it" as the same thing.

## Explicitly rejected

- **Expressing axis differences with conditional branches inside templates** (`{% if source_kind == "screenplay" %}`): the settings page would have to execute the template to know the wording under a given axis value, a user changing the wording for one axis value would have to find the spot inside branches, and the change surface would cover all axis values. This is the path that all three reasons in this document reject at once.
- **Putting the template directory into the agent runtime profile**: the profile is an instruction directory that the agent loads verbatim, while templates are data rendered by the server. Putting them together would make materialisation, the sha256 three-state logic and the reset interface manage a batch of files that should never be materialised, and would tie the core library's rendering capability to the profile's deployment form.
- **Referencing partials with `{% include %}`**: with `trim_blocks` enabled, the newline after an include tag is swallowed, making line-level concatenation uncontrollable. Use expression references instead (`partial(...)` / `variant(...)`), and specify that a partial's rendered result has its trailing newline stripped, with newlines decided at the reference site; the same rule covers both inline and whole-line usage.
- **Having the template module locate the template directory itself**: tests for wrong paths would then have to rely on monkey patching or environment variables, and the directory location is part of the deployment form anyway.
- **Pre-rendering all lists in code into string slots**: that would hide wording such as 「故事节点：」 (Story beats:), 「（暂无）」 ((none yet)) and 「当前形态：」 (Current form:) back in code, contradicting "prompt text is visible to users".

## Consequences

- The template module is the single rendering exit for prompt text in the whole repository, exposing only three actions to callers (render by id, list metadata, read source and partial list by id). Adding a generation step means adding a template file, not a builder function.
- Adding a new axis value (a new source file type, asset type, or duration tier) requires adding one file for every variant family on that axis, including the deliberately empty ones; missing one errors at load time rather than being discovered during some generation.
- A test that scans the built-in directory enforces the automatically checkable parts: no axis value comparisons, complete variant families, literal partial names, loops only in list partials, and deduplication enabled only on templates with a plain-text paste-back form. The first boundary (no axis-derived boolean slots) has no automatic defence; reviewers need to watch where newly added boolean slots come from.
- Shared partials are extracted at the threshold of "used by two or more generation steps", counted across all steps being brought under the mechanism, not just those already migrated; fixed wording referenced by only one template is written directly in its body. The threshold also governs references between partials: wording referenced by only one partial is inlined back into that partial rather than given its own file, and sharedness is not inherited through a parent partial. The cost is that a change to a shared partial takes effect across steps, which is exactly why it exists, but during migration the new wording has to be confirmed step by step.
- Wording upgrades in templates do not make existing artifacts stale: templates are the source of the renderer's derived wrapping and, per `docs/adr/0070`, are not part of the artifact basis.
- Spacing between blocks is written at the reference site in the body. When a block-level reference (an expression alone on its line) renders empty or has nothing left after deduplication, the line disappears together with its trailing newline, so empty variants in a consecutive list leave no blank line; after the whole body is rendered, only the extra blank lines produced by the template itself are collapsed, while blank lines and leading/trailing newlines within slot values (user data such as source text windows) are preserved verbatim.
- Idempotent deduplication is not a general rule of the renderer but a capability that a template explicitly enables in its frontmatter with `idempotent: true`, only for templates that have a plain-text paste-back form (`storyboard/image`, `storyboard/video`); templates that do not enable it never skip partials. Text templates reference the same data partial in multiple places (each asset roster being 「（暂无）」 ((none yet)), the current and next episode outlines sharing a list partial), and content-based deduplication would swallow the later data. When enabled, only block-level references take part in deduplication, and it is judged line by line: lines of a partial's rendered result that already appear as a complete line in the body or in a previously injected partial are skipped, and the remaining lines are injected as usual; the `Style` and `Visual style` lines of the style block are judged independently, so a change in one line's value will not cause the other line to be duplicated. Inline references are always injected, so short wording is not swallowed by a string in the body that happens to look the same; list partials under `lists/` carry data and are never deduplicated in any template. The `docs/adr/0070` requirement that "repeated calls on already rendered plain text do not inject twice" accordingly requires these two templates to enable deduplication, and the shared style block and `Avoid` line to be referenced at block level.
- The frontmatter `description` states only one sentence of the template's purpose; its readers are users of the settings page. The reasoning behind wording choices (for example, the asset image exclusion says 「出镜人物」 (on-screen people) rather than 「人物」 (people) so as not to affect portraits or human figures on packaging) goes in the commit message or this ADR, not in `description`, and not in Jinja comments either: a partial's body is the prompt, and Jinja comments would appear on the settings page along with the template body.
- Template language variants are not implemented and no naming slot is reserved for them (`applies_to` has no language axis); per repository policy, the bodies of model-facing templates and partials are exempt from i18n.
