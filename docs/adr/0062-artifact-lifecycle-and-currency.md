# The artifact lifecycle uses the artifact manifest as the single basis of judgement: backfilled means current, stale is still usable

> The applicability of two statements in this ADR — "targets whose basis cannot be projected from the project's current state at backfill time are not registered and report missing on read" and "a backfill failure puts the whole project into a blocked state" — has been narrowed by `docs/adr/0098`: generation gaps no longer prevent basis projection, formal artifacts whose files are usable are always backfilled, and only those whose basis genuinely cannot be computed are not registered; rejecting a whole project because of data is limited to the project or script being unreadable and the import package being unsafe, and a migration that couldn't be completed still blocks per this ADR.

The user has paid once for every artifact (asset design images, script_plan intermediate drafts, formal scripts, grid images, storyboard images, videos, narration audio, subtitles, presentation pieces), and the system must be able to answer two questions: does it exist, and does it still match the current content. Scanning directories or reading path strings in the script can only answer the first question, and mistakes "the file exists" for "the content matches"; storing a status field per artifact requires writing it back in sync on every content change, and one missed write means lying for a long time. We decided to keep the answer in the **artifact manifest** (`lib/artifacts/artifact_manifest.py`, a `.arcreel_artifacts.json` sidecar in the project directory): the manifest registers each formal artifact's identity, on-disk path, and **generation basis digest** (basis digest: canonical JSON + sha256 over the formal content and direct upstream artifacts the artifact directly consumes), and for video and audio also records content facts of the formal file itself (see below); it **stores no status**; currency is derived on read by comparing the expected basis projected from the current project with the manifest entry, producing the four states `current / stale / missing / blocked` (`ArtifactStatus`). Status is not written to disk, so the "forgot to write back" form of distortion doesn't exist — when the content changes, the next read naturally reports stale.

## Decision

- **Currency tracks only formal content and direct upstream artifacts.** The basis captures an artifact's content basis: the formal script captures script_plan and the project's formal metadata, storyboard images capture the script entry body and the asset sheets / originals it references, video captures the storyboard image and the unit body, and so on. The basis of visual artifacts (grid images, storyboard images, videos) describes only formal content: provider and credentials, model, pixel resolution, seed, audio-track switch, and prompt renderer version are all **excluded from the basis** (`lib/artifacts/visual_artifact_provenance.py`) — they are the intent of "how to generate next time", and changing configuration shouldn't collectively judge a whole roomful of images the user already has as stale and force a round of repeat payments; configuration changes take effect on the next generation the user explicitly initiates. Narration audio falls on the other side of this line: voicing parameters (provider, model, voice, speech rate) determine who the user hears reading and how fast, and are part of the delivered content itself rather than generation intent, so they enter the basis together with the narration text (`lib/speech/narration_delivery.py`), and judging old audio stale after a voice change is a truthful statement. The dividing line is "does this bit change the finished content the user gets", not "is it entered on the settings page or written in the script".
- **Asset images brought in as finished products are registered by the image itself.** An asset image's basis is derived from the description, art style, and original, and a derivative asset image's basis from the base asset image and the variation description; this holds only for images generated in this project. Asset images and derivative asset images uploaded by the author, and asset images applied to the project from the global asset library together with the derivative asset images brought in with them, are themselves finished products — whether originally generated in another project or uploaded directly into the library, what matters to the project is the image itself; the description is only a generation input and takes no part in judging it. Library assets therefore carry no provenance marker. Uploading and applying both select a version record with `source: manual_upload` in the same formal commit that writes the image (when applying a batch of assets, all images' version records, files, `project.json`, and manifest registrations are committed together, and failure at any step rolls back the whole); when the planner projects the expected basis for an asset image or derivative asset image, if the selected version is a manual upload and its managed snapshot matches the declared image bytes, it projects a basis determined only by the image bytes (`build_uploaded_asset_sheet_basis`, excluding description, art style, base asset image, and asset name); otherwise it projects from generation inputs as usual. Registration doesn't compute a separate basis; it registers after projection through the same planner, so writing and comparing share a source. Consequently: when the description is empty, bringing it in claims it; afterwards changing the description, art style, or name does not make it stale, and uploaded or brought-in derivative asset images don't become stale when the base asset image is regenerated or the base description changes; afterwards generating and selecting a new image in the project, or the image being externally replaced so its bytes no longer match the selected snapshot, returns to judging currency by generation inputs; restoring the manually uploaded version registers it by the image itself again. Existing asset images without an upload record keep being projected from generation inputs, with no retroactive discrimination. Version records thereby become an input to the asset image's expected basis: when `versions.json` can't be read, asset image currency is judged blocked just like typed media, and does not degrade to projecting from generation inputs — otherwise finished images would be silently re-judged. Archives that export only current content keep the selected manual-upload snapshot in the package, so import and backfill reach the same conclusion.
- **Content digests are cached by file stat identity; the digest value is still a content hash.** Projecting the expected basis requires content digests of input files such as asset design images and storyboard images (`lib/infra/content_digest.py`), and claiming, requests, and polling repeatedly ask about the same set of files. Digests are cached in-process keyed by the file's `(st_dev, st_ino, st_size, st_mtime_ns)`, with a capped capacity and least-recently-used eviction when full: if the identity is unchanged it is reused, if it changed it is re-hashed. What is cached is the content hash, not the identity, so the semantics of the currency judgement are unchanged: when content is replaced, the identity changes with it, and the next read re-hashes and judges stale; copying, importing, and restoring change only the mtime, causing one recomputation, and identical content gives an identical digest, so there is no false stale. The known and accepted cost is that when content is replaced while both size and nanosecond mtime are deliberately restored to their original values, the old digest is returned. Freshly written files (mtime within a few seconds of finishing the read) are not cached, so consecutive rewrites under coarse-grained timestamps aren't treated as unchanged. The cache is in-process only, not written to disk and not a second basis of judgement; losing it costs only speed.
- **Record facts at write time, compute conclusions at read time.** At write time only facts that won't be distorted by later changes are recorded: the generation basis, and the content fingerprint of video and audio artifacts themselves. Conclusions such as currency are always derived at read time, never marked at write time. Project files have write paths that bypass the interface (the agent editing scripts directly, users replacing files by hand, import and restore), so the correctness of write-time marking would depend on every writer never making a mistake; after content is changed back, marks already applied would also need undoing; and marking interrupted halfway would leave a wrong state. Deriving at read time has none of these problems. The root of slow reads lies in how reading is implemented (per-item IO, repeated judgement, re-reading video), not in the principle of deriving at read time itself.
- **Video and audio artifacts record their own content facts at write time.** Besides path and basis digest, entries for video (`episode-video`) and narration audio (`episode-audio`) also record, at the moment of registration, the formal file's content fingerprint (bare sha256 hexdigest), byte count, and nanosecond mtime (`ArtifactContentFacts`; `content_digest` / `content_size` / `content_mtime_ns` in the manifest). The version record also records the content fingerprint of that version's snapshot (`content_digest`). Collection is centralized in the public registration entry point (`observe_registered_artifact`): paid generation, upload, version restore, voice-over delivery, and repair registration all go through it, and the facts are taken from the version of the file read by the same descriptor at admission. When activation (migration activation and self-certifying backfill of envelope-less archives) proves that "the formal file and the selected version snapshot are byte-identical", it records the content facts from the same descriptor; the v17→v18 migration backfills existing video and audio by the same proof, writing into both manifest entries and version records. Importing an archive with an envelope carries content facts only when the activation proof holds and what it proves is exactly the bytes of the envelope fingerprint; entries whose proof doesn't hold carry no facts and are judged stale after import, just as in the source project. Re-keying and compensating rollback move or put back the original entry, and content facts stay with the entry. Content facts take no part in entry equality: writer CAS, rollback judgement, and import validation look only at path and basis digest. When judging whether a write changed the manifest, content facts are included in the comparison.
- **When judging the currency of video and audio, compare against the registered content facts, not the version snapshot.** Only with content facts can it be proven that the formal file is the registered version: if both byte count and nanosecond mtime match the record, it is accepted directly without reading the file content; if either differs, the full fingerprint is computed and compared with the record, and a mismatch is judged stale. When the registered mtime is no earlier than the manifest file's own mtime, a rewrite within the same timestamp might not change any stat field, so it is treated as racy and degrades to full comparison, the same idea as git's racy check against the index file. Entries without content facts cannot be proven and are judged stale. Version snapshots are verified only when actually used: restoring a version and, before producing the final cut, comparing against the fingerprint in the version record; a mismatch fails with an explanation. In the final cut's basis, a video unit's content fingerprint is taken from the version record's snapshot fingerprint; only old versions without a recorded fingerprint are computed on the spot. The known cost is the same as for the content digest cache: if content is replaced while byte count and nanosecond mtime are deliberately restored, it is missed.
- **Backfilled means current.** When the project schema is upgraded to the artifact manifest, the project's existing formal artifacts are registered into the manifest once, using the basis projected at the moment of migration; the registered value and the expected value share a source, so backfilled artifacts are **always judged current**. Backfill uses `project.json`, the `generated_assets` of episode script entries, asset definitions, and the controlled `grids/grid_*.json` records as the authoritative index (`lib/artifacts/artifact_planner.py`, exposed externally via the unified facade `lib/artifacts/artifact_activation.py`), without scanning directories or guessing paths. No third "legacy / unknown provenance" state is introduced, nor is stale presumed because "this artifact was produced by the old flow": after upgrading, users shouldn't be misled into regenerating things they've already paid for. Targets whose artifact file is absent, or whose basis cannot be projected from the project's current state at backfill time (e.g. a required upstream artifact doesn't exist yet), are not registered, and report missing on read because the manifest has no such entry; archive import goes through the same entry point but keeps the basis digests frozen in the archive rather than the current projection, so an imported project may carry stale entries — this truthfully relays the facts at archive time and is not a defect. Subtitles and presentation pieces bind, at materialization, to the video version selected at the time, and `use_tts` variants also bind to the narration voice-over version; if a unit later switches its selected video or audio (manual upload, AI regeneration, or switching versions), these entries are temporarily not applicable during export and import: those still fully self-certifying against the video and audio versions they're based on are preserved as usual, a full export carries them in the package, and after import switching back to that version makes them valid again; an export of current versions only doesn't carry old version snapshots, so these entries don't go with the package. Entries that can't be proven for other reasons still make export and import fail as usual. Unactivated projects can still be exported as archives: export is a read-only path and is allowed as usual for unactivated projects (including those blocked by a failed migration); their archives are judged by the data-version gate to carry no manifest envelope (`server/services/project/project_archive.py`), and after the import side runs the migration chain it goes through self-certifying backfill, the same approach as the upgrade path. This compatibility branch is deliberately kept — it shares its criterion with the activation gate (whether the schema is the current version), judging "is there an effective manifest to preserve right now": that is the case for never-activated projects; and likewise for projects that were once activated but whose schema lags the current version — the manifest file exists but is no longer effective, its frozen basis digests don't go into the archive, and the import side recomputes them under the backfill approach after re-projection; the archive keeps no second reading basis for an ineffective manifest. Deleting this branch would mean a blocked project couldn't even export a backup, escalating one data anomaly into trapped data. This is a different matter from the runtime `blocked` below: here there are simply no entries to register at backfill time, while `blocked` means the manifest already has entries but the runtime read or basis computation itself failed.
- **Stale is still usable.** The meaning of `stale` is "older than the current content", not "unusable": it can be viewed, takes part in the final cut and export as usual, blocks no step, and is not a regeneration instruction. The usable set is `usable = current ∪ stale`; generation calls that don't specify IDs only fill `missing` (fill in what's missing), and redoing stale must be explicitly chosen by the user. `blocked` (manifest unreadable, path stopped by a blocker, basis unavailable) always fails loud and doesn't degrade to missing — treating unreadable as absent would turn a fault into an automatic payment.
- **Task results and artifact currency are independent.** A batch generation is exhaustively partitioned per request into `succeeded ∪ failed ∪ blocked` (`GenerationItemState`), while artifacts independently report the four states, and neither set of states is derived from the other. When a forced regeneration of a current artifact fails, the task is failed while the artifact is still current; an artifact being missing doesn't imply the previous task failed (it may never have been requested). The receipt carries both side by side so callers read them separately, rather than letting "this attempt didn't succeed" and "there's no usable content now" substitute for each other.
- **The four status axes are not merged.** Artifact currency (`ArtifactStatus`), task status (queue row status and the external `GenerationTaskState`), the batch admission conclusion (`BatchAdmissionDecision`, see `docs/adr/0061`), and per-ID execution results (`GenerationItemState`, `lib/generation/generation_result.py`) answer four different questions — "is there usable content now", "how far has that async job got", "should this batch request happen", "what happened to each item that did happen". They are carried side by side on the same receipt record and are not folded into one "status" field: any folding would require a translation table elsewhere, and would inevitably say the wrong thing for some combination (typically a task that succeeded but whose artifact was later deleted externally, or an artifact that is current while this forced regeneration failed).
- **`schema_version == 8` is the only activation gate.** Whether the manifest is effective for a project depends only on whether `schema_version` in `project.json` equals `CURRENT_PROJECT_SCHEMA_VERSION` (`lib/project/project_schema.py`). Activation goes by forward commit: within the project metadata lock the migration first does a complete read-only pre-check, then writes the whole manifest at once; if the pre-check re-verification fails after that, the manifest is rolled back to the pre-write snapshot. The schema version is committed only after the manifest is written — if this step fails, the manifest stays at the newly written content but the schema is still the old version, so the manifest is not effective, equivalent to staying at the old version; no second manifest-level rollback is done, and after fixing the data, rerunning the migration converges to the new version, the rerun itself being an idempotent full re-projection. Unactivated projects have no second reading basis to fall back to: `active_artifact_currency_resolver()` raises `ProjectMigrationError` for them directly, so a caller that can't get a resolver has no way to answer artifact status, and therefore no way to silently degrade. Blocking is uniform — generation entry points, the queue's `enqueue_task()`, MCP tools, and REST write paths read the same verdict (persistent record of migration failure ∪ schema lagging the current version), the reason is surfaced as-is, and retry after fixing the data. Blocking is governed by entry-point declarations: REST write routes attach the `require_project_migration_ok` dependency, and agent tools are wrapped at the entry point via the migration-blocking policy declared by the tool; inner verdicts in callees (such as `ScriptBatchEditor`) serve only as a backstop and are not a reason for any entry point to omit its declaration. Rerunning the migration chain is not a reconciliation entry point: for a project already at the current version it returns immediately and does nothing; when a full re-projection is needed, use schema-preserving activation (`activate_artifact_target_state(bump_schema=False)`) — recomputing the target state and atomically replacing the whole manifest, returning `False` when entries are unchanged, idempotent and re-entrant. Day-to-day artifact content changes don't need re-projection; read-time currency judgement answers them. The project can still be opened: read-only paths fetch script and canvas files directly by path, not through the manifest. At any moment a project has only one answer to "can it generate", and only one answer to "do artifacts exist and do they match" — after activation the manifest answers; before activation the answer is "unreadable, fix it first".
- **The manifest lock protocol is project-level, cross-process, and full-replacement.** Each project has one `.artifact_manifest.lock` (portalocker exclusive, non-blocking polling, errors after a timeout rather than waiting forever), with project rather than episode granularity — artifacts depend on asset sheets shared across episodes, and episode-level locks can't stop the real contention. All writes complete their read-modify-write inside the same lock, and writing to disk goes through temp file + fsync + atomic rename, so the manifest is always a self-consistent snapshot with no half-written state. Reads therefore don't take the manifest lock: the descriptor a reader opens necessarily reads some complete manifest; each read still verifies the project root identity, rejects symlinks and junctions, rejects FIFOs, and caches only the parse result in-process. A request reads only one manifest snapshot (read when the currency judge is constructed), and admission and all currency comparisons within the request happen on that snapshot, so the manifest being replaced mid-request doesn't affect that request's conclusion. On Windows, while a reader has the manifest open, atomic replacement and deletion of an empty manifest both fail with a sharing violation; the writer then retries briefly a limited number of times, and errors as usual when retries are exhausted. Scoped CAS (replace only the entries involved this time, keep unrelated ones) and full CAS are used to turn drift between "read—judge—write" into explicit failure rather than overwriting. Activation and pre-payment re-verification additionally need the coarser project metadata lock `.project.json.lock`, with a fixed hierarchy of metadata lock ⊃ manifest lock and no reverse nesting. "Errors after a timeout rather than waiting forever" describes only the manifest lock; the project metadata lock (`lib/artifacts/formal_write.py`) is a blocking lock without timeout working with queue-wait semantics, and the two locks' wait policies are not unified.

## Explicitly not adopted

- **Judging artifact existence by scanning directories or reading path strings in the script**: can only answer "does the file exist", not "does it match the current content"; and the same tally would be written three times on the frontend, REST, and agent sides, so after deleting one storyboard the conclusions would inevitably diverge. This holds for unactivated projects too — keeping a side path for them that answers by file existence would be keeping a copy of an already rejected basis behind a schema branch.
- **Storing a status field on manifest entries, or marking downstream as outdated at write time**: requires every content write to write back all downstream entries in sync, and one miss means lying for a long time, and the write-back itself needs a cross-file transaction; for the reasons around interface-bypassing writes, content being changed back, and interruption, see "Record facts at write time, compute conclusions at read time" above. Comparison at read time builds correctness on the single invariant "basis digests are equal", at the cost of a projection on every read, the most expensive part of which is content-hashing input files; that part is cached by file stat identity, so the cost depends only on files that actually changed and does not grow linearly with the number of reads.
- **Including all generation configuration in the basis**: switching a video model would make the whole project's videos stale, which amounts to using configuration changes to hint at repeat payments; configuration that only affects "how to generate next time" should take effect on the next generation and not retroactively judge existing artifacts. Conversely, "nothing entered on the settings page goes into the basis" is likewise not adopted — narration voicing parameters are entered on the settings page yet determine how the finished product sounds; the line is drawn by whether it changes the finished content, not by where it's entered.
- **Marking stale after backfill, or introducing an "unknown provenance" third state**: the upgrade itself changes no content, and judging things old out of thin air would only push users to regenerate artifacts already paid for; a third state would also require every consumer to write an extra branch.
- **Automatic regeneration of stale artifacts**: "old" doesn't mean "should be redone". Automatic regeneration turns a status query into a charge, and often the user knows precisely that it's old but this version is good enough.
- **Silently pretending everything is fine after a migration failure**: for migration (including backfill) failure we do not "swallow the error and keep answering artifact status with the historical reading behavior" — that would make users think the project is intact. The failure must be persisted as a blocking verdict (`migration verdict`, see the "迁移失败判定" (migration failure verdict) entry in `GLOSSARY.md`), the reason surfaced as-is, generation entry points refuse, and the project can still be opened but does not pretend the manifest basis is in effect. Projects whose schema lags and which the migration chain hasn't reached yet fall under the same verdict: they have no written failure record, but they likewise can't read a single artifact, so computing "not yet upgraded" on the spot from the schema criterion suffices; the written record takes precedence only because it names the specific data to fix.
- **Episode-level locks or incremental per-entry manifest writes**: activation writes a complete target state, and per-entry writes would leave a half-activated project after interruption; asset sheets shared across episodes also mean episode-level locks can't stop real concurrent writes.

## Consequences

- **Manifest size contract**: every manifest write is a full parse / full serialization + whole-file rename; read-only queries reuse the parse result of the same version in-process by manifest file identity, and when the file changes the whole thing is re-read and re-parsed. The upper bound on entry count is about `asset count + Σ_per episode(2 + grid count + 7 × storyboard entry count)` — each script entry owns at most 7 artifact identities: storyboard image, video, audio, two kinds of subtitles, and two kinds of presentation pieces. A project of a hundred episodes × dozens of storyboards per episode would reach tens of thousands of entries and several MB in a single file, with per-read/write cost rising linearly. **This is a known and accepted cost point of this design**: entries have no cap and no LRU / TTL pruning — pruning would turn "does the artifact exist" back into guesswork. The manifest shrinks only in two cases: the canonical ownership of an artifact disappears or moves (a script entry is deleted, a resource is renamed), and the whole sidecar is deleted when entries are emptied; **a basis change only makes an entry stale and does not make it ownerless, which is deliberately kept**. If size becomes an actual bottleneck, the way out is sharding or switching to an incrementally readable container, not dropping entries.
- A backfill (migration) failure puts the whole project into a blocked state: readable, existing artifacts viewable, no generation. This trades "silent degradation" for "explicit shutdown + repair path", at the cost that one data anomaly leaves the user completely unable to continue generating, so the failure reason must be visible as-is, and there must be a retry entry point that doesn't require hand-editing JSON.
- Reads don't take the manifest lock, so long lock-holding writes (activation, batch registration) don't make concurrent status queries wait or fail; manifest lock timeout errors fall only on concurrent writers. Reads also don't create the lock file, so read-only queries never turn into a write.
- The correctness of currency judgement depends on "projecting the expected basis" and "registering the basis" using the same code; once they diverge it shows up as a whole class of artifacts going stale for no reason. When adding a new artifact kind, the registration path and comparison path must share the same basis constructor; writing one each is not allowed.
- Product assets' standardized sheets share this lifecycle with other asset sheets — registered as artifacts, four states judged by the same rules, stale usable and not automatically regenerated (see `docs/adr/0034`).
- The unified facade of `lib.artifacts.artifact_activation` is a long-term contract: the four submodules split by responsibility, `artifact_planner` / `artifact_currency` / `artifact_input_claims` / `artifact_registration`, are not exposed directly outside the module, and external references always go through the facade namespace; the underlying data module `lib.artifacts.artifact_manifest` is not part of this split and not bound by this item. Test stubbing is an exception within the design: the facade provides symbols by re-export, and patching a facade alias can't replace runtime references inside submodules, so stubs that replace submodule behavior land on the implementation modules. If the split is ever to be made visible to consumers, this item must first be revised and call sites migrated.
- Terminology follows the "产物与制作状态" (Artifacts and production status) section of `GLOSSARY.md`: entries such as artifact, artifact manifest, artifact currency, backfill, and production status share a source with this ADR, and wording does not evolve separately; mechanism statements unique to this ADR (the four status axes are not merged, fill in what's missing, task results and artifact currency are independent) are recorded only here and not repeated in the glossary.

## User-provided artifacts (revision)

"Asset images brought in as finished products are registered by the image itself" is extended to user-uploaded storyboard images and videos: when the selected version is a user upload byte-identical with the artifact, the expected basis is determined only by the uploaded bytes, and the prompt, referenced assets, art style, and storyboard-image upstream take no part. Thus an upload is current immediately, later changes to the prompt or assets don't make it stale, and downstream consumers (video takes the storyboard image as input) no longer question its generation basis; generating and selecting a new version, or the storyboard image being externally replaced so it no longer matches the selected snapshot, or the video being externally replaced so it no longer matches the registered content fingerprint, returns to judging currency by generation inputs. The system does not judge whether user-uploaded content matches the current script; that judgement is left to the creator.

Two previous practices are abolished together: uploaded videos were never registered and were only claimed by the fallback of the version record's manual upload; and uploaded storyboard images had their entry deleted and were judged missing when the prompt was empty or a referenced asset lacked an asset image, causing downstream video to be rejected with "storyboard image not registered". Batch generation that fills in what's missing will therefore no longer pay to overwrite user-uploaded artifacts.

## The basis of storyboard images and grids does not record asset names (revision)

"Draw the line by whether it changes the finished content" applies equally to asset names: the reference images sent to the image model for storyboard images, grid composite images, and cut-cell storyboards are listed only by type as "图N" (Image N), and `@[名称]` (`@[name]`) in the body text is also rendered as "图N" (Image N), so the asset name is not a model input. These three kinds of basis therefore record only the asset reference image's type, role, kind, and content fingerprint; mentions in the prompt that identify asset reference images are replaced with "图N" (Image N), and mentions that don't match a reference image are kept as-is (the model sees the name); identities of non-asset reference images such as the previous storyboard image are still recorded (`without_asset_names` in `lib/artifacts/visual_artifact_provenance.py`). When an asset is only renamed these artifacts stay current, and they become stale only when the asset image is changed. The declaration lines of reference-to-video and the dialogue of storyboard image-to-video contain asset names, and asset images' prompts contain asset names; their bases are still recorded, and becoming stale after a rename is correct.

The basis of grids and cut-cell storyboards is replayed from the reference images frozen in the grid record, so the cascading transaction of asset renaming also rewrites the reference-image names in grid records and the paths migrated with the rename. When assets are merged, derivatives that move with their images under the surviving asset's name go through the same rewrite; those merged into a derivative the surviving asset already had are replaced by a different image, the record is not repointed, and they become stale as usual. Existing projects are carried over by v18→v19: the manifest only rewrites registrations that were current before the upgrade, the bases frozen in version records are rewritten entry by entry with the same function, and the change of basis format does not make existing artifacts expire wholesale.
