# Image / video models are configured by capability bucket: a single default + optional capability overrides

> The part of this ADR stating "the audio-track form of custom providers is not open to model-level overrides" has been superseded by `docs/adr/0104`: the audio-track form, like other channel facts, can be replaced as a whole dimension by a capability override on a provider model the user is responsible for. Without a capability override, a custom provider's audio-track form is still handled as "no signal, no tightening".

Some video models have only some capabilities (i2v only, no reference-image slots); a single "video model" setting cannot express this constraint, and a project with the wrong model selected only fails at execution time on the reference-to-video path. We decided to unify image and video as "**a single default model + optional override buckets by capability**": image t2i / i2i, video i2v / r2v; the resolution order is isomorphic with the text tiers (`docs/adr/0051`), project first — project bucket > project default > global bucket > global default > automatic inference, with empty buckets falling back to the default layer. The mapping between buckets and call sites is fixed in code: images are bucketed by the request shape at execution time (see `docs/adr/0001`), while video first fixes its axis by the **project generation route** — the route is fixed at creation and immutable thereafter (read-side bucketing function `lib/config/resolver.video_bucket_for_generation_mode`, route predicate `project_manager.is_reference_video_project`); scripts carry no route information, and all three content_modes follow the same approach (see `docs/adr/0055`). Storyboard route (including grid assembly) → i2v; within the reference route, shots are further routed by the reference images actually available: with images → r2v, **degenerate shots without images downgrade → i2v**. The reference route's quoting, Web/Agent pre-checks, queue rate limiting, and execution layer all first hydrate the current assets with `lib/script/reference_video/request_projection.py`; when declared references and actual assets diverge, a declared→hydrated result and a structured blocker are returned, without silently switching bucket or model. This ADR converges the configuration form of the two image slots; the three-way endpoint split and runtime gating of `docs/adr/0015` are unaffected.

## Explicitly not adopted

- **A t2v bucket**: its only call site would be the reference route's degenerate imageless shots, which are taken over by the i2v bucket (degraded execution): the i2v bucket already has a configuration surface and resolution gate, and adding a third bucket for the pure-text case would only add configuration surface. The downgrade changes the success criterion for a degenerate shot from "does the r2v bucket model accept empty references" to "does the i2v bucket model accept a pure-text request", without promising the shot will be executable — the i2v gate checks only `first_frame`, so a model that only serves image-to-video endpoints (Vidu's `viduq3-pro-fast` / `viduq1-classic` / `vidu2.0` are not on the `/text2video` allow-list) still fails explicitly at execution time when it receives empty references. What falls into this residual surface are narrow-capability "image-to-video only" models, a much narrower set than what previously fell into "mainstream r2v models that reject empty references" (DashScope R2V, MiniMax S2V raise `video_reference_images_required`), and switching the i2v bucket to another model resolves it.
- **Configuring models per generation route**: a route is a video source path, not a capability; it cannot express the original constraint "the model has only some capabilities", and adding or removing routes would directly hit the configuration surface.
- **Mandatory per-bucket configuration (no default layer)**: all-capability models are the mainstream case, and forcing per-bucket configuration is pure burden for most users; a flat set of isomorphic dropdowns also has no hierarchy; default + refine as needed keeps the configuration surface tight.
- **Silently switching models when capabilities are not met**: the user would pay, unknowingly, for a model they never selected. When capability validation fails at resolution time, a structured error is raised directly (aligned with the text vision precedent), and the error message guides the user to configure the corresponding bucket.
- **Write-side interception and cascading cleanup of bucket references**: the causes of dangling bucket references (custom model capability overrides modified, model / provider deleted, endpoint changed, registry upgrade changing the system's judgement) are uniformly backstopped by the resolution gate's error. Write-side interception would require reverse-scanning project buckets scattered across each project.json, which is expensive and has a concurrency window; cascading cleanup is just another form of silently changing configuration. Both video routes re-project against the current configuration before submit; submitted tasks recover only from the dedicated execution checkpoint and do not go back and silently switch models.

## Consequences

- The capability source of truth stays with the existing declarations, with no new copies: both buckets take the backend's `VideoCapabilities` — i2v looks at `first_frame` (the storyboard route is driven by the first frame, and grid assembly doesn't change that), r2v looks at `max_reference_images > 0`; for custom providers = endpoint system judgement ⊕ model-level `capability_overrides` combined. For built-in video models these two dimensions are declared only in the backend; registry `ModelInfo` carries no video capability bits or reference-image limit — a single token can't distinguish the image-to-video and reference-to-video paths (e.g. `happyhorse-1.0-r2v` accepts only reference images, not a first frame). Bucket dropdowns pre-filter candidates accordingly; the default-layer dropdown does not filter — the default layer promises no capability.
- The final cut's audio track (whether there is one, whether its switch is controllable) also belongs to the backend's `VideoCapabilities`, and is **declared once per bucket**: `audio_track` describes the i2v path, `reference_route_audio_track` describes the r2v path (absent means both paths have the same form), and values are always taken via `audio_track_for_route(capability)`. Per bucket rather than per model, because the two paths of the same model can give different answers — Kling v3-omni's multi-image subject sub-path (R2V) has no audio switch `sound` in its native schema, so the final cut is necessarily silent, while its image-to-video sub-path's switch is controllable. The presentation layer (greying out the switch on the settings page), the enqueue pre-check (rejecting "turn off audio" for always-audio models), and sound-consistency derivation all read the same per-bucket declaration, so reference-to-video is presented truthfully as "this path has no audio switch", rather than letting through a switch that is certain to be discarded at execution time. An undeclared model takes `controllable` (no signal, no tightening), so models with unknown capabilities are not falsely reported as having a non-working switch.
- The audio-track form of custom providers does not take part in the derivation above and is always handled as "no signal, no tightening" (has an audio track, switch controllable), and model-level overrides are not opened up: the settings UI can't get a per-model audio-track catalog for custom models (they are not in `/providers`), so server-side unilateral derivation would make the UI and the enqueue pre-check say different things; the upstream model behind an endpoint is filled in by the user and cannot be verified, and misjudging it as always-audio would block legitimate configuration from enqueueing. This user-set bit also has no execution-side counterpart — a protocol backend either sends the audio-track switch or doesn't, and the declaration can't change that.
- All read sides (`video_capabilities` queries and agent tools, cost estimation, narrowing of duration / resolution constraints) follow the same approach as the execution side: fix the bucket as above, then go through the same resolution function. Project-level read sides (`video_capabilities` queries, storyboard document preview) fix the axis once by the project route, need no episode or script context, and don't branch on the three content_modes — when they evaluate, units either don't exist yet or are irrelevant, so there are no shots to route. Shot-level read sides of the reference route (cost estimation, rate-limit routing projection, Web/Agent pre-checks) share the request projection with the execution side: read the current project/script/unit, expand and verify the actual assets, then fix the bucket and resolve provider/model and duration tier. The projection is advisory, not an executable snapshot; it issues no token/fingerprint, and the worker must re-project the latest state when it starts. The WebUI's per-storyboard video generation endpoint still fixes the bucket by project route, and reference-route projects are rejected outright at that entry and directed to the reference-to-video flow (see `docs/adr/0055`).
- Neither video route locks provider/model at enqueue time: the task row's `provider_id` is only claim/rate-limit advisory, and old video identity keys in the payload are ignored at execution; the payload stores only task location and user request options, and does not freeze the complete request. Edits to the project, script, or assets while queued therefore take effect when the worker starts. Only a path that misses video reuse and is truly about to enter provider submit crosses the execution checkpoint boundary: the actual provider and the versioned complete execution facts are atomically written to a dedicated task column immediately before submit, without rewriting the payload. After the provider creates the job, polling and restart recovery read only that checkpoint, without recomputing the current script/references/provider/model; the current project only supplies credentials and backend construction, and if the resolved identity or custom endpoint differs from the checkpoint it fails explicitly. The agent tool layer's `resume=true` (re-enqueue unfinished shots for submission) is a different mechanism, and computes a new execution identity from the configuration at that time.
- On the image side, an empty bucket means "fall back to the default layer"; there is no reading of "empty = follow automatic inference"; key combinations in existing configuration are exhaustively handled in migration.
- Frontend presentation and per-model storage are keyed by the **executing model**: any UI element that looks up capabilities by model or stores configuration by model (capability panel, resolution under `model_settings`, etc.) always takes the model the current configuration will actually execute — the in-bucket model when a refined bucket is in effect, otherwise the result of computing through the default layer; on the video side the bucket is first fixed by project route and then evaluated, from the same source as the backend's route-based bucketing, so it is consistent across the whole project. One exception on the image side: `executingImageModel` takes only the executing model of the T2I layer, and the image resolution is stored and retrieved under that key, while I2I uses its own executing model — when the two are configured with different models, I2I at execution time looks up `model_settings` by its own model, doesn't find the key, and falls back to the provider's default resolution tier. The default-layer model is not used as a lookup or storage key unless it is the executing model.
- The settings UI for all three media (text tiers / image buckets / video buckets) shares the same interaction form: a persistent main default dropdown + a collapsible capability refinement area; placeholders of unconfigured buckets compute through to the finally effective model and label the call sites each bucket covers (zh / en / vi in sync); the creation wizard exposes only the default layer.
- On the video side, the executing model and capability facts are evaluated once per request as "video request facts"; in reference-to-video projects, when the i2v bucket is unavailable, the tier of units without reference images is "unknown" and does not fall back to r2v; see `docs/adr/0086`.
