# Script save validation uses "no worse" semantics; the asset write-back hot path is exempt

Script structure validation (`segment`/`scene`/`unit` shapes, `duration` range, required fields) had previously been extracted into a pure function but was only called at the archive boundary; the write-to-disk path did no validation at all — dirty data was not reported at write time, `load_script` only does `json.load` and did not report it either, and it only blew up deep inside the worker during parsing. We decided to move this structure validator (defined once as a pure function) forward into the unified Python write-to-disk entry point `_write_script_unlocked`, but **not** to adopt "always strictly raise": a write is rejected only when "valid before the change ∧ invalid after the change" (i.e. this write introduces a new structural error); legacy scripts that were already invalid before the change are let through as usual; at the same time, the asset write-back hot paths that only touch `generated_assets` (`update_scene_asset` / `batch_update_scene_assets` / `update_character_sheet` / reference video task write-back) **skip** validation entirely. The validation target is the structural Pydantic model (choosing `Narration`/`Drama`/`ReferenceVideoScript` by `generation_mode`/top-level keys), **not** the FS-aware `DataValidator` — the latter reads the disk and rejects valid half-finished drafts (storyboard images not yet generated).

## Consequences

- Saving sometimes accepts an already-invalid script (broken before the change). This is deliberate: the guard's job is "don't let this edit bring dirty data into the system", not to take the blame for historical leftovers produced by schema evolution; otherwise a user editing an old script that was "valid when written but doesn't satisfy the current schema" would suddenly get a 400, and not because this edit was invalid. When `load_script` has no preceding `before` (e.g. normalize calling `save_script` directly), it produces a fully recomputed script, and strict validation is fine.
- Skipping validation on the asset write-back path means a worker attaching `generated_assets` to a legacy invalid script will not be dragged down along with it. The rationale is performance + semantics: these are high-frequency hot paths that only write `SkipJsonSchema` runtime fields, the structure cannot get worse because of them, and there is no need to validate the whole script every time.
- Validation failures surface **at write time** on the spot (the manual path returns an error), rather than blowing up in the execution layer after queuing.
- Scripts/`project.json` have three write surfaces: the Python API (`save_script` etc., covered by this ADR), the agent generation tools (`text_generation`→`ScriptGenerator`, already Pydantic-validated at generation time), and **the agent's bare `Write`/`Edit`**. Before `docs/adr/0003` landed, the last surface only went through the PreToolUse JSON syntax hook (`json.loads` + curly quotes), so structural errors still landed on disk, bypassing this ADR's unified entry point; it is now rejected by two layers (the `_check_write_access` hook + sandbox denyWrite, see `server/agent_runtime/agent_access_policy.py`) and taken over by in-process MCP tools — script edits (`patch_episode_script` etc.) go through the `_write_script_unlocked` choke point, and `project.json` (`patch_project`) goes through `ProjectManager.update_project` / `upsert_assets` and their error-set diff guard; each of the two write paths has a single mandatory validation point.
- **Do not "tighten it into always strictly raise"**: that would make editing old scripts regress to 400 and add a full validation cost to every hot-path write-back — these two points are exactly what this decision deliberately avoids.
- This and enqueue-side validation are two independent axes: this ADR governs "writing to disk"; enqueue-side structural validation (provider-agnostic) and capability validation (duration↔supported_durations, resolved at execution time, see the `docs/adr/0001` principle) land separately, and depend on provider resolution convergence (#599) landing first.
