# The market uses multiple market-source GitHub repositories; browsing and installing depend on no central service and need zero accounts

Sharing of custom invocation endpoints previously stopped at file export and import; having the ArcReel side operate a central service for browsing and one-click install was listed as out of scope, because it would require long-term operation of a service and an account system. We decided that **the market is hosted by multiple market sources, each of which is a GitHub repository or an equivalent direct `https://` link**: the official market source ships preset with each release, can be disabled but not deleted, and is also a GitHub template repository, so forking it creates a third-party market source; submissions are PRs to the official repository, gated by manual merge and CI validation; third-party market sources are added by users themselves, at their own trust and risk. "Zero server" means browsing and installing do not depend on any central service operated by the ArcReel side: the local `server/` still provides the market API and install transactions, and fetching is initiated by the backend on the user's behalf. Install counts, ratings and share submissions are handled by an official service as an overlay independent of the index (`docs/adr/0093`, `docs/adr/0094`); it is not a market source, and when it is turned off or unreachable, browsing and installing work as usual. The market is a user feature; the embedded agent does not browse or install market entries.

**Explicitly rejected**: browsing and installing via a central service, or on-site publishing that bypasses market-source PRs (this requires long-term operation of an account system and would create a second source of truth outside the index, contrary to the open-source self-hosted positioning); sharing between users within the same instance and link / short-code sharing (both need an addressable center); comments (need accounts and content moderation); proactive takedown notifications and remote disabling (only passive status is possible).

## Three deviations that will be questioned

- **The whole fetch chain uses only raw file URLs and does not call the GitHub API.** Anonymous API rate limits will inevitably be hit with many sources and many users, and adding a token brings back the account problem; more importantly, the mainland China reachability solution is a nullable global proxy prefix that is prepended to `raw.githubusercontent.com` URLs, and the prefix can cover all GitHub-shaped traffic precisely because there is only one kind of URL, raw. The cost is losing metadata only available through the API, such as stars and Releases, so the index must carry everything the client needs to display. The backend fetches arbitrary `https://` URLs on the user's behalf, so the implementation must be treated as a server-side request forgery exposure: the URL, resolution results, redirects and response size all need bounds, with the rules carried by the Spec.
- **The index is a CI projection of the definitions' `meta`, committed into the repository by a bot, not a hand-written second source of truth.** Submitters only add their own entry directory and do not touch the index, so there are no merge conflicts; client browsing reads only the index, and the single definition is fetched only at install time; if the index and the definition disagree, installation is refused, and neither side is taken as authoritative. Third-party sources that do not use the generator may write the index by hand, as long as it conforms to the schema. The index schema and the definition schema have different compatibility rules: the index must let old clients ignore unknown optional fields, and only a higher major version makes the whole index unreadable.
- **The validator and generator are implemented only once, in this repository, and market repositories' CI follows this repository's `main` via a reusable workflow.** The alternatives were copying the scripts into the template repository (a fork gets a snapshot and loses touch as soon as the rules change) or pinning a version (each fork upgrades itself). Following was chosen, trading "a rule change in this repository may suddenly turn market repositories' CI red" for "the rules have a single implementation, and forks need zero maintenance". A released client carries its own version of the validator, so the official repository may accept entries before a release; this is handled by the minimum application version that each entry declares.

## Consequences

- Two new entities are added, market source and installation record, and the index cache is stored in the database; for installation records see `docs/adr/0079`.
- The official repository's default branch is the release branch; takedown means deleting the directory, with no trace left.
- The official service acts only as an overlay: the three rules (fetch only via raw URLs, the index is the only truth, the validator has a single implementation) do not change because of it; the official service references the same validator when pre-checking share submissions.
- Introducing central capabilities beyond the overlay into the market (push, remote disabling, making browsing or installing depend on a central service), or switching to the GitHub API, requires revising this ADR first; the market API of the local `server/` evolves as usual and does not trigger a revision.
