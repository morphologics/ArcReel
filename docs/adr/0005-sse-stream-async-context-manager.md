# Session/project event SSE streams are exposed as async context managers; consumers poll is_disconnected on idle wake-ups to guarantee cleanup

Real-time pushes for sessions (`SessionManager`) and project events (`ProjectEventService`) used to expose a bare `asyncio.Queue` as the interface: each consumer did its own `subscribe` → hand-written `while queue.get()` loop → `finally: unsubscribe`. Forgetting the `finally` meant a subscriber leak. We converged this into an **async context manager** `stream_messages()` / `stream_events()`, made `subscribe/unsubscribe` private, and hid subscription + queue consumption + unregistering on exit behind the seam; history replay is not hidden inside the seam — the session stream marks that the subscription has been atomically established with a first-event barrier, and after the barrier the consumer reads the existing backlog from the database itself (see Consequences). But **merely making it an async generator is not enough to guarantee cleanup**: `async for ... break` **never** automatically acloses an async generator (an absolute fact at the language level); its `finally` only gets run by the event loop after garbage collection; and whether `finally` runs promptly when the client disconnects depends on **how the runtime terminates/cancels** this generator chain — it is neither necessarily prompt nor necessarily left to GC. FastAPI's native SSE `fastapi.sse` implementation (source analysis based on 0.136.1, pinned at decision time, whose comments cite PEP-789 as motivation; this decision does not depend on that version's specific cancellation timing — precisely because the timing of cancellation injection cannot be guaranteed, we don't bet on it, and later version upgrades do not overturn the conclusion) uses structured concurrency for teardown: it hands the endpoint generator to a task group on the request-level `AsyncExitStack`, and on disconnect does `cancel_scope.cancel()` rather than throwing `GeneratorExit` into the generator. Per its source, the cancellation signal only propagates down the chain into a nested generator's `finally` when the generator is **waiting for the next item** (the `__anext__` chain); if the generator is parked at its own `yield` (the consumer isn't taking, buffer full — the common case on disconnect), the cancellation hits the send and **cannot reach** the nested `finally`, so cleanup falls back to GC again. Therefore we decided: (1) the interface shape is an **async context manager** rather than a bare generator, letting `__aexit__` carry the cleanup; (2) the consumer loop relies on idle wake-ups (the session stream's heartbeat events / the project event stream's `_idle` sentinel) to wake periodically and `await request.is_disconnected()` to **actively detect the disconnect and break normally**, so that `__aexit__` triggers deterministically, rather than betting on whether cancellation injection lands on time. `project_events.py` already used this `is_disconnected` polling approach — this decision aligns the session SSE path with it.

## Consequences

- `stream_messages()`/`stream_events()` must be consumed with `async with`, and cannot be used directly with `async for` as a bare generator. All new SSE consumers use the CM form; in review, a bare `async for some_stream()` is treated as a cleanup hazard.
- The event shapes of the two streams are **per stream, not global**: the session stream (`SessionManager.stream_messages`) produces semantic events — the first event is a subscription barrier (`SubscriptionReady`, marking that the subscription has been atomically established and that broadcasts after it have no gaps; history replay is not inside the seam — a consumer such as `AssistantService` reads the existing entries from the database via `event_log.list_entries` after the barrier, and duplicate deliveries between subscribing and the database read are filtered by identity through a seq threshold), followed by individual live items (`LiveMessage`) and heartbeats (`Heartbeat`); subscription queue overflow is expressed as **end of stream**, and end of stream is the reconnect signal; the overflow sentinel is kept inside the subscription broadcast component SseChannel (`server/sse_channel.py`) and consumers are unaware of it. The project event stream (`ProjectEventService.stream_events`) is still bare message dicts + an `_idle` idle sentinel (consumers dispatch on `msg.get("type")`), using "snapshot as the first event" in place of a replay boundary; when the subscription queue overflows, the subscriber is removed and its stream ended, and after reconnecting the client is realigned by the initial snapshot (see the last item). Consumers must handle the corresponding shape according to "which stream they consume". For the boundary decision of the session stream seam (typed events absorbing the sentinels) see `docs/adr/0046`.
- Idle wake-ups make the SSE path check `is_disconnected` periodically, and maintain liveness and the cleanup boundary through the session stream's `Heartbeat` or the project event stream's `_idle`.
- Do not rely solely on FastAPI/anyio cancellation injection or GC for "prompt cleanup when the client disconnects". Disconnect promptness is the responsibility of the consumer's `is_disconnected` self-check; the CM's `__aexit__` is responsible for "unregister no matter why it exits". Missing either one: with only the CM and no self-check, a parked-at-send disconnect still drifts to GC; with only the self-check and no CM, exception paths may still miss unregistering.
- When `ProjectEventService` overflows, it must end the stream of the removed subscriber: a stream that only sends idle heartbeats will not trigger a client reconnect, and subsequent one-off events (such as the resume notice for an autonomous turn) would be silently lost.
