# Message rewriting is implemented by an application-layer prefix fork, not by relying on the SDK's native fork

Message rewriting requires "going back to before a historical user message was sent and resending it with the rewritten content", i.e. forking from a midpoint of the session and discarding what follows. The Claude Agent SDK's `fork_session` is close but not enough: it accepts `up_to_message_id` to truncate at a given message, but `_build_fork_lines` filters out all `isSidechain` entries and reassigns a uuid to every message — the subagent sub-timelines are lost entirely, and the same historical message no longer has the same name in the original session and the branch. `rewind_files` rewinds only files and explicitly does not rewind the conversation (the official docs say verbatim "It does not rewind the conversation itself"). The Claude Code CLI's `/rewind` can rewind the conversation, but that is an internal CLI feature that truncates and replays its own transcript at the application layer, not exposed through the SDK.

We decided to implement a **prefix fork** ourselves at the ArcReel application layer: copy the transcript prefix before the rewrite point (including subagent subpaths) from the DB mirror (`agent_session_entries`) under a new session_id, start a new SessionActor with `resume=new id`, and send the rewritten message as the new session's first input. This is isomorphic with how the CLI implements `/rewind` internally — operating on the transcript store you own — the only difference being that the CLI truncates jsonl while we copy DB rows.

Key constraints and risk containment:

- **The fork point is fixed at a user message boundary**. The previous turn is necessarily fully wrapped up, which guarantees tool_use/tool_result pairing and sidechain integrity; rewriting is forbidden while the session has a pending question card, which exactly avoids moments when the previous turn has a dangling tool_use.
- **Encapsulated as a single service entry point**. "Feeding an assembled prefix to SDK resume" is unofficial usage, and the risk and knowledge are contained in this one place; callers don't know how the prefix is assembled.
- **Entry uuids are copied with the prefix as-is**, without remapping. Unique indexes and the materialized directory are both scoped by session_id, so the same uuid across sessions never meets; the same historical message keeps the same name in all branches, so cross-branch alignment and branches of branches need no extra identity bookkeeping.

## Anchor identity

The rewrite anchor given by the frontend is the uuid of an event log entry, while truncation must land on a transcript entry, and the two belong to two different uuid domains. On the vast majority of entries the two domains have the same name: during lazy generation a user entry takes the transcript entry's uuid directly, and prefix copying preserves uuids, so the identity relation holds recursively for branches of branches. The only exception is the active path — an entry identity has to be given when the POST is accepted, before the SDK has assigned a uuid, so a `user-<hex>` is minted first, and afterwards the echo claim pairs it and records it in the mapping table `agent_session_user_message_links`.

Resolution therefore has two stages, contained in one place, `EventLogService.resolve_user_message_anchor`: the mapping table first; on a miss, verify that this uuid corresponds in the event log to a mainline plain user entry (no subtype, no parent_tool_use_id), and if so adopt it by identity. The fallback does not verify transcript existence — an active-path entry missing from the mapping reaches here and returns a uuid that the transcript has no entry for, and the prefix fork rejects it when slicing. Likewise, the transcript also writes tool receipts as `type:"user"` entries, and those mixed with text cannot be distinguished from real user messages by entry type; the prefix fork rejects them as "carries tool_result" — otherwise the paired tool_use would dangle at the end of the prefix. The two checks have a clear division of labor, and both resolution paths benefit.

## Explicitly not adopted

- **SDK native `fork_session` + prompt override** (the only official approach): even with `up_to_message_id` truncation, dropping sidechains and remapping uuids already rule it out — the former makes the branch lose subagent history, the latter makes cross-branch alignment impossible; and a whole-history fork without truncation would keep the rejected wrong branch in context eating tokens and polluting later generation, degrading correction to appending instructions.
- **Truncating the original session in place**: deleting the transcript rows and event log rows after the edit point and resuming with the same session_id. This breaks the append-only foundation of the event log (`docs/adr/0048`), invalidates the frontend's incremental projector and the SSE `Last-Event-ID` resume semantics along with it, and a backup of the abandoned branch would have to be implemented separately. With the prefix fork these problems don't exist: leaving the original session's data entirely untouched is the backup, and the new session's event log is lazily generated from the transcript by the existing replay-rebuild mechanism of `docs/adr/0048`.
- **Waiting for upstream to implement it**: midpoint forking has long been a feature request upstream with no timeline; correction ability is a real pain point in weak-model scenarios and shouldn't be shelved indefinitely.

## Publishing relies on compensation, not transactions

A fork has to write three things: the new session's transcript prefix, the new session's metadata row, and the original session's superseded pointer. They span two stores, the transcript mirror and session metadata, each committed separately, with no shared transaction boundary — every append to the store is a commit, and transcript rows are visible to session enumeration without depending on the metadata row. Publishing is therefore not atomic, and a mid-way failure is rolled back by the service as a whole: clear the pointer, delete the new session's transcript (including subagent subpaths), delete the new session's metadata row; each step is fault-tolerant on its own, and failures of the cleanup itself are only logged and do not mask the original error. Putting `create` and `mark_superseded` in the same transaction would not change this property; it would only move the window to the transcript side.

Tolerable window boundary: in the instant before rollback, the new session row may already exist while the pointer is not yet set. At that point it is an idle session — no actor, no input. For it to cause actual harm would require "the session list happens to poll at this instant" combined with "the user immediately deletes the session they just saw", which is in the same family as the repository's existing concurrency trade-offs (single-user local deployment). The pointer itself is guarded by a conditional update: `WHERE superseded_by IS NULL` ensures the same session isn't written once each by two forks; a duplicate fork fails at this step and triggers the full rollback.

## Consequences

- The original session is marked superseded and records a pointer to the new session; the session list filters it out, and its data is kept intact; idle eviction works as usual. When a branch in the chain is deleted, the predecessor pointing to it is redirected to its own successor, so the predecessor doesn't stay out of the list forever with a pointer to a nonexistent session.
- `superseded_by` expresses a replacement UX — a session presents only one timeline, and the superseded one exits. Fork lineage is stored separately as `fork_parent_session_id` + `fork_anchor_uuid` (transcript domain), written at branch time and never changed thereafter: the former is a presentation projection that can be rewritten when deletion takes over, the latter is an immutable fact. If branches are someday to be presented as a tree, relaxing the single-child constraint plus presentation-layer work is enough; the data layer needs no migration.
- Rewriting does not roll back file and project-data side effects. The SDK's `enable_file_checkpointing` + `rewind_files` could be a later enhancement, but its blind spots (Bash writes aren't tracked; project data is written via the task queue/DB) mean it can at most be a partial rollback, and it doesn't change this decision.
- Zero changes to the event log and frontend projection contracts: truncation semantics are expressed entirely by "a new session", and the three existing conventions — append-only, unchanged prefix, SSE resume — hold as they are.
