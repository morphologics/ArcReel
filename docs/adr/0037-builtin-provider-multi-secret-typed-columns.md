# Multi-secret credentials for built-in providers are stored in typed columns named after the registry key, not JSON / a child table / concatenation

Kling is the first built-in provider that needs **two secret strings** (`access_key` + `secret_key`, JWT HS256 authentication). `docs/adr/0008` already settled that "multi-field credentials go only through the built-in provider's `PROVIDER_REGISTRY.required_keys: list[str]`", but that is only the **declaration layer** — **storage** of built-in provider credentials is the `provider_credential` table (the multi-credential + manual-active mechanism of `docs/adr/0016`), which has fixed columns `api_key` / `credentials_path` / `base_url`, and `overlay_config()` also only moves these three columns, so there is no room for a second secret. The existing "multi-field" providers are in fact not two secret strings: gemini-vertex is a single service account file path (the `credentials_path` column), and all the others are a single `api_key`.

We decided to **add typed columns named after the registry key to the `provider_credential` table** (`access_key`, `secret_key`, nullable Text), with `overlay_config()` producing config under the column name as-is (`config["access_key"] = ...`), so that **registry key name = form field name = backend constructor parameter name = config dict key** are all the same name end to end, with no column-name ↔ key translation layer; masking reuses `mask_secret` per column. **Explicitly not adopted**: ① concatenating `access_key:secret_key` into a single `api_key` and splitting it again (already rejected by `docs/adr/0008`; breaks the single-key display semantics of `mask_secret`); ② a generic JSON `extra` column (`docs/adr/0016` already considered "concurrent read-modify-write on a single JSON field complicated", and it would need a per-field masking pipeline); ③ a credential-field child table (a new table + join for one provider; the most mechanical work); ④ reusing the KV `ProviderConfig` to store Kling secrets (bypasses `docs/adr/0016`: does not take part in multi-credential active switching, invisible to the ready check, and would need a special case in the resolver).

This is a YAGNI trade-off: currently only Kling needs two secret strings (Volcano visual CV's AKSK is not a built-in provider in this batch, and Vertex is a single file path). A JSON/child-table mechanism for one provider is not worth it; typed columns also continue the existing precedent of "provider-specific typed columns" such as `credentials_path` in the table.

## Consequences

- **Column bloat risk explicitly accepted**: on the `provider_credential` table, `access_key`/`secret_key` are always NULL for every provider except Kling (sparse columns); `api_key` and `access_key` coexist as near-synonymous columns. They are explained by this ADR and the registry declaration, and are not considered dead fields awaiting cleanup.
- **Refactor trigger**: when a **third** built-in provider needing ≥2 secret fields appears (especially with differing field names), upgrading to a generic JSON `extra` column or a credential-field child table should be re-evaluated — that would then be a well-founded refactor, and this ADR becomes superseded.
- **Holding existing boundaries**: follows `docs/adr/0008` (no bypass by string concatenation; multi-field only via built-in providers) and `docs/adr/0016` (credentials in a dedicated table + typed columns, not JSON). Any later PR that wants to switch to JSON/child table/concatenation must deprecate this ADR first.
- **Changes contained in the credential layer**: the model + one additive nullable add-column migration (no backfill; the two columns appear in no `WHERE`), `CredentialRepository.create/update`, `overlay_config`, the credential CRUD routes (request body + per-field masked response + field metadata), and the settings-page credential form (rendered from `required_keys`). Provider-specific connectivity tests (such as Kling's JWT-signing liveness probe) are not in this layer and come with each provider's integration.
