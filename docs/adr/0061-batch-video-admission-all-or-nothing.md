# Admission for batch video generation is whole-batch; only execution results are per-item

Before creating any task, "Generate all / Batch generate" first evaluates the target set of the request once as a whole: it resolves a stable target set and reuses, per target, the same `SpeechComposition` and the same request projection; if any target has re-planning, mixed voicing, missing assets, failure to resolve, exceeding provider limits, in-flight task conflicts, or unconfirmed cross-tier costs, **the whole batch creates zero tasks**. Only when all targets pass is the complete task set created within the same admission operation; a mid-way failure during sequential enqueueing is reported per ID, and tasks already created run as usual. The judgement sits in a two-layer shared seam: `lib/generation/batch_admission.py` is a transport-independent pure fold (conclusion, confirmation tiering, per-unit relaying), and `server/services/admission/video_batch_admission.py` connects the current state (task store, quotes, request projection) to it; the Web batch endpoint and the agent's four video tools all go through this one path, rather than each implementing its own.

**Atomicity of admission and partial success/failure of execution results are two different things, and neither can substitute for the other.** The question before enqueueing is "should this request happen at all" — it is decided by the user's current script, assets, and configuration; admitting item by item would only make the user pay for a batch of half-finished results, and leave them to piece together "why weren't the other few queued". The question after enqueueing is "how did the execution that already happened go" — provider-side failures are naturally independent per item, and success/failure is reported per ID under the `requested / succeeded / failed / blocked` contract (`lib/generation/generation_result.py`). **Enqueueing itself is on the far side of this line**: once admission passes, each task created is a complete, billed unit, and a mid-way failure during sequential enqueueing does not undo them — undoing would make tasks the user has already paid for disappear from the workbench and the conversation, and whatever couldn't be undone would need someone else to clean up. Targets whose turn never came are reported failed per ID with an "enqueue interrupted" problem code; they never created tasks and were never billed, so the next "generate what's missing" fills in exactly these. A blocked batch is relayed with the same contract: every target has its own conclusion, and targets that were fine in themselves carry `generation_batch_admission_withheld` naming who blocked them, so callers don't have to infer it from "it's not on the list".

## Explicitly not adopted

- **Per-item admission, per-item enqueueing (frontend serial loop)**: tasks before the first bad target have already been created and billed, and the user gets a batch of half-finished results plus a failure message; and the judgement is scattered in a browser loop, with another copy on the agent side, so the two sides' approaches are bound to diverge.
- **Abort on the first problem, reporting only the first gap**: in batch scenarios several gaps often exist at once; reporting only the first turns one operation into N rounds of trial and error, each re-resolving the whole script. The whole-batch conclusion requires every target to carry its own stable problem code, reason, current/required tier, and next step.
- **Collapsing a whole-batch rejection into a generic 4xx**: "evaluation succeeded, the conclusion is not to admit" is not a request error. The batch endpoint's three outcomes (admitted / awaiting confirmation / blocked) all return the same envelope with 200, and callers branch on `decision`; HTTP error codes are reserved for genuine request errors. Enqueue interruption is also 200: some tasks have already been created, and collapsing it into a 5xx would make the caller think the whole batch didn't happen.
- **Freezing an execution content snapshot at confirmation**: confirmation binds the target set and options already resolved for this request (including the requested tier per unit), and does not freeze the body text, references, or provider. When the worker starts it still re-projects from the latest intent — a frozen snapshot would silently discard changes the user made after confirming, and would contradict the principle of execution-time predicates sharing a source (see `docs/adr/0056`).
- **Automatically regenerating stale but usable old artifacts**: the target set is determined by the user's selection or "generate what's missing" semantics; treating "old" as "should be redone" would bill repeatedly without the user asking.

## Consequences

- Admission does not read the narration delivery method, nor is it blocked because TTS is unconfigured, missing, expired, or in flight: video is requested at the orchestrated duration, and narration voice-over belongs to the editing stage (`docs/adr/0089`).
- Confirmation of cross-tier costs is displayed aggregated by requested tier (each tier's tier, unit count, and total cost), and tiers with incomplete quotes show no total — a partial sum would under-report the amount the user is agreeing to pay.
- Concurrent submissions are contained by two guardrails: the in-flight tasks of all targets are probed once before admission, and duplicate submissions hit the queue's unique index for deduplication and are honestly reported as `deduped`.
- Enqueueability (whether a `TaskSpec` can be constructed, see `docs/adr/0001`) is the boundary of the target set and precedes the admission judgement: units for which no request can be constructed enter the conclusion with their own problem code, and are not resolved, not quoted, and not silently dropped.
