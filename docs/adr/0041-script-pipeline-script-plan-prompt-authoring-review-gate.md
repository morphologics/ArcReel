# The two-stage script pipeline is split into script_plan for content / prompt_authoring for visuals, with a blocking script_plan→prompt_authoring review gate

> The parts of this ADR about "the script plan as a persistent basis, prompt authoring incremental per entry, entry fingerprints" have been superseded by `docs/adr/0080`; the content/visual layering, pass-through, and content confirmation remain in effect.

Drama / narration scripts go through two stages: script_plan (normalize) organizes the source text into a markdown table of scenes / segments, with spoken content (dialogue / voiceover / `novel_text`) embedded in the free-text "scene description" column, and prompt_authoring (generate-script) then re-parses structured fields out of that free text. Verbatim / source content therefore passes through two LLM gates, "structure → free text → structure": screenplays risk losing fidelity, novels show creative drift, and narration's `novel_text` has been observed to occasionally expand (>10% only warns). And between script_plan finishing and prompt_authoring running, the web side was completely unaware of the intermediate state, so the user could not review or modify it. We decided to cut the two stages' responsibilities cleanly — **script_plan = content** (scene / segment boundaries, characters/scenes/props, drama's `utterances` + `source_text` / narration's structured `novel_text`), **prompt_authoring = visuals** (image_prompt / video_prompt); prompt_authoring **passes through** the spoken / source content already fixed by script_plan and **no longer re-recognizes it**; the free-text column henceforth carries only visual adaptation content (loss is tolerable). And between script_plan→prompt_authoring we introduce a **blocking web review gate**: the structured intermediate state produced by script_plan is visible on the web and can be edited manually / by the agent, and the expensive prompt_authoring visual generation runs only after the user explicitly confirms. Drama, narration, and reference_video share this mechanism (narration does not introduce `utterances`; its spoken content is still `novel_text`; the script_plan of the reference_video generation path is a video_unit breakdown — unit → shots narrative text + duration + references list — likewise a structured JSON intermediate state, which prompt_authoring uses as its sole basis to generate the ReferenceVideoScript). The script_plan intermediate state of all three is rendered by structure and editable on the web, and prompt_authoring is released only after confirmation.

## Considered Options

- **Have script_plan output structure only for screenplays, keep novel creation in prompt_authoring**: small change, but script_plan output would be asymmetric across sources, prompt_authoring would still keep a re-recognition branch by source_kind, and novel / narration drift would not be fixed. The full version was chosen so prompt_authoring is uniform across both sources and double transcription is eliminated at the root.
- **Leave the pipeline unchanged and rely on the scene-level `source_text` anchor to detect distortion after the fact**: detection ≠ prevention; for the "verbatim fidelity" goal prevention comes first; and it does not solve the web side's unawareness.
- **Spectator-style gate (intermediate state visible but prompt_authoring proceeds automatically)**: the user could still miss the review window; since the goal is "able to review and modify", blocking until confirmation stops erroneous content before it enters expensive visual generation.

## Consequences

- The script_plan tool contract changes (`normalize_drama_script` etc. go from "output markdown only" to "output structure"); the intermediate artifact for human review still exists, but is rendered from the structure rather than being a free-text draft.
- script_plan output is always generated and written to disk by server-side tools (normalize / split) through the text pipeline (model source resolved by tier per `docs/adr/0051`); the subagent only orchestrates the calls and does not generate content in its own context.
- reference_video's prompt_authoring prompt (`lib/prompts/prompt_builders_reference.py`) is assembled on the basis of structured unit data and does not parse free text; the web-side script_plan preview and editing are rendered by structure.
- The prompt_authoring (generate-script) prompt / flow uses the script_plan-confirmed structured data as its sole basis — fully preserving the scene / segment boundaries and non-visual fields such as `characters_in_scene` / `scenes` / `props`, `utterances` / `source_text` / `novel_text` already fixed by script_plan, and only generating / overwriting the visual layer (`image_prompt` / `video_prompt`); the branch that re-extracts spoken content by source_kind is removed.
- prompt_authoring is incremental per **entry** for existing scripts: each entry of the script plan gets a content fingerprint (`lib/script/script_plan_entries.py`, using the same canonical JSON + sha256 constructor as the artifact manifest, shared between registration and comparison), and each entry of the script persists the value it consumed (`script_plan_entry_revision`, hidden from the LLM and in no PATCH allow-list). Re-running prompt_authoring sends only entries whose content mismatches and new entries into the prompt and LLM output; unchanged entries keep `image_prompt` / `video_prompt` / `note` / `end_frame_image` / `transition_to_next` / `generated_assets` / `needs_replan` as-is, and entry order and membership follow the script plan (deleted entries are removed from the script; artifact files are not deleted and are naturally judged stale / missing by the artifact manifest per `docs/adr/0062`). Changing one `source_text` therefore rewrites only that one entry, and prompts the user has refined and paid-for artifacts are not overwritten by a whole-episode rewrite. `scope` / `entry_ids` of `generate_episode_script` can explicitly request a whole-episode rewrite or name specific entries; judgements outside that scope are unchanged — the content-confirmation gate blocks the incremental path as well; the script plan's whole-episode fingerprint `script_plan_revision` is kept for compatibility and quick checks; existing scripts (entries without fingerprints) fall back to judging by it and are not falsely reported as invalid because of the upgrade; and when workflow-status computation reads such a script it backfills by it — if the whole-episode fingerprint still matches, that proves this script consumed exactly the current script plan, so each entry is stamped with the same value the assembly exit would stamp (the single constructor in `lib/script/script_plan_entries.py`), and from then on it is incremental per entry. Backfilling only works before the script plan has been changed: once the whole-episode fingerprint mismatches, there is no way to know what each entry consumed, leaving only the whole-episode approach to fall back on, and a whole-episode rewrite would overwrite the visual layer the user refined.
- prompt_authoring pass-through preserves fidelity by engineering means, not by relying on the prompt's discipline: prompt_authoring's LLM output schema contains only `scene_id` (alignment anchor) + visual fields (`image_prompt` / `video_prompt`); the backend merges the visual layer back into the structure confirmed by script_plan by `scene_id` (not list order), and validates that `scene_id` is unique and fully covered; non-visual fields such as `utterances` / `source_text` are not in the LLM output — eliminating drift of non-visual fields via Structured Outputs through engineering rather than prompt discipline. The reference_video path follows the same principle with a different implementation: its prompt_authoring output is a list of writing-layer bodies of the same length and order as script_plan, with no ids to drift; alignment relies on "same unit count + position-wise pairing", and dialogue markers are guarded against rewriting by a verbatim diff (the syntax source of truth for the writing-layer body is the built-in shared template fragment `shared/writing_syntax`).
- A web review state and confirmation action are added between script_plan→prompt_authoring (service / router + frontend); prompt_authoring is triggered by user confirmation.
- Drama's `utterances` / `source_text` data model is in ADR 0040; opening up novel voiceover with restraint is also in 0040 (its content is produced in script_plan and passed through by prompt_authoring).
- The two stages are named **script plan (`script_plan`)** and **prompt authoring (`prompt_authoring`)** (terminology in `GLOSSARY.md`); on-disk file names, episode fields in `project.json`, script metadata fields, and artifact kinds all use these two identifiers, and existing projects are renamed by the v9→v10 schema migration. The only retained items are two tokens of the artifact fingerprint — `SCRIPT_PLAN_BASIS_KIND` (value `structured-content/step1`) and `SCRIPT_PLAN_BASIS_INPUT_KEY` (value `step1_content`) in `lib.artifacts.artifact_provenance`: they take part in computing `basis_digest`, and the manifest stores only the digest, not the inputs, so changing the values would judge all existing script-plan and script artifacts stale. The values are a persistence format and do not change with terminology renames.
