# After a restart, orphan tasks never re-trigger generation; submit-poll tasks resume polling by job_id

Before this decision, `generation_worker.py`, when the worker obtained the lease and this instance had no in-flight tasks, called `requeue_running_tasks()`, throwing all orphan tasks in the DB with `status='running'` (tasks with no corresponding asyncio.Task in the worker's memory, whose only realistic cause is a service process restart — deployment or crash recovery) back to queued so the next claim would rerun them. In a system where "external services are re-entrant and billed by duration" this is a reasonable self-healing strategy, but ArcReel is not that: media generation cost is settled per **provider API call**, so each requeue charges once more; and a single video generation easily costs from several tenths of a yuan to several yuan, so a restart peak (deployment window, container OOM) can rerun dozens of running tasks in a project all at once — in a real user incident on 2026-05-24, the custom-11 video pool with capacity 3 was filled by 3 long-polling Sora tasks, which, combined with the defect at the time that cancelling a running task could not interrupt the asyncio.Task, locked up the whole project (for the current decision on cancellation semantics see `docs/adr/0006-cancel-only-queued-tasks.md`); had the user restarted then, they would have been charged three more times.

We decided: orphan tasks **never** automatically re-trigger generation. The default behaviour is to mark the status `failed` with error_message stating "interrupted by service restart", letting the user decide whether to resubmit. But for **submit-poll video** backends (e.g. Gemini/Ark/OpenAI/NewAPI video — these backends' video calls are "submit a job once + then poll the job_id for the result"), we provide a "resume polling" capability: the Task table gains a `provider_job_id` column (alembic migration), each video backend persists the job_id to the corresponding task immediately after submit; when the worker scans the table on startup, for orphans with a job_id it calls the backend's new `resume_video(job_id)` interface to continue polling, without triggering submit again. No job_id (synchronous backends, or the process died before submit), backend doesn't implement resume, provider returns job expired/unknown — all are marked failed, with error_message distinguished as `[restart_lost]` / `[resume_unsupported]` / `[resume_expired]` (these three are shorthand for families of failure categories; this document and code comments use the same convention; the actual error_message is a structured token from `encode_failure`, subdivided by variant, e.g. `restart_lost_image` / `resume_unsupported_provider` / `resume_expired_detail`, see `lib/generation/task_failure.py`). Vidu's video, although also submit-poll, has polling fully inlined in `generate`, with no separate polling entry point to continue from, and `generate` also doesn't persist the job_id, so it doesn't implement resume; and because it never persists a job_id, its orphans land in the "no job_id" branch of the startup scan triage and are marked `[restart_lost]` (`restart_lost_no_job_id` / `restart_lost_checkpoint_no_job_id`), not `[resume_unsupported]` — `resume_unsupported_provider` only covers the defensive path "has job_id + checkpoint but the provider doesn't support resume" (`NON_RESUMABLE_VIDEO_PROVIDERS`, preventing project configuration drift from misjudging such orphans as resumable). **Image tasks are not in this ADR's resume scope**: the vast majority of image backends are synchronous (request-response, lost as soon as HTTP drops); a few, such as Vidu / NewAPI image, are technically poll-based, but image tasks are short and the benefit of adding image resume is small, so per YAGNI it isn't done; these image orphans uniformly take the fallback "mark failed → user resubmits manually".

## Consequences

- The `requeue_running_tasks()` call site is removed from the worker main loop; the function body is kept but only for unit tests or future manual rescue. Worker startup instead goes through the new `_handle_orphan_tasks_on_start()`, dispatching per the strategy above: resumable ones resume polling, the rest are marked failed.
- "Resume polling" requires backend cooperation. The `VideoBackend` abstract class gains an optional method `async def resume_video(job_id: str) -> ...` (raising `NotImplementedError` by default). Submit-poll backends reuse their existing `_poll_until_complete`; the entry changes from "call after submit" to "call directly with the job_id", without rewriting the main logic. Synchronous backends (Grok image/video, and Gemini/Ark/OpenAI image), as well as Vidu video with polling inlined in `generate` and no job_id persistence, don't implement resume, and orphans are marked failed directly (Vidu orphans land in the `[restart_lost]` triage because they have no job_id).
- From the user's perspective: video tasks being generated at restart (the vast majority use polling) continue automatically and the user notices nothing; image tasks being generated (the vast majority synchronous) become failed and the user needs to resubmit manually. This scope doesn't include a retry UI (confirmed); the user's "resubmit" goes through the existing "click the generate button" path — this is a conscious trade-off, aimed at keeping this PR's scope to the three items of "fix the queue paralysis".
- This ADR goes together with the fact that "GenerationWorker is always bundled with the server main process" (see the module docstring of `lib/generation/generation_worker.py`): under a single uvicorn process, the only cause of orphans is a restart; there is no "false orphan" problem (lease expired but this process is actually alive) caused by lease/heartbeat jitter without multi-worker coordination. If multiple workers are really built in the future, this strategy needs re-examination — specifically, it would need to distinguish "orphans from this just-started process" (genuinely nobody is running them) from "orphans whose other worker is still alive" (the asyncio.Task still exists in another process's memory). This ADR reserves no decision logic for that future scenario.
- The orphan scan only handles `running`. The `cancelling` intermediate state was removed along with "cancellation is only available for queued tasks" (`docs/adr/0006-cancel-only-queued-tasks.md`); the upgrade migration converges leftover `cancelling` rows to `cancelled`, and the orphan scan no longer has that branch.
- Neither overlaps nor conflicts with `docs/adr/0006-cancel-only-queued-tasks.md`: 0006 governs "which tasks can be cancelled by the user" (only queued ones), 0007 governs "what to do with tasks that aren't dead yet after a restart". Restart orphans go to failed or resume, never written as `cancelled` (cancellation is the user's subjective intent; a restart is a system event).
- Do not fall back to requeue to "make restarts less noticeable": that would turn the cost model from "billed per call" into "calls × number of restarts", the user loses out on the bill, and this ADR's cost-semantics protection would be defeated.
- Persisting `provider_job_id` must **complete synchronously** before entering polling — if `submit` has returned a job_id but the DB write fails (e.g. SQLite I/O error, connection dropped), the task must immediately be marked `failed` and **not** enter polling. Otherwise the job keeps being charged at the provider, but ArcReel can neither resume it (job_id not stored) nor cancel it (the worker doesn't know this task is still running), creating an untraceable "ghost task". Implementation path: after `submit`, first commit the job_id in a separate transaction; if the commit fails, raise immediately and the worker's finally marks it failed; only on a successful commit enter the `_poll_until_complete` loop.
- The fail-fast path must be **observable**: the "mark failed" branch triggered by a `provider_job_id` persistence failure writes a structured log starting with the stable token `provider_job_id_persist_failed` (including task_id / provider / the job_id returned by submit / the error reason); operations can search by this token to pick "ghost-task protection triggered" out of the noise of "normal provider failures" — a deployment-time regression (e.g. occasional DB I/O faults) being silently buried is exactly the failure mode this protection aims to avoid. This repository has no metrics infrastructure (no prometheus/statsd/otel dependency), and no counter metric is introduced just for this.
- For both video routes, the resumable identity cannot rely on job_id alone. Immediately before the first provider submit, the task persists a dedicated, versioned and strictly validated execution checkpoint, writing the actual provider in the same transaction. The checkpoint freezes the task/project/script/unit coordinates, the capability bucket, the provider/model/backend, the custom endpoint protocol, the final prompt/duration/request settings, and the logical identity, byte digest and controlled location of the actual provider media. These facts are not written back into the enqueue payload, nor mixed with the task status, job_id or the Artifact Manifest's current pointer; a same-tier reuse hit does not cross the submit boundary and does not create a checkpoint.
- All video orphans are triaged exhaustively by checkpoint/job combination: neither present means an ordinary interruption before reaching the resumable submit boundary; only a checkpoint means submit was attempted but there is no pollable handle, and it is not disguised as resumable; both present and the checkpoint strictly parses/binds means it can resume; a job but with a checkpoint missing, corrupted or with mismatched coordinates means an unrecoverable execution identity. Resume only replays the submit-time request from the checkpoint; the current project is used only to fetch credentials and construct the same backend; drift in provider/model/backend or the custom endpoint fails explicitly.
- The storyboard first/last frames, reference images and voice references actually attached to the provider request are materialised before submit into task-local immutable staging, and the provider only reads those bytes. Staging uses project-boundary checks, byte-digest re-verification, atomic publishing and idempotent conflict checks; failure, cancellation or the task's terminal state only clears this task's provider-media directory, does not follow symlinks/junctions, and does not delete registered paid version history.
- A 413 on the reference payload only allows a downgrade retry when it can be proven locally that the provider has not yet accepted the request; once the job handle has been persisted, or once a black-box call has been entered where "rejected before acceptance" can't be distinguished from "failed after acceptance", any 413 fails as-is and is never automatically resubmitted.
- Normal generation and resume use the same formal file/version registration transaction: the provider first writes a temporary file in the same directory, which is promoted to the formal file only after download, accounting and version registration complete. Version history carries the same checkpoint provenance facts and the standard visual basis; these facts record "how this paid request was produced" and do not claim it is still consistent with the current script/assets.
