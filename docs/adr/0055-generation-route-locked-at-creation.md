# The generation route is locked at creation, and grid is demoted to an assembly option within the storyboard route

`generation_mode` is the project's **generation route**, a required binary value: `storyboard` (storyboard image-to-video) and `reference_video` (reference-to-video). The route is chosen between the two at project creation and cannot be changed afterwards — immutability is guaranteed by structure rather than validation rules: the route field does not exist in the project PATCH model, the episode-level PATCH model, or the agent's project-settings allow-list, so no write surface can change it. Grid is not a route; it is expressed by a separate project-level boolean `grid_storyboard` (default false, meaningful only for the storyboard route, always rejected for the ad content mode), which can be toggled at any time.

**The criterion that distinguishes routes is the input contract fed to the video model**: the storyboard route's input is a single storyboard image (i2v, first-frame driven), the reference route's input is a collection of asset reference images (r2v, reference-image-slot driven). Grid changes **where and how** storyboard images are produced — multiple scenes composed into one N-cell large image generated at once, then cut into each scene's starting storyboard image — after cutting it is still a single image going through i2v, with exactly the same input contract as per-image storyboards, so it is an assembly option inside the storyboard route, not a third route. Industry facts support this: no mainstream model's public API natively accepts "one whole multi-cell storyboard board image" to output a multi-shot continuous video in one go; the only paradigms with consistent terminology across vendors are r2v and first/last frame: the former is this document's reference route; the latter, by input contract, is still i2v (adding a last-frame constraint on top of the first frame), which this document classifies as a keyframe sub-mode within i2v. Product features from various vendors named storyboard (Sora storyboard editor, Flow Scenebuilder, Runway Multi-Shot Recipe, etc.) are product- or orchestration-layer capabilities: they organize content by shot, call the underlying generation capability per shot, and then stitch — they don't change the model API's input contract.

Locking the route means neither episodes nor scripts carry route information any more, and the whole project's axis is fixed by a single field: the script skeleton (declared resolution in `docs/adr/0045`), video capability bucketing and sound-consistency tiers (`docs/adr/0054`), duration linkage constraints, cost estimation, and generation enqueueing all read the project's `generation_mode`, and the read side needs no episode context — the reference-image tier in the duration linkage constraint is the exception: the route only decides whether this constraint applies, and the concrete narrowing is decided by whether the unit actually carries reference images (`uses_reference_images`); estimation and execution both read the project route, leaving no room for divergence of "estimate along one path, execute along another": the WebUI's per-item video generation endpoint likewise fixes its axis by project route — reference-route projects are rejected at the submission entry and directed to the reference-to-video flow, and the reference route for all three content modes uses `video_units`; the storyboard route's enqueue pre-check and execution use the same bucket derived from the project route. Existing projects are re-encoded once by the project migration framework's v4→v5 migrator (`lib/project/project_migrations/v4_to_v5_generation_route.py`): the three-value `grid` expands to `storyboard` + `grid_storyboard=true`, a missing field is filled with an explicit `storyboard`, all episode-level route override fields are removed, and script files are untouched. Existing scripts whose skeleton is in a different family from the project route are explicitly rejected with re-split guidance by the agent's enqueue generation tools and data validation via the route gate `ensure_route_skeleton`; the WebUI's per-item generation endpoint only guards the route (reference route rejected outright), and under the storyboard route locates entries by the script's actual skeleton without going through the skeleton gate; viewing, editing, and project archive export are likewise unaffected, and Jianying (CapCut) draft export takes segments by project route, so a mismatched script yields no completed segments.

## Explicitly not adopted

- **Episode-level route override**: letting one episode take a different path demotes "the project generates along one path" to a per-episode attribute; capability queries, cost estimation, and duration constraints would all need episode context to answer, and the approach the user sees at project level could stay inconsistent with what a given episode actually executes for a long time. The need for mixing across episodes is expressed by "create another project".
- **Scripts carrying a route stamp**: writing the route into the script JSON creates a second source of truth — the script stamp and the project field can diverge, and on mismatch whichever side wins is wrong (following the stamp means letting historical data overrule the user's current configuration; following the project means silently replacing the path this script can actually generate). The route is a project attribute; scripts carry only content and structure; leftover stamp fields in existing scripts are ignored as unknown fields and disappear on regeneration.
- **Mapping on read (compatibility branch)**: mapping the old three values on read to "route + grid switch" would save a migration, but at the cost of every read point repeating the mapping, while the write side could still write old values back, so the mapping could never be deleted. Instead a one-time migration completes the re-encoding, the read side has no mapping branch for the old three values, and the route itself has no default fallback: if missing in an existing project, the migration fills in an explicit value, and the HTTP creation endpoint rejects omission by validating it as a required binary value. The write side keeps one data-layer default — `ProjectManager.create_project_metadata` uses `setdefault` to fill in `storyboard` for callers that bypass the router (tests and internal scripts), ensuring new projects contain both fields explicitly when written to disk and no project.json missing the field is produced; this is a backstop for the creation shape, not a read-time compatibility mapping. Capability resolution sends out-of-table and non-string route values uniformly to the i2v bucket (`lib/config/resolver.video_bucket_for_generation_mode`), as a dirty-data defense against hand-corrupted project.json and queries with no project context, not a compatibility mapping for old values.
- **Grid as a third route**: see the criterion above — it does not change the model input contract. Putting the assembly method side by side with the generation route in the same selector would make an optimization of "how storyboard images are drawn" read as an irreversible project-setup decision, and would give every route-dispatching piece of code an extra branch behaving exactly like the other one.
- **Putting the grid switch in the agent allow-list**: when asked to change assembly, the agent directs the user to the settings page; when asked to change the route, it says the route cannot be changed. The assembly switch determines whether subsequent storyboard images can be batch-produced as grids (the grid entry and cost estimation read `grid_storyboard_enabled`; the per-item storyboard generation entry doesn't check it, and single re-renders work as before); it is an explicit settings action by the user and does not go through a conversational side channel.

## Consequences

- `generation_mode` in the creation request is required with no default; if missing, 422 — there is no path of "didn't choose, silently locked into some route". `grid_storyboard` may be written at creation; for ad projects, `grid_storyboard=true` is consistently rejected in three places: creation, PATCH, and data validation.
- The frontend wizard presents the binary route choice as two cards (no preselection, required), with the grid switch embedded in the storyboard card, and states clearly on the wizard that "the generation method cannot be changed after creation"; the settings page displays the route read-only, and the grid switch can be toggled at any time and only affects subsequent generation, leaving existing content untouched.
- Mismatched scripts produced by existing episode-level overrides (e.g. a `video_units` skeleton under a storyboard-route project) get a structural conclusion and re-split guidance when enqueued for generation via the agent, without silent downgrading; these scripts can still be viewed, edited, and archived/exported; for the boundaries of WebUI per-item generation and Jianying (CapCut) draft export see above.
- First/last frame has its own name in the industry, but by the input-contract criterion above it is still i2v; ArcReel's last frame is currently an optional transition-control means on the i2v path, and whether it deserves to be promoted to separate modelling is outside the scope of this ADR.
