# Node bindings are the only truth of a ComfyUI endpoint: saved explicitly; capabilities are derived only, never stored

A ComfyUI workflow has no official parameterisation convention: in the export, each node has only `inputs` / `class_type` / `_meta.title`, and which input of which node takes the prompt, first frame, size or seed, and which node produces the final file, all has to be inferred externally. The ecosystem has two camps: install dedicated nodes (ComfyUI-Deploy, comfy-pack) and trade `class_type` for zero misjudgement, or zero install relying on field-name and title heuristics (ViewComfy, dramaclaw-gateway); both camps infer afresh on every submission.

We decided that **node bindings are persisted explicitly and are the single truth once saved**: automatic inference at import time (signals from strongest to weakest: `ARCREEL:<slot>` title prefix, externally conventional node families, tracing back from sampler ports, field name × node type whitelist, field name alone, tracing back along links; the highest score wins, and a tie means ambiguity) only produces candidates; the user confirms or changes the choice in the binding editor, and the result is written to the `bindings` section of the definition; at runtime, values are filled by reading the bindings only, with no further inference. Each semantic item has three states: bound, explicitly unsupported, never inferred; unresolved ambiguity cannot be saved, and the prompt and output items cannot be saved unbound. Node ids are not stable after the workflow is edited, so bindings also record node type and title for re-matching on re-import; re-import always enters the binding editor and never saves silently.

**Capabilities are derived only from node bindings; the definition does not store a `capabilities` section.** The first frame / last frame / reference image cap map directly to the three image bindings; `text_to_video` is true only when there is no image binding at all; the audio track depends on whether the output node's `audio` input is connected; an image endpoint without a reference image binding is t2i only, and with one it is i2i only. Model rows of ComfyUI-protocol providers turn off `capability_overrides`: not shown, writes rejected, ignored on read. This is deliberately not isomorphic to the declarative endpoints' three layers of "`capabilities` section + user override + execution-layer reverse gate": those three layers serve "one protocol endpoint attaching multiple upstream models whose model-level differences the protocol cannot express", whereas one workflow is exactly one model; the bindings are already the complete model-level facts, an override layer adds no information, and two sources of truth would only conflict. Users have only one way to change capabilities: change the bindings.

**Explicitly rejected**: (1) **Inferring afresh on every submission** (what both camps' reference implementations do): the same workflow could be inferred to different nodes between two submissions, tasks would not be reproducible, and there would be nowhere to hand ambiguity to the user. (2) **Requiring users to install ArcReel-specific nodes**: zero install on native ComfyUI is a precondition of the integration, and the title prefix convention (changing `_meta.title`, which the ComfyUI backend ignores) is already enough for authors to mark things explicitly. (3) **Storing a capability declaration in addition to the binding table**: two sources of truth; if capabilities disagreed with bindings, the runtime would only fill values according to bindings, and the declaration would become a lie.

## The negative prompt becomes a provider parameter on this channel

ArcReel's negative prompt is rendered as an `Avoid:` line in the body and is not a provider parameter (`docs/adr/0077`). The text encoders of open-source models do not understand negation, so writing the `Avoid` section into the positive prompt only pushes the image in the opposite direction. The ComfyUI endpoint is the only exception: at submission, the `Avoid` section is split out of the body and filled into the negative-prompt node binding; if that binding does not exist, the whole section is dropped and does not go into the positive prompt. Other channels are unchanged.

## Size and duration reuse existing constraints and do not silently ignore user intent

Size is derived from the project aspect ratio × resolution tier via `aspect_size` (`docs/adr/0011`, ratio first), aligned to the step of the bound entry; when no resolution is selected, the short side takes the workflow's literal value. Duration is converted via `frames = round(duration × fps) + 1`; the selectable durations by default contain only the workflow's literal duration, users can add or remove them, and the resulting tiers are stored as a capability override on the selectable-duration dimension of the provider model (see `docs/adr/0104`). When size or frame count has no node binding, that dimension is fixed by the workflow, and the corresponding selector is disabled with an explicit notice, rather than, as in the reference implementations, skipping it when inference fails and producing 5 seconds when 10 seconds was selected without any warning. When there are fewer reference images than bound slots, the graph is modified according to the consumer's shape (removing optional inputs, bypassing pairwise merge nodes) rather than filling with duplicates.

## Duration fixed by the endpoint

When `frames` is unbound or no frame-rate source can be read, the duration dimension does not exist, and `supported_durations` is a legitimate empty set. This exemption applies at all consumption points, not just the UI: script planning borrows a fixed length as the storyboard basis, the request projection does not narrow, does not require duration confirmation, and passes the planned seconds through as-is (the endpoint ignores the seconds in the request body), and the UI's duration control is disabled with the reason explained. Missing any one of these three, a fully configured workflow would be blocked in the name of "model declaration missing". Pre-check and execution are two evaluations of the same judgement, with execution recomputing from current capabilities: this flag is carried to the worker along with the video lane, and when the worker rebuilds projection candidates itself it also skips tier validation based on it; otherwise a request allowed by the pre-check would be rejected again at execution, before submission, for "declaration missing".

## Consequences

- The binding editor is the core UI of the ComfyUI endpoint: inference runs on the server and comes with explanations of the matched signals; the UI only presents candidates and collects choices.
- The field-name aliases, node type whitelists, steps, optional-input and merge-node recognition, and audio-track determination that inference relies on are data, not code, one set per media type.
- Unlike declarative endpoints, capability synthesis for ComfyUI endpoints does not look at the model name, only at node bindings.
- A static override section (`overrides`, changing fixed values inside ArcReel without modifying the workflow itself) is not done in the first phase; the workflow itself is the user-editable base; if added in future, it likewise must not become a second source of capability truth.
