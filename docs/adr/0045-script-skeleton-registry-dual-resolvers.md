# The script skeleton registry is keyed by skeleton kind, and axis interactions are consolidated into declared/forensic dual resolvers

`SCRIPT_SHAPES` was keyed on the single content_mode axis, covered only three skeletons, and was adopted by only 4 consumers; about 19 other files hand-wrote `== "narration"/"drama"` literal branches, several degenerating into a binary "if not narration then scenes" fallback, and skeleton knowledge was stored again in data_validator's four-way if-elif and in script_editor's discrimination chain. The actual consequence had already happened: the binary fallback in the `project_events` snapshot made the entries of two kinds of scripts, ad (`shots`) and reference_video (`video_units`), always empty, so storyboard-level project events were never emitted for these two kinds of projects. The reference_video skeleton not being in the table meant every consumer had to special-case video_units on its own, and an omission silently lost entries — this is a structural cause, not an isolated oversight.

Decision: skeleton knowledge is consolidated into the zero-dependency leaf module `lib/script/script_skeleton.py`, and all consumers dispatch through it.

- **The table is keyed by skeleton kind**, four values `segments / scenes / shots / video_units` (for the domain concept see the "骨架" (skeleton) entry in `GLOSSARY.md`). The key itself is the entry-array key, so table rows reduce to `Skeleton(id_field, chars_field)`; `chars_field` may be `None` — video_units has no per-entry character list (characters exist as entries in `references` with `type == "character"`), and the table honestly declares the absence; a consumer that gets `None` must make an explicit decision (derive it itself or declare it not applicable); no fake field name is provided to make `get()` return an empty value.
- **The content_mode and generation_mode axes are not written into the registry**. Axis interactions are consolidated into two resolver functions: **declared resolution** `(content_mode, generation_mode) → kind`, serving consumers that have only the project configuration at hand, with generation_mode always coming from the project route field (`docs/adr/0055`); **forensic resolution** `script dict → kind` (the current `script_editor.resolve_kind` moves in), serving consumers holding script data, keeping its data-shape-first tolerance ladder — it answers "what does this script look like now", independent of the project's declaration, so existing scripts whose skeleton doesn't match the project route can still be edited and archived/exported. Input contract: when the input is a script dict that may be missing fields, use forensic resolution; declared resolution accepts only project-level mode pairs that have passed validation. Both needs are real and mutually exclusive — per-episode artifact scoring must dispatch by declaration and must not let a leftover array of the other family change the project route, which is the opposite of the editing side's "data first"; neither can replace the other.
- **The agent's generation enqueue tools and data validation additionally pass through a route gate**, which is a third entry point rather than a third resolver: `ensure_route_skeleton(script, content_mode, generation_mode)` first takes the skeleton required by the project route via declared resolution, then allows or rejects based on "is the array the route needs to read present" — a cross-family mismatch (storyboard family `segments`/`scenes`/`shots` ⟷ reference family `video_units`) raises `SkeletonRouteMismatchError` with the structural conclusion and re-split guidance; shape differences within a family and leftover arrays of the other family are allowed as they are. The return value branches by route: the reference route only asks whether `video_units` is present and returns it if so, and leftover storyboard-family arrays get no vote (same approach as cost estimation — the route decides the path, shape gets no vote); the storyboard route returns the forensic resolution's answer. Neither kind of question alone can bear the load on the generation side: using only declared resolution would compute a false success of "all generated" from a nonexistent array, and using only forensic resolution would let historical data overrule the user's route configuration. The gate governs only generation; viewing / editing / project archive export do not pass through it (Jianying (CapCut) draft export separately takes segments by the declared skeleton of the script's content_mode, see `docs/adr/0055`).
- **Declared resolution fails loud**: an unknown/missing content_mode raises `ValueError` (at call time), and `script_shape()`'s historical drama fallback is deleted. Rationale: content_mode at the `project.json` level is already a required and validated field; and the codebase has no consensus on the fallback value (script_shape and data_validator fall back to drama, text_generation and resolve_kind ultimately fall back to narration), so any silent default would mask data corruption and silently rewrite existing behavior elsewhere in the code. Table self-consistency (all four rows present, fields valid) fails fast at import time, using the same technique as `docs/adr/0039`.
- **Narrow table**: behaviors such as validate hooks and edit allow-lists are not written into the registry. Admission threshold: structural facts about the skeleton + no upward dependencies introduced. data_validator keeps its four validator functions and only replaces its home-grown axis-interaction judgement with declared resolution; the edit allow-list is left to follow-up work converging script_editor's dual implementation.
- **Test shape**: a central matrix (table self-consistency, all declared-resolution combinations including reference_video → video_units for all three content_modes, each step of the forensic ladder, fail-loud) + for each consumer containing skeleton dispatch, one exhaustive parameterized assertion iterating the table keys — when a fifth skeleton appears, unhandled consumers fail their tests one by one, rather than repeating the path where ad was silently skipped.

## Explicitly not adopted

- **A `(content_mode, generation_mode)` composite-key registry** — the two axes do jointly determine the declared skeleton, but they only need a compact mapping inside the declared resolver; the structural registry is still keyed by the final kind, avoiding duplicating the same `id_field` / `chars_field` facts for six combinations.
- **An ASSET_SPECS-style wide table (behavior written into the registry)** — ASSET_SPECS's wide table works because its consumers are homogeneous (the CRUD route factory); this table's consumers are heterogeneous (validation/export/billing/events), the four validators have different signatures (shots needs products, scenes needs language), forcing them into one is a false abstraction, and would reverse-couple server-layer behavior into a lib leaf.
- **A graded fallback of "default to narration when missing"** — about half the code historically falls back to drama; picking either side would silently change behavior elsewhere; instead it is exposed with an explicit error.
- **Regex interception tests (CI banning the binary-fallback ternary pattern)** — dropped after review; enforcement of the `docs/adr/0033` ban relies on exhaustive assertions and review.

## Consequences

- At implementation time, the fix for the `project_events` snapshot bug is delivered together with this consolidation (no separate stopgap PR), and ad and reference_video projects then regain storyboard-level event pushes; the `characters` of video_units entry snapshots are derived by filtering `references` for the character type.
- Deleting the `script_shape()` fallback is a behavior change, and the values passed by the existing 4 registry consumers must be checked one by one.
- About 45 content_mode literal dispatches must be handled in three categories: skeleton-structural (migrate to table lookup/resolvers), content-behavioral (script_plan paths, prompt selection — legitimate business dispatch on the content_mode axis, kept), and axis-interaction business rules (such as the reference route skipping storyboard estimation, kept); the classification list, PR slicing, and which scattered dispatch tests to delete or keep belong to the PRD phase.
- This ADR's status=accepted: the design has landed as `lib/script/script_skeleton.py` (`SKELETONS` narrow table + declared resolution `resolve_declared_kind` + forensic resolution `resolve_script_kind` + route gate `ensure_route_skeleton`), and the new names after implementation have been written into the "骨架" (skeleton) entry of `GLOSSARY.md`. A later PR that wants to introduce a composite key, write behavior into the registry, or restore silent fallbacks must deprecate this ADR first.
