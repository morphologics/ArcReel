# The edit timeline is named, can be multiple, follows current, and is formal content rather than an artifact

The final cut and the Jianying (CapCut) draft are always rendered from an edit timeline. An episode can have multiple edit timelines, each with a stable ID and an editable display name. A new one has two possible sources: generated mechanically in the current script order, using each video unit whole, all hard cuts; or copied from an existing one; after that, the agent or the creator edits on it. Each edit appends an immutable revision recording the author, change summary and parent revision; a write declares which parent revision it is based on, and is rejected if that parent is no longer the latest (optimistic concurrency); rollback means appending a new revision based on an old one. Export and rendering must specify an existing edit timeline; episodes without an edit timeline cannot be exported, and no temporary timeline is projected at read time.

**Clips reference video units, not pinned video versions.** The picture always takes the video unit's current video version, and picking a version means changing current. This way "which version does this video unit use" has a single answer across the whole project, unit preview, editing and export do not disagree, and the UI need not present a second set of states such as "the version used by the timeline differs from current". To avoid silently cropping the wrong picture after a version change, a clip additionally records which video version its in/out points were trimmed against; when current is no longer that version, rendering ignores the trim and uses the whole clip, and tells the agent in the read result. Both of these rely on video unit numbers never being reused: storyboard and video unit numbers are only allocated, never reused; each episode records the largest number used, and new, split, whole-generated, content-confirmation-materialised entries and entries restored from the project trash all take new numbers after it, by the same logic as episode IDs in `docs/adr/0096`. After a number referenced by a clip leaves the script it will never point to other content, and it is always reported as deleted on read; new content after redoing a whole episode has new numbers and is not distinguished from old content by version number.

**The edit timeline is not updated automatically when the script changes.** Script changes are deliberate actions by the creator, and the context is usually right there in the current agent session: either create a new edit timeline and re-edit, or patch the old one. When an edit timeline is read, it reports clips that reference deleted video units, and video units present in the script but not used by this timeline; rendering skips deleted references.

**The edit timeline is formal content, not an artifact.** It is a creative decision, not a file produced by paid generation, so it does not enter the artifact manifest's four currency states. The final cut and Jianying (CapCut) draft rendered from it are the artifacts, belonging to "episode + edit timeline + narration version", with the final cut additionally keyed by whether subtitles are burned in; their generation basis records only the content each actually consumes (the edit timeline revision and the referenced material; the without-narration version excludes narration voice-over), currency is judged at read time per `docs/adr/0062`, stale artifacts remain usable, and they are not re-rendered automatically.

**Transitions move from the script into the edit timeline.** A transition describes how two shots in an episode join, which is an editing decision; `transition_to_next` on script entries is removed, and existing non-hard-cut values are simply discarded, not migrated into edit timelines. `segment_break` (scene change point) stays in the script: it decides the reference image chain and grid grouping for storyboard images, and is a generation input, not an editing decision. Transitions use ArcReel's own vocabulary, and each item must correspond to both a Jianying (CapCut) non-VIP preset and an equivalent ffmpeg effect, ensuring the final cut and Jianying draft come from the same source. Transitions do not change the total duration: clips are joined end to end, the timeline's total duration equals the sum of the clips' trimmed durations, and the transition window is centred on the cut point, taking half on each side; this matches Jianying's constraint that clips on the same track cannot overlap, and the absolute positions of narration, subtitles and BGM are therefore unaffected by transitions.

## Explicitly rejected

- **Clips pin video versions, with deviation states such as "newer version available" derived at read time**: this preserves trims precisely, but the same video unit would have two answers at once, "current" and "the version a certain timeline uses", and both the UI and the agent would have to understand an extra layer of state; trading one field, "the version the trim was based on", for safety costs less.
- **Numbers can be reused, with version numbers distinguishing new and old content**: when new content takes back an old number, the old version history has already moved to the project trash and the new content's version numbers restart from 1, matching the version number the old trim was based on; the old clip would therefore be judged ready and the old trim applied directly to the new video, with no warning at all. Recording a content fingerprint on clips for this would make every read path understand an extra layer of identity.
- **When there is no edit timeline, project a default timeline from the script at read time**: this would produce Jianying (CapCut) drafts that belong to no edit timeline, and the final cut's ownership and currency would lose their anchor.
- **Edit timelines automatically following the script's additions and removals of video units**: this would need an extra exclusion list to distinguish "deliberately unused" from "newly added and not yet brought in", and the system does not understand the creator's intent better than the agent in the session.
- **Using a general interchange format such as OTIO as the edit timeline model**: the core semantics of the edit timeline (subtitles, volume, transition vocabulary) have no native schema in these formats, and neither output side has a ready-made adapter; if needed, it can be done separately as an export target.
- **Allowing stylised transitions that only Jianying (CapCut) has, with the final cut degrading to a cross-dissolve**: the two sides would no longer share a source, and the effect the agent sees while editing would not match the final cut.
- **Blocking rendering and export when narration overruns**: the final cut is rendered locally and costs nothing, and the Jianying (CapCut) draft is meant for a human to fine-tune anyway; blocking would only stop the creator from fixing it in Jianying.
- **Automatically pushing overrunning narration back, or automatically adding picture, at render time**: the final cut would deviate from the edit timeline, and the edit timeline would no longer be the single source of truth.
- **Automatically lowering BGM and original audio when narration plays (ducking)**: BGM in commentary videos conventionally uses a fixed volume, and rising and falling with narration sounds erratic; dynamic compression cannot be expressed in the Jianying (CapCut) draft, and a volume envelope derived from narration intervals would add a set of keyframes to the Jianying draft that are not editing decisions, hard to understand and modify during fine-tuning.
- **Editing text, line breaks or deleting individual subtitles on the edit timeline**: subtitles would no longer say the same thing as the narration voice-over and dialogue; text changes belong in the script, with voice-over regenerated accordingly. Line breaking and deletion are fine-tuning, left to Jianying (CapCut).
- **Opening subtitle style configuration (project-level, edit-timeline-level or per subtitle)**: each option opened adds another mapping between the two sides and another round of Jianying testing; style packaging is generative packaging, outside the scope of editing, and in Jianying the whole text track's style can be changed in bulk.

## Consequences

- The per-video-unit presentation model (`SpeechPresentation`) is kept as the material layer for clips, providing picture, narration, subtitle draft and measured duration; it no longer carries transitions.
- Narration is attached to only one clip of the video unit (the first by default), plays from that clip's start, and may extend onto following clips, but should not overlap the next narration nor run past the end of the timeline. Overrun is a warning-level issue that does not block rendering or export and affects only the with-narration version: the final cut is rendered faithfully per the edit timeline, with both narrations sounding at once where they overlap and the part past the end cut off when the final cut ends; the Jianying (CapCut) draft adds narration tracks as needed to separate conflicting narrations so that no track has overlaps, leaving fine-tuning to Jianying. Subtitles follow the narration in the with-narration version; otherwise they keep the source material timing and only the parts within the in/out points are shown. With or without narration is a choice made at render and export time, not written into the edit timeline; only TTS projects can choose with narration (`docs/adr/0089`). When rendering the final cut you can likewise choose not to burn in subtitles; the default is to burn them in; the Jianying (CapCut) draft always has a subtitle track.
- Subtitle text on the edit timeline comes only from the subtitle draft: the edit timeline does not change text or delete subtitles, and does not store subtitle text; corrections go back to the script, and after the subtitle draft is regenerated per the artifact lifecycle (`docs/adr/0062`), the edit timeline picks up the new text without needing changes itself. Subtitle style is fixed and built in, is not an editing decision, and neither the agent nor the creator can change it: taking Jianying's existing style as the baseline, position and font size are chosen by aspect ratio, the final cut gets as close as possible, and pixel-level parity between the two sides is not required. When subtitles overlap in time (narration overrun, or narration extending onto a clip with dialogue), the final cut leaves it to libass's collision handling to push the later one away; the Jianying (CapCut) draft adds subtitle tracks as needed so that no track has overlaps, with the added tracks shifted up as a whole by a fixed distance. Overlaps are not reported separately; the narration overrun and original-audio collision notices that cause them already cover them. The read result pre-checks the subtitle font for missing glyphs and reports them as warnings.
- BGM sits on the edit timeline as an independent audio track, placed by absolute time, with only one track playing at any moment. Volumes on the edit timeline are always static values: clips carry original audio volume, BGM clips carry volume and fade in/out, and rendering and export write them as-is, with no ducking and no derived volume envelope. When a new clip is created without an original audio volume, the default is taken from the speech owner: voice-over units have the whole track lowered, serving as an ambient bed under the narration, while dialogue and no-voice units keep their original volume. When BGM is registered, it is normalised to a common baseline by measured loudness, and BGM clips' default volume and fade in/out take fixed values. The system does not rewrite the volume of existing clips. When narration extends onto a dialogue clip or a clip whose original audio is not lowered, the read result warns that it may collide with the original audio; like narration overrun, this warning affects only the with-narration version: the without-narration final cut and Jianying draft do not mix in narration audio, so there is no collision.
