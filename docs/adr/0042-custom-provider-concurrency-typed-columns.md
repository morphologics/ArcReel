# Custom provider concurrency limits are stored in typed columns named per lane, not JSON / kv / a child table

Concurrency limits for built-in providers already go through the `image_max_workers` / `video_max_workers` / `audio_max_workers` config keys of `provider_credential` / `ProviderConfig`, loaded by `CapacityTable.from_db` and projected per lane into a capacity table. Custom providers (the `custom_provider` table, runtime id of the form `custom-{id}`) previously always got the global default in `from_db`, so users could not set a separate concurrency limit for a particular custom provider — asymmetric with built-in providers.

We decided to **add typed columns named per lane to the `custom_provider` table**: `image_max_workers` / `video_max_workers` / `audio_max_workers` (nullable Integer), where `NULL` means "not set → use the global default". When `CapacityTable.from_db` loads a custom provider it reads each column, and `NULL` falls back to the global default (replacing the previous always-global-default logic); projection still goes through `_lane_limits`, reusing the semantics established by the three-tier fallback slice. Custom providers are not in the built-in registry `PROVIDER_REGISTRY` and have no "provider-declared default" middle tier, so their fallback has two tiers (user column value → global default) rather than the built-in providers' three. **Explicitly not adopted**: ① a generic JSON `extra` column (would need a per-field read-modify-write and validation pipeline; concurrent read-modify-write on a single field is complicated, which ADR 0016 already disliked; not worth it for just three scalar limits here); ② the KV config table (custom provider configuration is not part of `ProviderConfig`'s KV system for preset providers; reusing it would need a special case in the resolver and bypass this table's single source of truth); ③ a concurrency-field child table (a new table + join for three scalar limits; the most mechanical work).

This is a YAGNI trade-off: currently only integer limits for three fixed lanes are needed; the field set is stable and symmetric with built-in providers, and typed columns are direct, indexable, and have the simplest migration — isomorphic with ADR 0037 (multi-secret typed columns for built-in providers), following the same rule of "prefer typed columns when the field set is known and stable, and leave JSON / child tables for genuinely dynamic cases".

## Consequences

- **Column sparsity explicitly accepted**: the three columns are always `NULL` for custom providers without configured concurrency (most rows); explained by this ADR and the two-tier fallback comment in `from_db`, and not considered dead fields awaiting cleanup.
- **Refactor trigger**: when custom providers need per-model concurrency, or the lane dimension changes from three fixed lanes to dynamically extensible ones, upgrading to a JSON `extra` column or a concurrency-field child table should be re-evaluated — that would then be a well-founded refactor, and this ADR becomes superseded.
- **Changes contained**: the model + one additive nullable add-column migration (no backfill; the three columns appear in no `WHERE`), pass-through in `CustomProviderRepository.create_provider` / `update_provider`, the CRUD schema (POST / PUT request bodies + response echo), wiring custom providers into `CapacityTable.from_db`, and three nullable number inputs in the settings-page form. The SlotTable occupancy ledger, lane isolation, and reload mechanism are not changed; per-model concurrency is not introduced.
- **Holding existing boundaries**: follows the three-tier fallback slice (custom providers are its two-tier special case) and ADR 0037 (typed columns when the field set is stable). Any later PR that wants to switch to JSON / kv / a child table must deprecate this ADR first.
