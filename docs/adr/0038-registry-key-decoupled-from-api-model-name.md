# Amphibious multimodal models are decoupled with a registry alias key + `api_model_name`, rather than changing the registry key to a composite `(model_id, media_type)`

`PROVIDER_REGISTRY[provider].models` uses the model_id string as its unique key; one model_id maps to one `ModelInfo` and one `media_type`. This key serves three roles at once: the **UI / persistence identifier** (the frontend model picker, `"model"` in `project.json`, the `ApiCall.model` column, and API request bodies all use this bare string), the **billing / capability lookup key** (`lib/billing/pricing/lookup.py` and the various capability lookups match it exactly), and the **model name sent to the provider API**. Having three roles share one globally unique string breaks down for "amphibious multimodal models": Kling v3-omni's image and video are **both called `kling-v3-omni`** in the Kling API, but a single key with a single `media_type` cannot hold two modality entries with the same API name.

We decided to **add `api_model_name: str | None = None` to `ModelInfo`** (default `None` falls back to the key name; zero impact on existing entries), stripping "the API name sent to the provider" out of the "internal unique key" role: the image entry uses the **alias key** `kling-v3-omni-image` (`api_model_name="kling-v3-omni"`), and the primary key `kling-v3-omni` belongs to video; the image backend sends `api_model_name or key name` (the video backend, because the only amphibious entry occupies the primary key and the key name is the API name, has no need for an alias yet and currently still sends the key name directly), and billing and capability lookups still use the registry key name. The two entries' `display_name`s are distinguished individually (`可灵 V3-Omni（图像）` (Kling V3-Omni (Image)) / `可灵 v3 Omni` (Kling v3 Omni)), so the synthetic key does not leak into the UI.

**Explicitly not adopted**: changing the registry key to a composite `(model_id, media_type)`. A composite key does fit reality better at the registry layer (one API model with two modalities = two rows sharing a model_id, needing neither an alias key nor `api_model_name`), but it touches the first two roles, which model_id handles fine: model_id is a **cross-layer identity token** — frontend selection / `project.json` / `ApiCall.model` / API request bodies / pricing lookups are all **bare strings without an accompanying `media_type`**. A composite key would push the cost onto all of these boundaries — in particular the cost snapshot (`docs/adr/0009`) has only the model string at the moment of finish, historical `ApiCall` rows cannot recover `media_type`, and the rate dicts inside the pricing module are also keyed by model string and would be forced to become composite too. Amphibiousness only conflicts with the "API name" role of model_id; imposing a composite-key tax on the whole system for it, with only one amphibious model in the entire registry, is disproportionate. Principle: **decouple only the conflicting role; leave the two unaffected roles alone.**

## Consequences

- **Backward compatible**: existing models have `api_model_name=None` and fall back to the key name, with zero behavioral change; new non-amphibious models need not care about this field.
- **Asymmetric backend adaptation**: currently only the image path consumes `api_model_name` (`KlingImageBackend` accepts the parameter and uses it as the API name); the video backend has no `api_model_name` parameter yet and sends the key name directly. That is fine today — the video side of the only amphibious entry, v3-omni, occupies the primary key, and the key name is the API name; but if a future amphibious model needs its **video** entry to use an alias key, `api_model_name` support must first be added to the video backend, otherwise the key name would be sent by mistake. This is prerequisite work for the "refactor trigger" below.
- **Synthetic-key smell explicitly accepted**: `kling-v3-omni-image` is a registry-internal identifier that does not exist in the provider's world; it is explained by this ADR + hidden behind `display_name`, and is not considered a dead key awaiting cleanup.
- **Refactor trigger**: when amphibious multimodal models multiply and the "alias key + `api_model_name`" boilerplate becomes uncomfortable, re-evaluate the composite key `(model_id, media_type)` or another root fix — that would then be a well-founded refactor, and this ADR becomes superseded.
- **Same-family convergence**: follows `docs/adr/0009` (pricing merged into `ModelInfo`, looked up by key) and `docs/adr/0013` (capability declarations converged at model level) — all three answer "what does the registry key / `ModelInfo` carry". This ADR is the third responsibility split applied to the registry key: separating the "external API name" from the "internal unique key".
