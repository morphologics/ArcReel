# Custom call endpoints use a declarative definition, unifying the "JSON in/out + submit/poll" family

Previously the only way to integrate a new video or image protocol was to change source code: `lib/custom_provider/endpoints.py` hard-coded all built-in call endpoints, and a new protocol required a new backend class, registering an endpoint key, adding inference rules, and i18n. Yet the protocols of long-tail aggregators and relay sites belong to the same family — JSON request in, JSON response out, poll after submit — differing only in field naming and value paths, so writing Python for each one is unsustainable. The image side has such providers too: paths and fields follow the OpenAI style, but the semantics are an async task polled after submission, which the synchronous OpenAI-compatible image endpoint can't handle.

We decided that **custom call endpoints use a declarative definition**: a JSON container (`kind: declarative`, file-level `schema_version`); requests use a JSON structural template + `{{ }}` placeholders (a whole string consisting of a single placeholder keeps the native type) plus a few fixed constructs (`$each` to spread fields, an object-level `$when` guard, an optional `result` second-fetch section); response extraction uses priority arrays in a restricted subset of RFC 9535 JSONPath, and status and enum mappings are plain dictionaries; the media type is declared by the definition (`media_type: image | video`, defaulting to video); no general template engine such as Jinja2 is introduced. The aim is not to express every protocol, but to be **the unified form of the "JSON in/out + submit/poll" family**: downward it covers long-tail aggregators and relay sites (8 of 10 sampled can express the full chain), and upward it absorbs HTTP-style built-in backends that can be expressed as a whole into declarative definitions shipped with releases (first batch newapi / v2_video_generations / minimax, with the corresponding Python paths deleted in the same PR that ships them). Inexpressible protocols — signature-based auth (JWT / SigV4), routing by asset, cross-list pairing, SDK-style integration — stay as Python built-in endpoints, and the format is not extended for them.

**Explicitly not adopted**: ① **Abandoning the declarative approach under a general coverage yardstick** — measured by "expressing every protocol", declarative coverage is only 50–60%; but with the scope drawn around the family, coverage was confirmed by acceptance testing in which 22 definitions replicated 8 HTTP-style built-in backends, and the debugging disadvantage is taken up by the endpoint test's three modes (preview request / validate response / test connection) and the validator shared with saving. ② **Runtime Python plugins as the integration form for custom protocols** — plugin loading, execution, and trust model are a separate topic (#872), for which the container reserves a slot via the `kind` field; what the declarative approach absorbs is the part that could be expressed as a whole, and it's not mutually exclusive with plugins. ③ **Extending the format for inexpressible constructs** (signature auth, per-asset branching, multipart, etc.) — under the principle that optional constructs are "invisible if not written", each extension is admitted based on real needs of the external long tail, not the pursuit of format completeness.

## Image definitions

Media type is orthogonal to `kind`: `kind` distinguishes the definition's form (protocol convention or workflow); images and video share the same declarative format and runtime, and ComfyUI endpoints likewise declare the media type in the definition (see `docs/adr/0081`). Image definitions differ from video definitions only in the following:

- **Capabilities declared explicitly**: an image definition states t2i / i2i capability and the reference image limit, and one definition may declare both; declaring i2i requires a reference image input. Gating follows `docs/adr/0015`, with no degradation. Capabilities are not inferred from inputs as ComfyUI does (see `docs/adr/0082`): video definitions already declare capabilities explicitly, so this stays consistent within the same `kind`; an inference rule like "whether the reference image input is required determines t2i / i2i" is too obscure for whoever writes the definition.
- **Template variables and input sources are split into sets by media type**: image definitions can only use prompt, model, aspect ratio, resolution, width/height, seed, and reference image inputs; writing duration, audio, or first/last frame errors at save time rather than rendering empty. The edit instruction for image editing goes through the prompt, with no separate variable.
- **Artifacts can be taken as URL or base64**: artifact extraction can specify a URL path, a base64 path, or both, and when both are given the URL is taken first. base64 is still a field in the JSON response and doesn't go beyond "JSON in/out". Video definitions take only URLs; revisit when a real case appears.
- **Only one image is taken at a time**, and the reference cost is computed at the per-image price of the model row, the same basis as ComfyUI images (see `docs/adr/0081`).
- **No resume**: only video has a resume protocol in the system; image tasks in flight when the service restarts are recorded as lost on restart, the same as ComfyUI images. Image tasks usually finish within tens of seconds, and building a resume protocol for them isn't worth it.

Assets for both media types are only inlined as data URI / base64, with no public URL hosting; all three endpoint test modes are available for both.

## Two deviations in storage

- **The definition itself is stored whole as JSON**: the new table `custom_endpoint` uses one JSON column `definition` as the single source of truth. This doesn't conflict with ADR 0042's "prefer typed columns when the field set is stable" — the definition evolves with `schema_version` and its field set is unstable, which is exactly the "genuinely dynamic" case 0042 leaves to JSON; typed columns only extract read-only mirrors the DB layer needs without parsing JSON (`kind` / `schema_version` / `media_type` / `display_name` / timestamps), derived from the definition at write time, not constituting a second source of truth.
- **Deletion is refused when referenced by model rows**: deleting a custom call endpoint referenced by `custom_provider_model` returns 409 with the list of references. This is the repository's first "refuse to delete" precedent, coexisting with rather than replacing the existing "delete + clean up dangling references" path: model rows carry the user's manual configuration (pricing, capability overrides), cascading deletion would lose the user's work, and leaving dangling references would defer the error until generation time. Referential integrity is guaranteed by service-layer counting, without an FK constraint — a 409 needs to return the reference list, while a constraint can only throw an `IntegrityError`, and the delete path has to look up references first anyway.

## Consequences

- Built-in call endpoints now have two implementation forms: a Python backend, or a declarative definition shipped with releases (`lib/custom_provider/builtin_endpoints/*.json`, entered into the registry at import time, keeping built-in keys, not stored in the DB); when the implementation behind a key is swapped, in-flight tasks are taken over by the declarative runtime by key, with no version lock.
- The default path for adding an HTTP-style submit/poll protocol becomes "write a definition" (UI or import, zero code), falling back to Python only once it's confirmed inexpressible; the catalog distinguishes implementation forms with `kind: python | declarative`.
- If a later PR wants to extend the format for inexpressible constructs, or have the declarative approach swallow SDK-style backends, it must first revise the family boundary of this ADR.
- The integration-approach selection in chapter 7 of `docs/research/arcreel-video-api-protocol-research.md` is governed by this ADR (that document carries a revision note).
