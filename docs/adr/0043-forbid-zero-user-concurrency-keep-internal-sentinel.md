# Provider concurrency limits forbid 0 as user input (require ≥1 or blank); 0 is kept only as the internal unsupported-lane sentinel

`0` plays two conflicting roles in the concurrency system: inside CapacityTable, a lane capacity of `0` is the sentinel for "this provider does not support this media" (`_lane_limits` projects unsupported lanes to `0` according to `media_types`, and the worker fast-fails with `mark_failed("provider_unsupported_media")` on `if cap <= 0`); while the user-configurable concurrency limit fields (built-in via `_validate_value`, custom via the API's `ge=0` + DB `CHECK >= 0`) previously all **accepted** `0`. A user entering `0` (misreading the "default" placeholder, or thinking `0` = unlimited) would silently shut that lane down, after which every task reports "the provider does not support this media" — a silent footgun whose failure message doesn't match the cause. The registry's factory default `ProviderMeta.default_concurrency` has long required `>= 1`; only user values let `0` through, so the two sides were asymmetric.

We decided to **remove `0` from valid user input**: all user input layers (frontend form, custom provider API `Field(ge=1)`, built-in `_validate_value`'s `parsed < 1`) and the DB CHECK (`>= 1` on the three `custom_provider` columns) uniformly require `>= 1`; blank / `NULL` still means "fall back to default". `0` is kept only as CapacityTable's internal "this lane is unsupported" sentinel and is not exposed to users. Since custom provider concurrency (ADR 0042) has not yet been released, tightening the DB CHECK **directly rewrites its add-column migration** (`>= 0` → `>= 1`, constraint name `_non_negative` → `_positive`), with no new migration and no data backfill (`0` has no automatic source; the only source is user input, and blocking it at the door means it is no longer produced). The runtime `if cap <= 0` / `_lane_limits` / `provider_unsupported_media` are all left untouched — from now on `0` can only come from "this provider genuinely does not support this media", so the failure code's semantics are exactly right.

**Explicitly not adopted**: making `0` a first-class "disable this lane" value. The provider is bound at enqueue time; `0` would not reroute the task to another provider, it would only fast-fail, so it cannot implement "graceful disabling"; the three-tier fallback already expresses "use the default" cleanly with blank / `NULL`, so `0` need not carry a second meaning; the honest way to not use a provider for a lane is to not choose it for that lane. If "disable a lane of a provider" becomes a real requirement in future, a separate explicit switch with an honest failure code should be added, rather than overloading `0`.

## Consequences

- **The two roles of `0` are fully separated**: the user contract layer "a concurrency limit is an integer ≥1 or blank" and the internal "capacity `0` = this lane is unsupported" no longer share one user-reachable value; the `SlotTable` docstring is updated to note the user contract surface as well.
- **Rewriting a migration already merged into main**: other worktrees / dev DBs that already ran the old (`>= 0`) version with `alembic upgrade head` will not have the CHECK tightened automatically (alembic does not rerun applied revisions), and need `downgrade -1 && upgrade head` or a rebuilt dev DB. Since it is unreleased and `0` has no automatic source, this is harmless in practice; it is a deliberate trade-off that "unreleased migrations may be rewritten in place", and this technique must not be used after release.
- **Changes contained**: validation in three input layers + DB CHECK on three columns + in-place tightening of the original migration + i18n copy (backend `max_workers_must_be_positive_integer`, frontend `正整数` (positive integer) and help text) + corresponding tests. Runtime scheduling, SlotTable, lane isolation, and reload are all untouched.
- **Holding boundaries**: unified with the registry's `default_concurrency >= 1` rule; follows ADR 0042 (custom provider concurrency typed columns).
