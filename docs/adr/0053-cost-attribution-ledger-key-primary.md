# Cost attribution treats the accounting key as strong evidence; the ID prefix is only a weak fallback clue

Cost aggregation needs to attribute each actual payment (cost snapshot) to an episode and a script entry. What takes part in attribution are image / video / audio calls **that wrote an accounting key** (for the key allow-list see `media_generator.segment_id_for`). Three kinds of spending are not included: text calls write no key and are summarized separately on the usage statistics side by provider and call type; asset images (character/scene/prop/product) have an empty key and are split by artifact path into project-level per-asset-type details, with anything that can't be split going into the project-level "unassigned"; historical video / audio accounting keys from before the `segment_id` column was back-filled are likewise empty, have no episode attribution clue, and go directly into the project-level "unassigned".

The accounting key is the resource ID frozen in the `segment_id` column of the call record, and takes three forms:

- **Script entry ID** (main form): the value varies by skeleton (`segment_id` for `segments`, `scene_id` for `scenes`, `shot_id` for `shots`, `unit_id` for `video_units`); the canonical format is `E{episode}S{n}` / `E{episode}U{n}`, and in existing data, sub-entries produced by insertion and splitting carry a `_{sub-index}` suffix (e.g. `E1S01_1`), which are also valid keys; on the reference route all three content modes attribute costs directly to self-contained `video_units` entries
- **Grid image ID** (`grid_{12 hex digits}`): on the grid-to-video path one grid image carries several storyboards, and accounting lands on the grid. It is claimed by reverse lookup via the script entries' `generated_assets.grid_id`, then split evenly across the number of entries the grid covers; it has no `E{episode}` prefix, so the prefix fallback below does not apply

These IDs are neither guaranteed globally unique nor guaranteed consistent with the episode they are in — scripts are editable and can be replaced wholesale; before `docs/adr/0090`, unit rebuilding reused numbers, so existing accounting may still point at reused numbers. We decided: the strong evidence for attribution is this frozen key. Estimate aggregation first sums all cost snapshots under the same (accounting key, cost type) by currency into one amount (different currencies are listed separately, not converted and merged), then consumes the whole amount on the basis of "within one estimate, each (accounting key, cost type) is claimed only once" — deduplication guards against the same money being counted by multiple script entries, not against discarding any call records; historical accounting that cannot be claimed by the current script is not discarded, but is uniformly presented in a separate "unassigned" line: the project-level unassigned is a catch-all bucket that receives every unclaimed amount; among these, those whose ID prefix parses to an episode number and whose episode is still in `project.json` are additionally shown in that episode's unassigned (those that fail to parse, keys without a prefix such as grid IDs, and those whose episode has been deleted appear only in the project-level one). The episode-level copy is a per-episode view of the same money, not additional spending — to compute the project total, read the project-level bucket only, and do not add the episode-level buckets on top.

The rejected alternative was to introduce a globally unique identity for script entries (a schema-level change): it would cure ID-reuse mismatches at the root, but would require migrating all existing accounting and script data, out of proportion to the benefit. Therefore IDs being non-unique and not guaranteed consistent with their episode is a **known and accepted limitation** — improvement suggestions based on "validate ID uniqueness/prefix consistency before attributing" do not hold, and would misjudge real spending as unassigned (or vice versa); such comments recurring in reviews should be rejected by citing this ADR.
