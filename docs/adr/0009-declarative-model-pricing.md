# Billing pricing becomes code-level declarative: pricing merged into `ModelInfo`, dispatched by `kind`, with no runtime DB+UI price editing

Before this decision, ArcReel's `CostCalculator` (`lib/billing/cost_calculator.py`) wrote each provider's per-modality rates as **scattered class-attribute dicts** (`IMAGE_COST` / `VIDEO_COST` / `ARK_VIDEO_COST` / `GROK_TEXT_COST` / `OPENAI_IMAGE_TOKEN_COST` and a dozen more), and `calculate_cost` used a long chain of `if provider == X` to manually route to the corresponding per-shape calculation function, with USD/CNY currencies mixed into each function. When adding a new built-in provider, if no explicit branch was added for it, video would **silently fall back to the Veo rate table** and be billed at the wrong unit price. Provider prices fluctuate with promotions; rate fields should be configurable, not hard-coded.

During evaluation one key fact was confirmed: **ArcReel's generation costs are snapshotted**. `finish_call` calls `calculate_cost` only once, at the moment the call completes, freezing the result into `ApiCall.cost_amount`; all usage/cost aggregation reads the frozen values and does not recompute. So the requirement to "keep rates for retired models for historical billing" doesn't hold — past records don't depend on the rate table. We also compared LiteLLM's approach: it uses a single data table indexed by model name, with each model entry carrying metadata, context window and pricing together (`input_cost_per_token` / per image / per second etc.), dispatching calculation by `mode`; pricing and model metadata are **not separated**.

We decided to make billing **code-level declarative**, and **not** to do runtime DB+UI price editing. Specifically: ① pricing data is **merged into each model entry of `PROVIDER_REGISTRY`** as the `ModelInfo.pricing` field (a single source of truth per model, aligned with LiteLLM); ② the type definition of `Pricing` and the calculation **strategies selected by `kind` tag** (`per_token` / `per_image_flat` / `per_image_by_resolution` / `per_image_openai_token` / `per_second_matrix` / `per_token_video` / …) **live in a separate `lib/billing/pricing` module**, separating the "calculation concern" from model declarations; ③ `calculate_cost` changes to **dispatch by `pricing.kind`** rather than `if provider == X`; ④ model retirement is marked with `ModelInfo.hidden` (removed from UI dropdowns, entry kept so that the edge case of "retired after enqueue, before finish" can still be priced), with no separate historical rate repository; ⑤ **fully migrate** all existing built-in providers (Gemini/Ark/Grok/OpenAI/Vidu) to the new system, a pure refactor with zero behaviour change, backstopped by full pytest comparison against old values. Runtime price editing (changing prices for promotions without redeploying), if really needed, is a separate future epic that this ADR does not presuppose.

## Consequences

- **`calculate_cost` becomes thin and extensible**: the `if provider == X` routing chain is replaced by `kind` dispatch. Adding a built-in model = writing one declaration in its `ModelInfo.pricing` + reusing an existing `kind` strategy, **no longer touching `calculate_cost` logic, no longer adding provider branches**, eliminating at the root the regression class "a new provider's video silently priced at Veo rates".
- **`pricing=None` is an explicitly declared exception, not the silent fallback being eliminated**: Agent Plan-type packages (`ark-agent-plan`) don't publish per-call rates, and their registry entries deliberately don't declare `pricing`; for "a known model whose pricing is None", `lookup_pricing` prices at the generic Gemini default rate and writes a debug log (`lib/billing/pricing/lookup.py`). The difference from the regression class this ADR eliminates (a missing provider branch causing an unknown model to be silently priced at Veo rates) is that the former is on record and visible in logs, while the latter is accidental routing.
- **Changing a promotional price = changing the declaration + redeploying**: this is a conscious trade-off. The cost is not supporting non-technical people changing prices at runtime; the benefit is not needing the whole surface of DB schema/migration/repository/settings page UI/trilingual i18n/validation. ArcReel is self-hosted, redeploying is routine, and costs are only used for cost estimates and internal accounting (not external billing), so the precision requirement is "not wildly off" rather than "adjustable in real time".
- **Historical rates need not be stored in the database**: because costs are snapshotted, past `cost_amount` values are already frozen, and pricing data only needs to cover **currently selectable** models. Retired models don't enter the pricing data; `ModelInfo.hidden` covers the rare edge case "retired after enqueue, still needs pricing at finish", with no need to maintain a graveyard of historical rates.
- **Custom provider prices are not merged into `ModelInfo`**: custom provider unit prices are filled in by the user in the DB (`CustomProviderModel.price_input/output/currency`) and are not static; `calculate_cost` keeps the `is_custom_provider` early branch going down the parameterised path (the caller pre-queries the DB and passes them in). This is consistent with [ADR 0008]'s "custom provider credentials/configuration are carried by the DB, not in the static registry".
- **Pricing and capability declarations are co-located but with layered responsibilities**: the data is merged into `ModelInfo` (single source of truth, a promo change visible in one place), but the **types and calculation strategies** of `Pricing` are in the separate `lib/billing/pricing` module — data is declarative, logic is unit-testable, and the two are not coupled in the single `cost_calculator` file.
- **`ModelInfo` is extended incrementally, not redesigned**: this ADR only adds two fields, `pricing` and `hidden`, to `ModelInfo`, and **does not** touch existing minor flaws such as the duplication between `capabilities: list[str]` and the `VideoCapability` enum (left as a separate issue, to avoid scope creep).
- **Advanced billing shapes such as tiers/caching add `kind`s as needed**: the first batch of `kind`s covers all existing billing shapes to guarantee zero behaviour change; Qwen's input-volume tiered pricing is initially priced at the 0-128K base tier unit price (flat), with tier modelling as an extension point for a later `per_token_tiered` kind, not introduced in this pure refactor.
- **Complementary to ADR 0008**: 0008 draws the boundary "the credential model is not polluted by protocol shape", 0009 draws the boundary "billing data is not polluted by scattered hard-coding; pricing shape is decided by `kind`, not provider"; both make the "determined at runtime vs declared at startup" division clear. Any later PR that wants to introduce runtime DB+UI price editing, or move pricing back into scattered dicts, must first deprecate this ADR.
