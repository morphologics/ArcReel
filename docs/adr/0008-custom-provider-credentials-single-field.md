# The custom provider credential model is fixed at `api_key` + `base_url`; multi-field credential protocols can only go through built-in providers

ArcReel's `CustomProvider` ORM (`lib/db/models/custom_provider.py`) currently exposes only two credential fields for each provider created by users at runtime: `api_key` (a single string, masked by `mask_secret`) + `base_url` (HTTP entry point). A contemporaneous survey of video API protocol adaptation found several protocols with "native multi-field credentials": Kling's official API uses JWT HS256 (`access_key` + `secret_key` dual keys, 30-minute token expiry), Vertex AI Veo uses a service account JSON file (`credentials_path`, plus project_id / OAuth2 scopes), and Volcengine visual.volcengineapi.com visual CV uses AKSK + canonical request + HMAC signing. If these protocols were exposed as-is as endpoints for custom providers, the CustomProvider credential model would have to be extended to multiple fields (candidate options: add an `extra_credentials: JSON` field, or add dedicated fields such as `api_secret` / `service_account_json`).

We decided **not** to extend the custom provider credential model. `CustomProvider` is permanently fixed at the single `api_key` field + `base_url`; any "native multi-field credential" protocol can **only** be integrated through built-in providers (`PROVIDER_REGISTRY.required_keys: list[str]`, which already supports multiple fields, e.g. `gemini-vertex.required_keys=["credentials_path"]`, and Kling supports choosing between single-key Bearer and dual-key JWT with `credential_groups=[["api_key"], ["access_key","secret_key"]]`). The compatible path for users connecting a multi-field protocol through a relay is **the relay doing protocol translation** — the relay handles multi-field authentication on its own server and exposes a Bearer `api_key` + the relay's `base_url` (supporting evidence: Kling relays commonly pass through Kling's native schema on `/kling/v1/videos/{text2video|image2video|multi-image2video}` paths, but fold authentication into a single Bearer key). What the endpoint closure sees is always a single api_key. This is the boundary decoupling the credential model from protocol shape.

## Consequences

- **The credential model is not polluted by protocol shape**: the CustomProvider schema, Repository, the `mask_secret` path, encrypted storage, the UI credential form (the settings page "添加自定义供应商" (Add custom provider)) and `/api/v1/custom-providers/discover` introduce no "multi-field credential" special cases. Each new native multi-field protocol (Kling, Vertex, AKSK, some future new provider) no longer needs to touch this whole chain — all protocol adaptation extension points converge on the backend implementations in `lib/backends/video_backends/`, `lib/backends/image_backends/`, `lib/backends/text_backends/` and registration in `ENDPOINT_REGISTRY`, and the credential layer is stable.
- **The same backend implementation can carry two credential modes**: the typical example is `KlingVideoBackend` (`lib/backends/video_backends/kling.py`, `auth_mode="jwt"|"bearer"`): the auth mode is chosen by credential shape — for the built-in provider `kling`, filling `access_key + secret_key` uses JWT (`KlingJWTManager`), filling `api_key` uses Bearer, and when both are filled api_key takes precedence (`_build_kling` in `lib/backends/backend_assembly/specs.py`); the `kling-video` endpoint closure only takes `api_key + base_url` and is always Bearer. The two modes share the same request body schema and state machine mapping. This is the same pattern as the existing dual mode `backend_type=aistudio|vertex` in `GeminiVideoBackend` (`lib/backends/video_backends/gemini.py`): the backend is the carrier of the protocol shape, and the authentication method is a construction parameter.
- **Protocols that cannot be relayed will never appear in the endpoint dropdown**: Vertex AI Veo (a service account JSON file cannot be redirected to a relay via base_url), Volcengine visual CV (SigV4-like signatures are usually not forwarded verbatim by relays and get rewrapped by the relay into NewAPI protocol pass-through) and so on are permanently absent from the custom provider UI. This is a conscious trade-off — if a user really needs this, use a built-in provider.
- **A future plugin mechanism must continue this constraint**: when a runtime plugin mechanism lands, plugin endpoints likewise can only take `api_key` + `base_url`; a plugin that wants to expose a multi-field protocol must bring its own "built-in provider style" declaration (and that path amounts to the plugin providing its own PROVIDER_REGISTRY extension, with significantly higher complexity, which this ADR does not presuppose). This constraint keeps the plugin interface surface stable.
- **GLOSSARY.md already includes this principle in the glossary** (the "自定义供应商（custom provider）" entry); this ADR gives the decision rationale for "why not extend the credential model", complementing the glossary's description of "what it is". Any later PR that wants to make an exception (adding a JSON credential field, adding a secondary key field) must first deprecate this ADR.
- **The constraint must not be bypassed by "concatenating a delimited string inside the api_key field"** (e.g. `api_key="access_key:secret_key"` split apart internally). This breaks `mask_secret`'s single-secret display semantics, leaving the UI unable to tell which part is the real secret; it also mixes string-parsing logic into backend implementations, blurring the boundary between "protocol structure" and "credential expression". If a user scenario really requires an exception, the correct path is to write a new built-in provider, not to hack the endpoint closure.
- **This ADR is consistent in style with `docs/adr/0001-image-capability-resolved-at-execution.md`**: it draws the "determined at runtime vs declared at startup" boundary clearly — the credential shape is declared at provider registration (`PROVIDER_REGISTRY.required_keys`) and is not extended dynamically at request time. Endpoints are constructed at runtime, but the credential shape is statically constrained by ENDPOINT_REGISTRY + the CustomProvider schema.
