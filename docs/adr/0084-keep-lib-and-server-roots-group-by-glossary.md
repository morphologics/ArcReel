# Keep the core library and server as two roots; organise directories into packages by the domain glossary

Backend code has two roots: `lib/` (core library) and `server/` (server). The core library's top level had 131 Python files, of which 130 loose modules sat flat next to the root `__init__.py`; filename prefixes had long been de facto subdomains, the application service layer `server/services/` also had 30 flat modules, and the directories were not isomorphic to the domain glossary (`GLOSSARY.md`): after reading the glossary, you still did not know where to look for code.

We decided to **keep the two roots `lib` and `server` with their names unchanged, keep the server's external launch entry unchanged, and organise packages under both roots by the glossary**: the core library's top level holds only packages, no loose files; which package a module belongs to depends on which glossary section's terms it implements, with the filename prefix used only for initial sorting; if prefix clusters appear again inside a package, it is split again (the "Scripts and storyboards" section therefore became the three packages `script` / `episode` / `prompts`); there is no cap on file count, and no `common` / `utils`-style packages are created; pure technical utilities are gathered in the clearly named `infra`. The application service layer gets subpackages by existing clusters; pure domain modules among them that do not depend on the server and have no implicit coupling (module-level global state, session lifecycle, delivery-layer contracts) move into the corresponding core library package. The criterion for the boundary is "what the module is", not "who uses it": a domain module used only by the server still belongs to the core library.

Each module's new home was written in a mapping table, which was the single source of truth for this regrouping: the move script executed according to the table, and the dry-run script used it with the existing import graph to compute inter-package cycles under the new package boundaries, the verdicts of existing import-linter contracts after rewriting, and where mirrored tests would go. The move left no compatibility layer for old paths (no re-exports), and filenames stayed the same by default, only the directory changed. The mapping table and the two scripts entered the main branch temporarily and were deleted after the move; their final versions remain under `scripts/regroup/` in commit `e00e28b8`.

**Explicitly rejected**:

- **Vertical slicing by domain** (one directory per domain, containing its routes, agent tools, services and core logic). The same domain core is shared by four kinds of entry point: HTTP routes, agent tools, remote MCP and the generation worker; slicing would scatter the agent tool runtime (unified tool registration, permissions and session context) across domain directories and make every domain directory depend on the delivery layer, so the boundary "the core library does not know HTTP, the Agent SDK or SSE exist" could no longer be checked.
- **Merging into a single root package** (e.g. `arcreel/`, with `core` and `server` under it). The only gain is a more conventional name; the cost is that the server's external launch entry (container images, local development commands and external launchers all start via `server.app:app`) would all have to change, and merging by itself does not bring the directories closer to the glossary.
- **Renaming only the core library**. The name `lib` really says nothing, but another name would equally fail to say which domains it consists of; what expresses the domains is the packages under it, not the root's name; the cost of renaming is the same as merging into a single root package.

## Inter-package cycles are recorded honestly, not eliminated by renaming or splitting files

Under the new package boundaries, 14 top-level core library packages are in the same strongly connected component. There are two causes: the current code already has a module-level cycle of 77 modules (the project manager, the artifact manifest family, config resolution, custom providers and some repositories are mutually reachable), spanning more than ten domains, which no assignment by glossary section can break; and the `project` package holds both low-level vocabulary referenced by every domain (asset types, resource paths, project schema version) and the top-level orchestrator that references every domain (the project manager). The order of handling was: first adjust assignment, then record as an existing exemption; splitting files is a behavioural refactor and outside the scope of regrouping. Three assignments therefore deviate from the filename-prefix intuition: task type buckets go to `backends` rather than `config` (putting them in `config` would make the lowest layer of the layering contract depend directly on an upper layer); reference image snapshots go to `artifacts` and image-N numbering goes to `prompts` (putting them in `references` would make the reference image package transitively depend on the reference-to-video subpackage, breaking the route-neutrality constraint). The remaining inter-package cycles were at the time recorded one by one in the mapping table's `[accepted_edges]`, each stating why it could not be eliminated by adjusting assignment.

## Consequences

- After reading the glossary you can find packages by section; a new module is placed according to "which section's terms it implements", and disputed assignments use the rulings in the mapping table's `[rulings]` at the time as precedent.
- The core library's packages are not layered: inter-package cycles are existing state; whether and when to establish contracts for inter-package direction is decided case by case when a direction actually causes problems, rather than pre-establishing a contract for every new package.
- The main branch undergoes this large-scale path change only once. A branch cut before the move can, after syncing with mainline, retrieve the move script from the commit above (`git checkout e00e28b8 -- scripts/regroup`), run `migrate.py` to rewrite its own newly added code, then self-check with `migrate.py --check`, and not commit it afterwards.
- Filenames are kept as-is, so some paths carry a prefix that duplicates the package name (e.g. `lib/artifacts/artifact_manifest.py`). Removing the prefixes would change mock paths and search terms across the whole repository once again, for the gain of a few fewer characters; it is not done this time.
