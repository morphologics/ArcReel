# Image capability (t2i/i2i) is resolved only at execution time; worker rate-limit routing uses an approximate capability

Whether a storyboard shot goes through text-to-image (t2i) or image-to-image (i2i) depends on **whether it has reference images**; and the set of reference images (the referenced character/scene/prop sheets, plus the **previous storyboard frame** referenced for visual continuity) is a snapshot of project state "at the moment drawing starts" — especially during batch regeneration, the frame N-1 that frame N depends on has often not been drawn yet at enqueue time. Capability is therefore a derived fact that can only be determined at execution time, and the two pre-execution stages — enqueue and worker claim — **structurally cannot know it**. On this basis we decided: capability is resolved only in the execution layer, and enqueue does not freeze the execution identity (the enqueue-time backend snapshot has been removed); enqueue still derives an advisory `provider_id` from the representative slot and stores it on the task row (`_derive_execution_model_for_enqueue`; if derivation fails it is left NULL and takes the fallback branch), used only for claim SQL pool filtering and rate-limit routing; the execution entry point re-resolves precisely, and if the result disagrees with the record it rewrites the record and requeues the task in place, without calling the provider.

Image edit tasks (`image_edit`, see `docs/adr/0050`) are the only exception: they use the current image as the sole reference image and are **always i2i**, so the capability is known at enqueue time; enqueue and claim resolve the provider precisely from the i2i slot for rate-limit routing, and if the i2i slot is unavailable the task is rejected before enqueue.

## Consequences

- Concurrency rate limiting (rate-limit pool routing) needs a provider, but the real capability is not available before execution, so apart from `image_edit` (resolved precisely from the i2i slot) a **representative** provider is uniformly taken with `capability="t2i"` — derived at enqueue time and stored on the task row, and claim SQL filters on it.
- Only when the user has **configured different providers** for t2i and i2i in the same project, and the task actually goes i2i, will the claim first land on the t2i pool; after the execution entry point resolves the i2i provider, it rewrites the record and requeues in place, so the task is requeued one extra time and then takes a slot in the pool that actually executes it. This is an accepted cost: as a result, the concurrency cap holds exactly for the provider that actually executes.
- This extra requeue **cannot be eliminated**: as long as "t2i/i2i can be configured with different providers" and "capability is only determined at execution time" both hold, slot ownership before execution can only be approximate. **Do not try to "fix" it by recording needs_i2i at enqueue/claim time** — that would require copying the execution layer's reference-image collection logic into the scheduling layer, and in batch scenarios the answer at enqueue time is simply wrong.
