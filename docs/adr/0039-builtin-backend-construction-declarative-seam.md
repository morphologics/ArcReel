# Built-in provider backend construction is consolidated into a declarative table, symmetric with the custom endpoint table but not merged with it

Before this decision, backend construction for built-in providers (assembling constructor kwargs from the provider config + the resolved model) was written out imperatively as `if gemini / elif kling / else` in three places in `server/services/tasks/generation_tasks.py` — `_get_or_create_video_backend` / `_get_or_create_image_backend` / `_get_or_create_audio_backend` — plus once more in `lib/backends/text_backends/factory.py` (these functions now live in `server/services/tasks/generation_context.py` and, per the decision below, delegate to `lib/backends/backend_assembly`). All per-provider knowledge leaked into the callers — gemini's `aistudio|vertex` dual mode, kling's JWT double secret + `api_model_name` decoupling, each provider's base_url precedence, dashscope/minimax text going through OpenAI-compat, and other differences were scattered across these four branches. There were also two copies of the `PROVIDER_ID_TO_BACKEND` mapping at the time (media side and text side), and they had already drifted: the text side treated dashscope/minimax as `openai`, the media side did not. Meanwhile the custom-provider side had long since turned the same job into one deep declarative table using `ENDPOINT_REGISTRY` in `lib/custom_provider/endpoints.py` (each `EndpointSpec` carries a `build_backend` closure) + a two-line forward in `factory.py`. Two parallel styles of writing the same thing is the shallow duplication this decision removes.

We decided to raise the built-in side to the same level as the custom side and consolidate it into one seam, "provider config + model → backend": ① create `lib/backends/backend_assembly/` (in lib — the seam spans both the built-in and custom families, and lib cannot import server), exposing one unified entry point `assemble_backend(provider_id, media_type, model_id, ...)` that internally dispatches to the two families' adapters via `is_custom_provider`; ② on the built-in side, add a `(provider_id, media_type) → ProviderSpec` table, each entry carrying a build closure, isomorphic to the custom side's `EndpointSpec`; ③ split construction into two phases, **async loading** (query DB/config and produce a `LoadedConfig` envelope: credential overlay + `PROVIDER_REGISTRY` meta + shared rate_limiter) / **sync construction** (a pure closure reads the envelope and assembles the backend); the sync phase is the deep-module core that can be unit-tested directly without a DB; ④ the custom side's `ENDPOINT_REGISTRY` is not changed by a single line; the DB-loading logic of `_create_custom_backend` moves down from server into lib, merging with the duplicate inlined in the text factory.

**Explicitly not adopted**: ① **Merging the two families into one table** — the two sides' credential models are fundamentally different (custom is fixed `api_key`+`base_url`, see `docs/adr/0008`; built-in has multi-secret typed columns, see `docs/adr/0037`), and `EndpointSpec` also carries frontend catalog fields (video caps, request path, display name) the built-in side doesn't need; merging would either lose types or stuff in `Any`. The two tables share one entry point (`assemble_backend`) but not a table structure — one door, two symmetric rooms behind it. ② **Introducing a unified `BackendRequest` input value object** (flattening the two input shapes so the single entry point takes only one parameter) — it has no second consumer and is just glue to make the two build signatures look alike; the deletion test sees through it: delete it and the complexity does not reappear in callers (callers already dispatch at `is_custom_provider`), and it would also force the two credential models that 0008/0037 deliberately separated into one type. The built-in build takes `LoadedConfig`, the custom build takes `CustomProvider`; each takes its own. ③ **Using a purely declarative data spec for the built-in specs of the construction seam** (a credential mapping table + a base_url strategy enum instead of closures) — this seam and the protocol-expression layer are two layers: the declarative definition of call endpoints (`docs/adr/0067`) expresses the HTTP request/response protocol itself, whereas this seam handles loading and assembling "provider config + model → constructor kwargs" and has to deal with construction forks such as gemini's dual mode, kling's double secret, and `api_model_name` decoupling; for the current ~11 built-in providers, pure data would be over-configuration and would still ultimately need a closure escape hatch. The closure approach uses the same technique as the custom side's `EndpointSpec` template and the dispatch-by-`kind` of pricing in `docs/adr/0009`. ④ **"Absent means default" for simple-family providers** (if no spec is found, apply a generic simple closure) — fail-silent: a mistyped `provider_id` would silently build a simple backend instead of raising an error; instead each simple provider registers one explicit line (sharing the same build closure), which is fail-loud and makes the table the complete picture, at the cost of only one line of declaration.

## Consequences

- **Adding a built-in provider drops from "change 4 files in 5 places" to "add one line"**: the simple family adds one `ProviderSpec`, the special-case family adds one plus a build closure, symmetric with adding one `EndpointSpec` on the custom side; the three `_get_or_create_*` in `generation_context.py` and the text factory are no longer touched.
- **The two copies of `PROVIDER_ID_TO_BACKEND` are merged** into the registry field of `ProviderSpec` (each `(provider, media)` row declares which registry backend it maps to), so drift is no longer possible at the data-structure level.
- **The construction core can be unit-tested without a DB**: hand-build a `LoadedConfig` envelope + model_id and directly assert the constructor arguments of the resulting backend (kling double-secret pass-through, gemini `backend_type` fork, dashscope text base_url derivation, kling `api_model_name` decoupling), with no DB or mock resolver needed; the async loading phase is tested with an in-memory DB (local-substitutable). Validation of the built-in table has two tiers: internal self-consistency checks such as `build` being callable and `(provider, media)` being unique run fail-fast at import time (same as `endpoints.py::_validate_video_caps_declarations`, equally lightweight); whereas "all `registry` names are in the media backend registry" can only be asserted by importing all of `lib.{image,video,text}_backends`, so to keep lightweight scenarios (CLI / migrations) from being forced to load all backends just by importing this seam, it goes into unit tests (importing the full set inside tests is harmless), not import time.
- **Caching stays with the caller**: `_backend_cache` is a performance concern of the server execution layer and does not sink into the seam; the seam is stateless and purely constructive, which makes concurrency and testing easy.
- **Scope boundary**: the seam only "builds backend instances" and does not interfere with lifecycle concerns such as task execution, queue scheduling, or billing — `provider_job_id` persistence is in `docs/adr/0007`, queue scheduling in `docs/adr/0010`, pricing in `docs/adr/0009`; none are in this seam.
- **Orthogonal to a future plugin marketplace**: if users sharing/installing third-party provider adapters lands, it will be a separate follow-up epic on the custom side's `ENDPOINT_REGISTRY` (`docs/adr/0008` already points the way for plugins: a plugin can only take `api_key`+`base_url`, and needs its own "built-in-provider-style" declaration to have multiple fields). This ADR consolidates the **built-in** side; the "two families are not merged" isolation is precisely what keeps a clean slot side for that epic, which is out of scope here.
- **Change gate**: any later PR that wants to merge the two tables, introduce a unified `BackendRequest`, or revert built-in construction to scattered imperative branches must deprecate this ADR first.
